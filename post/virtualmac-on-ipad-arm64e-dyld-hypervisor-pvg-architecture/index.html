把完整 macOS 装进 M1/M2 iPad：拆解 Virtual Mac on iPad 的 arm64e 缓存重织、无 Launchd 握手与 AGX 纹理逆向移植架构

2026-11-20 22 min read # arm64e # 架构剖析 # macOS # iPadOS # 虚拟化 # Metal

“在搭载 M1/M2 芯片的 iPad 上原生运行完整的 macOS”，这个极客社区追逐了十余年的执念，随着 Virtual Mac on iPad（GitHub 开源仓库：nfzerox/VirtualMacOniPad，MIT 协议）的问世正式成为现实。与 UTM 基于 QEMU 的纯软件/指令模拟路线，或 Henge、macPad 等无越狱替代方案不同，这个项目走了一条极为硬核的底层路径：直接从 macOS 13.2.1（22D68）的 dyld_shared_cache_arm64e 中逆向抽取出苹果原生的 Hypervisor、Virtualization 与 ParavirtualizedGraphics 虚拟化栈，重建为可在 iPadOS 14.0 至 16.3.1 上加载的 arm64e 动态库，并补齐缺失的内核 USB DFU 通道与 GPU 纹理硬件能力，最终让 iPad 原生跑起 macOS 12 Monterey 直至 macOS 27 Golden Gate，甚至流畅运行 Xcode、Logic Pro 与 Final Cut Pro。

为了摸清这套超过 32,000 行 代码（涵盖 Python、Go、C、Objective-C 与 Metal Shader）的工程奇迹究竟是如何打通重重系统隔离的，我完整拉取并逐层审计了 nfzerox/VirtualMacOniPad 源码仓库。下面我将从历史时间窗口、首个可加载 arm64e 共享缓存解包器、跨代 ABI 降级外科、无 Launchd 进程握手、PVG 图形与 AGX BC 纹理逆向移植，以及 Guest 侧 OpenGL 加速这六个维度，还原它的真实底层架构。

[!NOTE] 代码审计基线与硬件边界说明
本文所有符号名、十六进制偏移、指令序列、Mach-O 结构体字段与环境变量，均直接源自对 nfzerox/VirtualMacOniPad 仓库主分支最新提交（20166d7）源码的逐行阅读。需要明确的是，该项目严格限定运行在 越狱状态下的 iPad Pro（M1/M2）、iPad Air（M1）或 iPhone 14 Pro / 14 Pro Max，且系统版本必须位于 iPadOS 14.0 至 16.3.1 之间（在 VirtualMac/packaging/DEBIAN/control 中被硬性约束为 firmware (<< 16.4)）。原因非常残酷：从 iPadOS 16.4 开始，苹果彻底从 iPadOS 的 XNU 内核中移除了 EL2 Hypervisor 硬件虚拟化支持。

一、全局拓扑：把苹果桌面虚拟化栈“整套搬家”到 iPadOS

在阅读 VirtualMac/scripts/build-frameworks.sh 和 VirtualMac/scripts/build-ipad-vm.sh 时，我立刻看清了这个项目与传统虚拟机方案的本质区别：它没有自己重写 VMM（虚拟机监视器）或虚拟显卡，而是直接借用了 macOS 自带的整个原生虚拟化生态。

要把这套原本只存在于 macOS 13.2.1（Build 22D68）里的重型基础设施搬进 iPadOS，开发者必须连续跨过五道“几乎不可能”的技术天堑：

  1. 共享缓存不可逆困局：dyld_shared_cache 合并优化是单向的，传统抽取工具（如 DyldExtractor）抽出来的 arm64e 二进制文件缺少重定位链与 PAC 指针认证信息，iPadOS 的 dyld 根本无法加载；
  2. 跨代内核与运行时 ABI 断层：iPadOS 14 使用基于 XNU 20 的旧版 Hypervisor 且缺少新版 IPA 位宽配置接口；iPadOS 15 的 Objective-C 运行时则会把 macOS 13 签过 DA 密钥 PAC 的 class_t::data 当成非法内存地址直接崩溃；
  3. 无 Launchd XPC 服务域：macOS 上的 VirtualMachine.xpc 和 Installation.xpc 依赖系统级 launchd 的 XPCService 注册域完成发现与启动，而越狱后的 iPadOS user/501 域根本无法拉起它们；
  4. 内核硬件与驱动缺口：iPadOS 内核没有 AppleUSBUserHCI 内核扩展，导致恢复/安装 macOS IPSW 时无法识别虚拟机的 DFU USB 设备；同时 iPadOS 16.3.1 的 AGX 驱动尚未正式开放 PC/Mac 常用的 BC1–BC7 块压缩纹理格式；
  5. Jetsam 内存双倍记账陷阱：ParavirtualizedGraphics（PVG）会将客体内存二次映射到图形任务地址空间，在 16 GiB 内存的 iPad Pro 上，一个 8 GiB 内存的 macOS 虚拟机加上 8 GiB Metal 负载会瞬间触发物理内存上限，导致整个应用进程组被 Jetsam 强杀。

接下来，我逐一拆解源码中针对这五大天堑的工程解法。

二、核心突破一：uncache.py 与首个可加载 arm64e 共享缓存重建器

整个项目的基石位于 VirtualMac/vz/uncache.py（1,684 行 Python）及其配套的 Go 批量符号工具 VirtualMac/vz/ipsw_patches/dyld_a2sb.go。在它的注释与 README.md 中，作者坦言这是社区首个真正可加载的 arm64e 框架抽取流水线。

我顺着 build-frameworks.sh 和 uncache.py 的执行链路追踪了一遍，它从 macOS 13.2.1 共享缓存中主要抽取了 Hypervisor、ParavirtualizedGraphics、Virtualization、MetalSerializer，以及后续管线中的 vmnet、Netrb、VideoToolboxParavirtualizationSupport、DiskImages2 等核心框架。重织过程分为五个极为精密的步骤：

  1. 提取与批处理符号反查（dyldex + ipsw-a2sb）：
    先使用打过补丁的 DyldExtractor（VirtualMac/patches/dyldextractor-2.2.2-arm64e.patch，修复了相对方法选择器偏移与协议局部化）导出原始 raw 镜像。随后 uncache.py 遍历缓存中的 dyld_cache_slide_pointer3 信息，将“镜像内基址重定位（Rebase）”与“跨镜像符号绑定（Bind）”拆分开，再把所有外部地址批量喂给魔改版 ipsw dyld a2sb（一次打开 DSC 与 .a2s 缓存，以 0xADDR\tSYMBOL\tIMAGE 吐出符号），避免单次查询反复加载数 GB 缓存的耗时。
  2. Objective-C 元数据局部化救援：
    共享缓存会把所有 Selector 和类名字符串去重合并到 libobjc 的共享 __OBJC_RO 池里，导致 a2sb 无法解析出这些无名字符串引用。uncache.py 中的 build_local_str_va 与 read_cache_cstrs 会主动去缓存里把字符串读出来，在当前镜像自身的 S_CSTRING_LITERALS 节中匹配本地副本并转化为内部 Rebase。同时，它会清理 __objc_imageinfo 中的 OptimizedByDyld (0x8) | OptimizedByDyldClosure (0x80) | DyldCategoriesOptimized (0x1) 预优化标志位，并修复 DyldExtractor 生成的 __EXTRA_OBJC 合成段里的陈旧绝对指针——否则 iOS 的 objc 运行时在加载阶段急切解引用 protocol_t 的 mangledName 时会立刻触发 SIGSEGV。
  3. 保留 PAC 的 arm64e 链式指针重织：
    为了不破坏 Apple Silicon 的指针认证安全模型，uncache.py 手工实现了 pack_rebase、pack_auth_rebase、pack_bind、pack_auth_bind 四个打包器，重新构建 GOT 与 __auth_got（针对函数指针使用 IA 密钥与 addrDiv=1），并在每页（PAGE = 0x4000，即 16 KiB）内按链表形式编织出 DYLD_CHAINED_PTR_ARM64E_USERLAND（格式编码 9）指针链，最后在 __LINKEDIT 末尾拼接 LC_DYLD_CHAINED_FIXUPS（0x80000034）载荷并清除 MH_DYLIB_IN_CACHE（0x80000000）标记。值得一提的是，它在生成 DYLD_CHAINED_IMPORT 时特意将符号设为 weak_import=1（除非设置 VZ_NO_WEAK_IMPORTS），这样少数 iOS 上缺失的纯 macOS API（例如 AppKit 的 NSBitmapImageRep）在加载时会安全绑定为 NULL 而不会拖垮整个框架加载。
  4. 跨平台路径改写与缺席依赖弱化：
    rewrite_dylib_paths 会把 macOS 框架路径里的 Versions/A/ 扁平化（匹配 iOS 习惯）；weaken_absent_dylibs 则把 MetalSerializer、vmnet 这类 iPadOS 系统目录里不存在的依赖从 LC_LOAD_DYLIB 降级为 LC_LOAD_WEAK_DYLIB。
  5. 平台烙印改写与“禁用 ldid”铁律（stamp_ios.py）：
    VirtualMac/vz/stamp_ios.py 会把 LC_BUILD_VERSION（0x32）中的平台字段改为 PLATFORM_IOS = 2，将最低版本设为 16.0（或兼容构建的 14.5），然后调用系统 codesign -f -s - 进行 Ad-hoc 签名。源码注释里有一句血泪警告：这里绝不能使用 ldid -S，因为 ldid 重建 __LINKEDIT 时会直接丢弃刚刚辛苦织出来的 LC_DYLD_CHAINED_FIXUPS 命令！

面向 iPadOS 14 与 15 的跨代 ABI 外科补丁

为了同时兼容 iPadOS 14、15 和 16，仓库还准备了两套堪称外科手术级别的兼容方案：

  • iPadOS 15 的 Objective-C PAC 降级（patch_ipados15_objc_class_data.py）：
    macOS 13 Ventura 在编译时会使用 DA 密钥（key = 2，diversity = 0x61F8）对 __objc_data 段中每个 40 字节 class_t 结构的第 5 个字段 data 进行 PAC 签名。但 iPadOS 15 的 Objective-C 运行时并不期待这个字段带有认证位，它会把高位 PAC 比特直接当成内存地址去解引用，导致 readClass 崩溃。这个脚本专门遍历 __objc_data，精准匹配 diversity == 0x61F8 且 key == 2 的指针并将其降级为普通 Rebase，同时保持 isa 和 superclass 的 PAC 认证完好无损。
  • iPadOS 14 的“双代缝合”内核兼容（build-ipados14-hypervisor.sh + hypervisor14_compat.c）：
    iPadOS 14 运行在 XNU 20 上，不支持 Ventura 版 Hypervisor.framework。构建脚本干脆从 macOS 11 Big Sur（20G165） 抽取了与 XNU 20 对齐的 HypervisorBigSur，再用 hypervisor14_compat.c 包一层门面，通过 dlsym(RTLD_NEXT, ...) + 裸汇编跳转转发基础 API，并对 Ventura VMM 新增的 hv_vm_config_get/set_ipa_size 返回固定 36-bit IPA 位宽（kDefaultIPABitLength = 36）；同时从 Ventura 抽取出 libc++.1.dylib（LibCxx.dylib）喂给 VMM，甚至在 vmmhook.m 中编译了一段宏开关 VZ_IPADOS14_NETWORK_COMPAT——当检测到 Big Sur 的 vmnet 缺乏 Ventura 校验和卸载（Checksum Offload）契约时，在数据面拦截 vmnet_write 手工重算 IPv4 与 TCP/UDP 校验和！

三、核心突破二：无 Launchd 匿名 XPC 握手、VMM 指令手术与 Jetsam 防杀

解决了框架加载问题后，虚拟机依然跑不起来——因为 Apple 的 Virtualization.framework 并不是在 App 进程里跑虚拟机，而是通过 XPC 拉起独立的特权服务 com.apple.Virtualization.VirtualMachine.xpc（简称 VMM）和安装服务 Installation.xpc。在没有完整 macOS launchd XPCService 域的越狱 iPad 上，VMM 的 main() 一调用 xpc_main() 就会报错 "Could not retrieve service name" 并立刻退出。

阅读 VirtualMac/vz/host/vzxpchook.m 与 VirtualMac/vz/host/vmmhook.m 时，我被这套跨越 Mach 内核边界的进程握手设计彻底折服：

  1. 匿名监听 + 挂起派生 + task_for_pid 注入 Mach 权柄：
    宿主侧的 vzxpchook.m 会拦截 xpc_connection_create。当目标服务名为 com.apple.Virtualization.VirtualMachine 时，它在当前进程内用 xpc_connection_create(NULL, ...) 创建一个无需 launchd 注册的匿名监听器 L，并调用 xpc_endpoint_create(L) 生成端点对象 E，然后直接从 E + 0x18（EP_PORT_OFF）偏移处读取底层的 Mach 发送权（Send Right）。接着，宿主以 POSIX_SPAWN_START_SUSPENDED 挂起状态 posix_spawn 拉起 VMM 二进制，趁它第一条指令尚未执行，调用 task_for_pid 拿到子进程任务端口，再用 mach_port_insert_right 把匿名监听器的发送权强行插进子进程的 Mach 端口命名空间，通过环境变量 VMM_EP_PORT 告知端口编号后再恢复子进程运行。
  2. 子进程劫持 xpc_main 反向汇合：
    VMM 启动后，预加载的 vmmhook.m 拦截 xpc_main(handler)，读取 VMM_EP_PORT 重新拼装出 xpc_endpoint_t 并创建反向连接，从而触发宿主匿名监听器 L 的回调拿到对等连接 P，无缝交还给上层的 [VZVirtualMachine start]！而针对 Installation.xpc（安装过程会建立多个 XPC 连接），vzxpchook.m 还用互斥锁 gInstallationLock 复用同一个监听器端点，确保所有连接都路由到同一个恢复会话中。

针对 VirtualMachine.xpc（22D68）的定点 ARM64 指令手术

由于 iPadOS 内核与硬件拓扑和 Mac 存在差异，VMM 内部有两个致命的死锁与越界漏洞必须通过二进制补丁直接“拆弹”：

  • 允许缺失的宿主设备继续启动（patch_vmm_optional_devices.py）：
    iPadOS 内核里根本没有 AppleUSBUserHCI 驱动，导致 VMM 初始化 com.apple.virtualization.avp.usb-device-controller 时 IOUSBHostControllerInterface 返回 nil 并中止整个虚拟机。作者逆向定位到设备工厂循环在 0x154F20 处有一条判断失败跳转指令 tbz w26, #0, failure（机器码 0x3600017A），而后面的代码原本就支持空指针设备！于是脚本严格校验前后 4 条指令上下文，直接把 0x154F20 改写为 NOP（0xD503201F），优雅放行。
  • 修复 PCI 总线 0x7ff 自动地址越界踩内存（patch_vmm_pci_address.py）：
    在 iPadOS 上，某个 PCI 设备有时会保留自动分配哨兵值 0x7ff，而 macOS VMM 居然直接拿 0x7ff 当成 256 项 PCI 总线表的数组下标去读写，直接越界踩坏总线后方约 16 KiB 的堆内存，导致启动时而报“槽位被占用”、时而诡异成功随后崩溃！因为重织后的二进制不便新增导入表，作者极其巧妙地征用了二进制里一段未使用的 VirtioSocketDevice 日志字符串尾部（偏移 0x1A5F4A，4 字节对齐到 0x1A5F4C），往里面硬塞了一段 14 条原生 ARM64 机器码（cmp x8, #0x7ff -> 扫描 256 个槽位找第一个空位），再把 0x179DF0 处的原地址计算指令 add x8, x24, x8, lsl #3 替换为跳转到这段字符串空洞的 bl 指令！

解决 Jetsam 杀进程的“双倍高水位 + 优先级倒挂”策略

在 vmmhook.m 的 configure_vmm_memory_policy()（第 82 行）和 VirtualMacApp.m 的 setVMJetsamProtection()（第 51 行）中，我看到了极为老练的 Darwin 内存账本调试经验：

  1. VMM 放宽至 2 倍物理内存高水位：PVG 会将 Guest 内存页二次映射进图形任务，XNU 的进程记账账本会把同一块物理页算两遍。在一台 16 GiB 内存的 iPad Pro 上，开一个 8 GiB 内存的 macOS 虚拟机加上 8 GiB Metal 渲染工作负载，账本立刻触及 16 GiB（1x 物理内存）红线被 Jetsam 秒杀。vmmhook.m 通过 memorystatus_control（命令字 7）把非致命高水位线（memlimit_active / memlimit_inactive）直接拉高到 physicalBytes >> 19（即 2 倍物理内存 MiB 数），解除伪超限误杀。
  2. 宿主 UI 进程优先级压过 VMM：iPadOS 16 上提取的 VMM 作为系统服务默认跑在 Jetsam 优先级 180 档位，而普通前台 UIKit App 只在 100 档位。一旦遇到真实物理内存吃紧，系统会先杀掉轻量的 UI 宿主、后杀庞大的 VMM，导致界面突然闪退。VirtualMacApp.m 主动调用 memorystatus_control（命令字 2）将自身断言优先级抬高到 190（iPadOS 14/15 为 19），永远压在 VMM 上方一档，保证压力来袭时优先回收吃内存的 VMM 并让宿主界面从容弹出停机诊断。

四、核心突破三：PVG Metal 桥接、iPadOS 16.4 BC 纹理逆向移植与 OpenGL/FCP 加速

如果说前面解决的是“跑得起来”，那么图形栈（metalshim.m、native_bc_texture_support.m、pvg_display.metal 与 OpenGLPVGCompat.m）解决的就是“能用 Final Cut Pro 和 Metal 3D 加速”。

1. 宿主侧 metalshim.m 与三版本 Shader 重建

iOS 的 Metal.framework 面向单核集成 GPU，缺失了 macOS 版 VMM 强依赖的多卡枚举 MTLCopyAllDevices()、着色器缓存路径 MTLSetShaderCachePath() 以及 MTLDevice.isLowPower / isRemovable / isHeadless / isDepth24Stencil8PixelFormatSupported / isFramebufferReadSupported 等查询选择器。metalshim.m 通过重导出真实 Metal.framework 补全了这些入口，并把 macOS 专属的 MTLStorageModeManaged（原始值 1）全部静默转为 Apple Silicon 统一内存的 MTLStorageModeShared。

同时，由于未修改的 macOS ParavirtualizedGraphics 里的 default.metallib 无法在旧版 iPadOS Metal 运行时直接加载，VirtualMac/vz/shaders/pvg_display.metal 根据原始 AIR 反射元数据一比一还原了 BlitInRGB_2P_XR10_A8、BlitOutRGB_2P_XR10_A8 和带 Gamma 查表矩阵的显示片元着色器，并由 build-frameworks.sh / build-ipad-vm.sh 分别以 -std=metal3.0（iPadOS 16）、-std=ios-metal2.4（iPadOS 15）和 -std=ios-metal2.3（iPadOS 14.5）编译出三套 .metallib 按宿主版本动态加载。

2. 把 iPadOS 16.4 的原生 BC1–BC7 压缩纹理硬塞回 16.3.1

这是我在整份仓库中看到最惊艳的逆向发现之一（见 VirtualMac/vz/host/native_bc_texture_support.m）：

macOS 应用和游戏大量使用 BC1–BC7（MTLPixelFormat 130–135、140–143、150–153）块压缩纹理，而苹果直到 iPadOS 16.4 才正式在 iPad 端开放这些格式。作者通过对比 iPadOS 16.3.1（20D67）与 16.4 的 AGXMetal* 驱动二进制文件后发现——硬件和底层 GPU 命令管线早在 iOS/iPadOS 14–16.3.1 里就已经全部就绪了！驱动里唯一缺失的，只是 TextureFormat 分发开关表里的那 14 条 0x60 字节表项！

于是 native_bc_texture_support.m 做了一个不依赖固定地址、跨芯片代际通吃的动态 Hook：

  • 遍历 _dyld_image_count()，匹配位于 /System/Library/Extensions/AGXMetal 路径下的硬件驱动（兼容 AGXMetal13_3、AGXMetalG14G、AGXMetalG15 等）；
  • 在 __TEXT,__text 段中用 13 条指令指纹模式 MatchTextureFormatChooser（同时兼容 iPadOS 14 的 x0 传参和 15/16 的 w0 传参）定位私有纹理格式选择函数；
  • 通过 MSHookFunction（自动寻找 libellekit.dylib 或 libhooker.dylib）将其拦截到自定义的 ChooseTextureFormat，在检测到请求格式为 130..153 时直接返回从 16.4 提取出的 14 组 kBCFormatDescriptors 结构体，并在描述符校验层用尺寸等效的 ETC2 / EAC / ASTC 代理格式绕过 iOS 上层校验——从而在 iPadOS 16.3.1 上实现了真正的零开销硬件级 BC 纹理采样！

3. 超越 UTM 与 VirtualBuddy：Guest 侧 OpenGLPVGCompat.m 激活 Final Cut Pro

连运行在真实 Mac 上的 VirtualBuddy 和 UTM 默认都无法在 macOS 虚拟机里提供 OpenGL/OpenCL 硬件加速与 Final Cut Pro 支持，因为 macOS 系统默认不给半虚拟化显卡 AppleParavirtGPU 分配 AppleMetalOpenGLRenderer。

项目在 Guest 侧注入了 VirtualMac/vz/guest/OpenGLPVGCompat.m（并贴心地排除了 firefox 与 sublime_text 等冲突进程）：

  1. 伪装注册表与 GPU 家族：通过 __DATA,__interpose 劫持 IORegistryEntryCreateCFProperty，当查询 AppleParavirtGPU 的 IOGLBundleName 时强制返回 "AppleMetalOpenGLRenderer"；随后替换 AppleParavirtDevice 的 supportsFamily: 方法，对 1001..1007（即 Apple7 / M1 家族）全部返回 YES，诱导 GLDRendererMetal 走现代化的 agx2 渲染分支；
  2. 绕过 MetalSerializer 校验拒绝：Ventura 的序列化器会拒绝 GLD 提交的 defaultRasterSampleCount 和自定义 FSAA 采样位置。OpenGLPVGCompat.m 在 renderCommandEncoderWithDescriptor: 入口将其归零，且为了避免硬编码偏移，它直接解析 Objective-C 运行时 _private 成员变量的完整类型编码字符串（ivar_getTypeEncoding + NSGetSizeAndAlignment），动态算出 numCustomSamplePositions 的内存偏移并清零；
  3. 解决 Rosetta 2 转译下的 x86 OpenGL 顶点可见性 Bug：对于经过 Rosetta 2 转译运行的 x86_64 应用（通过 sysctl.proc_translated 检测），PVG 的无拷贝映射无法把 Rosetta 地址空间写入的 16 KiB GLD 暂存缓冲及时同步给宿主 GPU。垫片会在 setVertexBuffer:offset:atIndex: 时截取最多 16 * 1024 字节的 NSData 快照，改用内联 setVertexBytes:length:atIndex: 随命令缓冲区直接序列化发送。

五、核心突破四：用户态 DFU USB 恢复控制器、UIKit 桥接与外设生态

在首次从零安装 macOS .ipsw 固件时，苹果的 Installation.xpc 会把虚拟机重启进虚拟 DFU（恢复）模式，并通过 MobileDevice.framework 与虚拟设备的 USB 恢复控制器通信。但在 iPadOS 上，底层既没有 AppleUSBUserHCI 内核服务，也缺少 macOS 的 libcrypto.35.dylib / libssl.35.dylib。

  • 整套用户态恢复栈重建（build-ipad-installation.sh + installationhook.m + installation_usb_shim.m）：
    项目从 Xcode DeviceSupport 包里抽出了真品 MobileDevice.framework（1857）与 usbmuxd 守护进程（把监听路径 /var/run/usbmuxd 改写为 /tmp/vzusbmuxd），用 uncache.py 抽出了配套的 OpenSSL 35 动态库（并在 installationhook.m 里解码 ERR_get_implementation 的 ADRP/LDR 指令提前初始化错误表槽位，防止多线程初始化竞态崩溃）。最绝的是 installation_usb_shim.m（1,848 行 C 代码）：它完全不依赖内核 USB 驱动，直接在用户态为 MobileDevice 伪造了一套从 0x766d2000（io_service_t）、0x766d1000（io_connect_t）到 IOCFPlugInInterface 的假 IOKit 注册表与用户客户端句柄，然后把所有控制传输与 Bulk 端点帧通过 UNIX 域套接字 VZ_USB_BRIDGE_SOCKET 透传给 VMM 内部真实的 AVP 恢复 USB 控制器！
  • AppKit-on-UIKit 适配（NSViewShim.m）：
    Virtualization.framework 的显示视图 VZVirtualMachineView 继承自 AppKit 的 NSView。NSViewShim.m 直接在 UIKit 进程里实现了一个替身 NSView（继承自 UIView）来托管 _appKitLayer、代理 UIWindow.occlusionState，同时把 CGSMainConnectionID() 和触控板震动反馈函数 CGSActuateDeviceWithPattern() 垫成返回 0 的空实现——防止在 iPad 屏幕上点击第一下时因调用空指针 CGS 符号而直接闪退。
  • 原生直触与 120Hz 手柄透传（docs/experimental-native-touch.md & VirtualMac/docs/gamepad-network/README.md）：
    最近合并的 PR #86 还引入了实验性的原生多点触控直通（VZNativeTouchInput.m + VZNativeTouchIdentity.m）：只要配置相同的 displayUUID 注入到虚拟触控屏 HID 属性和 PVG 显示共享状态，就能让 Guest 的 WindowServer 把 UIKit 手指通过 _VZTouch / _VZMultiTouchEvent 原生绑定到对应屏幕，且安全边界极其克制——启动前会校验 Virtualization、VMM 和 ParavirtualizedGraphics 三个镜像的整文件 SHA-256 哈希，不匹配即拒绝启用。而游戏手柄转发桥（VZGamepadBridge）则支持以高达 120 Hz 采样率通过 Virtio Socket（vsock）（无需 Guest 配置 IP 网络）或 UDP 将手柄输入喂给 Guest 内的 IOHID 虚拟手柄，自带 750 ms 超时归零保护防止卡键，实测可在 Guest 原生 Steam 客户端中正常工作。

六、架构启示与已知边界总结

通读完 nfzerox/VirtualMacOniPad 的源码，我最大的感受是：这不仅是一次越狱黑魔法的胜利，更是一部活生生的 Darwin / Mach-O / Metal 系统工程百科全书。

在 AI Coding Agent 辅助下，人类对苹果私有二进制生态的理解深度已经被推向了全新的边界——无论是通过指令指纹把 iPadOS 16.4 的硬件纹理表反向移植回 16.3.1，还是用 14 条机器码寄宿在弃用日志字符串里修补闭源 VMM 的 PCI 总线越界，每一处都透露着对计算机系统底层极其扎实与克制的掌控力。

技术维度 Virtual Mac on iPad 实现方案 工程局限与注意事项
硬件与系统门槛 M1/M2 iPad（或 iPhone 14 Pro），iPadOS 14.0–16.3.1 依赖越狱释放 EL2 Hypervisor；不支持 16.4+ 及 Dopamine-roothide
二进制重建基座 uncache.py + ipsw-a2sb + stamp_ios.py 必须用 codesign 签名，不可用会剥离链式修复的 ldid -S
图形与专业软件 metalshim + AGX BC1-7 Hook + OpenGLPVGCompat OpenGL/Final Cut Pro 需 macOS 14+ Guest；部分浏览器/编辑器辅助进程已做排除
系统恢复与安装 用户态 MobileDevice + usbmuxd + VZ_USB_BRIDGE_SOCKET 极少数环境需调整 /var/root 权限或临时卸载系统 usbmuxd 防端口冲突
账户与生态边界 本地完整运行 Xcode / FCP / Logic Pro / Rosetta 2 虚拟化环境不支持登录 iCloud / Apple Account

如果你的抽屉里正好躺着一台停留在 iPadOS 14 至 16.3.1 的 M1 或 M2 iPad Pro（尤其是 1 TB / 2 TB 配备 16 GB 内存的版本），这个项目绝对值得亲自研究与折腾。
