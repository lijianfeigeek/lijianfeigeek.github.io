把多域名邮局、OAuth 2.1 与 MCP 服务器塞进单个 5 美元 Cloudflare Worker：Softwaiz/gentlemail 架构全解

2026-11-23 19 min read # RedwoodSDK # OAuth 2.1 # 开源邮件系统 # Cloudflare Workers # MCP

开源自托管邮件系统长期面临两难：要么在 VPS 上维护由 Postfix、Dovecot、Rspamd 组成的庞大容器栈，要么把域名和 API 密钥交给第三方 SaaS 按席位付费。最近我拉取并精读了 Softwaiz/gentlemail（MIT 协议）的全部源码，发现它给出了一条极具工程克制的边缘无服务器解法：不申请任何 Cloudflare API Token，也不引入任何 ORM，仅凭单个 5 美元月付的 Workers Paid 节点，就把多域名 Webmail、REST API、签名 Webhook 以及面向 AI 助手的 OAuth 2.1 + MCP 服务器装进了一体化架构。

顺着它的 9 份 D1 迁移脚本、78 个 TypeScript 源码文件与端到端 Miniflare 测试套件往下拆解，我看到了许多只有真实踩过 Cloudflare D1 与邮件协议暗坑才会写出的防御性设计：从 byteLength 字节分流规避中日韩长邮件入库溢出，到 30 秒 AES-GCM 密文宽限期化解 OAuth 令牌轮换并发冲突，再到剥离隐形 Unicode 字符的防钓鱼授权同意页。这篇文章把它的全栈拓扑、权限求交模型与安全工程细节一次拆清。

[!NOTE] 源码审计基线与范围说明
本文所有架构剖析、表结构字段、阈值常量与安全机制分析，均对照自开源仓库 Softwaiz/gentlemail（dev 分支至 commit c156814，应用基线为 0.6.1 及后续未发布 PR #32/#34）。核心邮件 Worker 位于 apps/mail/（共 78 个 .ts/.tsx 源码文件），配套 packages/sdk/ 提供零外部依赖的 TypeScript 客户端与 Webhook 验签工具，文档站 apps/docs/ 基于 Astro Starlight 构建。

一、零密钥绑定拓扑：一个 Worker 吞下 HTTP、Inbound Mail 与 Cron

在传统 Cloudflare 自动化项目里，应用常需要用户手动去控制台生成一串高危的 CLOUDFLARE_API_TOKEN 和 Account ID，再作为环境变量塞进部署面板。GentleMail 在架构原点上直接砍掉了这一步——翻开 apps/mail/wrangler.jsonc，它对 Cloudflare 所有基础设施的访问全部通过 Worker 原生绑定（Bindings） 完成：

  • DB：绑定 Cloudflare D1（SQLite），承载用户、会话、邮箱成员、邮件索引、API Key 权限矩阵与 OAuth 2.1 状态机；
  • MAIL_BUCKET：绑定 Cloudflare R2，专门承接原始 .eml 归档、附件二进制流以及超出 D1 单行字节限制的超大 HTML 正文；
  • EMAIL：绑定 Cloudflare Email Service（send_email），直接通过 env.EMAIL.send() 发信，无需维护 SMTP 账密或外部发信商密钥；
  • REGISTER_LIMIT：绑定 Cloudflare Rate Limiting（每 IP 每 60 秒最多 10 次），为无须登录即可调用的 /oauth/register 端点兜底防刷。

顺着入口文件 apps/mail/src/worker.tsx 往下看，MailWorker extends WorkerEntrypoint<Env> 在同一个运行时内同时暴露了三条完全不同的执行入口：

入口方法 触发源 核心链路与容错语义 关键源码位置
fetch(request) HTTP/HTTPS 流量 交由 RedwoodSDK（rwsdk 1.7.5）路由器处理：先过全局安全响应头与 CSRF checkOrigin 校验，再分流至 /api/v1/*、/mcp、/oauth/*、媒体沙盒端点及 React 19 RSC 页面。 src/worker.tsx、src/app/http.ts
email(message) Email Routing Catch-All 接管所有已接入域名的入站邮件。若目标邮箱或域名不存在/已禁用，直接调用 message.setReject("550 5.1.1 ...") 拒收；若解析或写库抛错，则以 451 4.3.0 临时故障码退回，触发上游投递服务器稍后重试。 src/worker.tsx、src/lib/inbound.ts
scheduled(controller) * * * * * 每分钟 Cron 每分钟拉取到期的失败 Webhook 执行指数退避重投；当 UTC 分钟数为 0（每小时整点）时，顺带清理超过 30 天的垃圾邮件以及过期的 OAuth 授权码、已用 Refresh Token 和僵尸注册客户端。 src/worker.tsx、src/lib/oauth.ts

在框架选型上，作者没有用重型全栈元框架或 ORM，而是明确在仓库 AGENTS.md 中定下两条硬规矩：纯 SQL 预处理语句（No ORM） 与 服务端动作内置守卫（Self-Guarded Server Actions）。每一个页面渲染只做只读查询，所有写操作必须经由 rwsdk 的 serverAction 触发；而在 src/app/actions/guards.ts 中，signedIn、adminOnly 与邮箱归属校验会在每个动作函数内部独立执行，即便恶意请求绕过前端路由直接向任意页面 URL 发起 RSC Action Post，也无法越权。

二、反脆弱的 SQL 工程细节：D1 100 绑定参数上限与 CJK 字节陷阱

读 GentleMail 的数据库层 src/lib/db.ts 与 src/lib/util.ts，能明显感觉到作者对 Cloudflare D1 物理边界的敬畏。D1 底层基于 SQLite，在 Workers 环境中有两项极易在线上触发崩溃的硬限制：

  1. 单条 SQL 语句最多允许 100 个绑定参数：在邮件系统里，长回复链的 References 邮件头可以轻松积累上百个 Message-ID，用户批量归档或删除会话时选中的 ID 列表也可能突破三位数。如果直接拼 IN (?, ?, ...)，D1 会在生产环境直接报错崩掉。为此，项目在 src/lib/util.ts 设计了 chunks(list, size = 90) 分片器（刻意留出 10 个余量给其他条件绑定参数），并在会话归并引擎 src/lib/threads.ts 中对 References 列表直接 .slice(0, 80) 截断。
  2. D1 行容量按 UTF-8 字节计数，而非 JS 字符串 .length：这是 PR #32 刚刚修复的一个经典国际化暗坑。D1 单行总上限为 2 MB，在 JavaScript 中，1 个中文或日文字符的 .length 是 1，但 UTF-8 编码后占用 3 字节！以前发信模块只保存收件人长 HTML 到 R2，却把发信人的 Sent 副本直接塞进 D1；结果遇到超长中文邮件时，env.EMAIL.send() 已经成功把信发出去了，随后的 INSERT INTO messages 却因超出 D1 行限制而失败，前端报错 "Sending failed" 诱导用户重复点击发送。

现在 src/lib/inbound.ts 与 src/lib/outbound.ts 统一执行了 D1_TEXT_LIMIT = 900_000 字节红线（以 TextEncoder.encode(s).length 计算）：

  • 当 byteLength(html) > 900_000 时，HTML 正文不入 D1，而是写入 R2 的 bodies/<mailboxId>/<msgId>.html，数据库仅留存 html_key 指针；
  • text_body 则调用 clipBytes() 按 UTF-8 字节切片截断，并通过 .replace(/\uFFFD$/, "") 剥离末尾可能被半路劈开的多字节 UTF-8 替换符，确保不破坏字符完整性；
  • 发信总额度校验（MAX_TOTAL = 25 * 1024 * 1024）也在 outbound.ts 中把附件大小、input.body 与 input.html 全部计入总和，提前以 422 状态码拦截会遭到上游 Email Service 拒收的边缘超限请求。

三、三维权限矩阵与 AI 助手沙盒：API Key 与 OAuth 2.1 的同一套内核

GentleMail 最值得玩味的设计，在于它把人类用户的邮箱访问权、自动化脚本的 API Key 与 AI 助手（Claude / ChatGPT / Cursor）的 MCP OAuth 连接统一收拢进了同一张 SQL 策略表 api_key_grants 中。

在 0009_organize_permission.sql 迁移落地后，每条授权记录（Grant）都由三个维度精确刻画：

  • 目标粒度（Target Type）：all（全局所有邮箱）、domain:<id>（整域通配，自动覆盖该域名下未来新建的邮箱）或 mailbox:<id>（单邮箱精确匹配）；
  • 操作能力（Scope）：read（读取与检索）、organize（标星、已读/未读、归档、Trash、Spam 移动）与 send（发信）。作者在 0.6.1 专门把 organize 从 read 中剥离出来——此前一个仅被允许“只读”邮箱的 AI 助手，竟然也能调用 update_message 把邮件归档甚至扔进垃圾箱；剥离后，只读连接不仅无法调用该接口，在 MCP tools/list 阶段连这个工具的名称都不会看到；
  • 人机权限求交（Intersection）：当一条记录属于 OAuth 连接的 AI 助手（即 api_keys.user_id IS NOT NULL）且对应用户不是管理员时，src/lib/apikeys.ts 中的 coveredSql() 与 permFor() 会在 SQL 查询与内存鉴权双重层面强制将 Grant 覆盖范围与 mailbox_members 表取交集。

[!IMPORTANT] 域名通配的 SQL 防后缀欺骗细节
在 src/lib/apikeys.ts 的 GRANT_COVERS_SQL 条件中，判断一个邮箱地址是否属于某个域名 Grant，并没有采用脆弱的 LIKE '%alpha.test'，而是严格比对 substr(lower(b.address), -length(d.name) - 1) = '@' || lower(d.name)。在测试文件 apps/mail/test/api-access.test.mjs 中，专门构造了 notalpha.test（形似后缀撞车）和 sub.alpha.test（子域名）两类边界靶子，确保域名级授权绝对不会越界穿透。

而面向 MCP 客户端的 OAuth 2.1 授权链路（src/lib/oauth.ts + src/app/pages/oauth.tsx + src/app/mcp.ts），更是把端到端协议安全做到了教科书级水准：

拆开 src/lib/oauth.ts 与 src/app/pages/oauth.tsx 的源码，可以看到 5 个极硬核的安全防线：

  1. 动态客户端注册（RFC 7591）的字符清洗：任何 AI 客户端都可以调用 POST /oauth/register 自报 client_name。为了防止攻击者用双向文本覆盖符或零宽空白字符伪造客户端名称欺骗用户，代码在第 122 行使用正则 /[\p{Cf}\u115F\u1160\u3164\uFFA0\u2800]/gu 强行剥离所有格式控制符、韩文填充符与盲文空白，并截断至 80 个 Unicode 码位（Array.from() 避免把 Emoji 劈成乱码代理对）。
  2. 防钓鱼授权同意页与动态 CSP 放行：因为谁都能把 client_name 填成 "Claude"，同意页 AuthorizePage 专门弹出醒目的琥珀色警告卡片，拆解并展示真正的回调目标地址 redirect_uri（明确区分 https: 网站、本机 http://127.0.0.1 回环端口以及 cursor:// 等原生协议，甚至特别注解 "claude.ai:cb" must not read as claude.ai）。同时，由于全站响应头锁死了 form-action 'self'，同意页在服务端动态把当前 redirectUri 的 Origin 或 Scheme 临时追加进该次响应的 Content-Security-Policy 中，使 303 重定向得以合法跳回外部客户端。
  3. S256 PKCE 与原子抢占换票：只允许 S256 挑战码。在 exchangeCode() 中，先通过 UPDATE oauth_codes SET code_challenge = '', expires_at = ? WHERE id = ? AND code_challenge = ? 原子清空挑战码把授权码占住（同时续命 60 秒防止整点清理任务误删），随后在同一批 env.DB.batch() 事务中基于 EXISTS (SELECT 1 FROM oauth_codes WHERE id = ?) 条件写入 api_keys、api_key_grants 与 oauth_tokens，杜绝高并发双请求竞态换票。
  4. 30 秒 AES-GCM 密文重试宽限 + 令牌族全量熔断：OAuth 2.1 要求 Refresh Token 每次使用必须轮换，但现实中浏览器双标签页或网络丢包极易导致客户端重发同一个旧 Refresh Token。GentleMail 在 0008_oauth_retry.sql 给 oauth_tokens 增加了一个 answer 列——首次刷新成功时，Worker 用从旧 Refresh Token 派生出的密钥（SHA-256("gentlemail retry:" + token)）通过 AES-GCM 加密新生成的 Token Pair 存入 answer。只要客户端在 REUSE_GRACE = 30s 内带着同一个旧令牌重试，且新链条尚未被继续消费，服务器就能解密返还完全一致的那对新令牌；一旦超过 30 秒或新令牌已被推进后再出现旧令牌重放，判定为令牌泄露，立即执行 DELETE FROM oauth_tokens WHERE family = ? 将整条设备登录链彻底踢下线！
  5. 无状态 Streamable HTTP MCP 网关与提示词注入防御：POST /mcp 不维持 SSE 长连接或服务端会话（支持最多 MAX_BATCH = 10 的批量 JSON-RPC），仅支持 2025-11-25 等主流 MCP 协议版本。toolsFor(auth) 按权限动态裁剪暴露工具集（共 7 个工具：list_mailboxes、search_messages、get_message、get_thread、send_email、reply、update_message）；其中 get_thread 在超过 25 封邮件时保留第 1 封原始问题与最新 24 封，并显式在 JSON 数组中插入 left_out 占位提醒，防止大模型把断档会话误读为连续上下文；所有读取类工具返回体与 initialize 指令均强制注入 UNTRUSTED 警示，明确要求助手将邮件正文视为不可信数据而非指令，而发送类工具全部标记 openWorldHint: true 引导客户端二次确认。

四、收发信双管线、HTML 配平清洗与三层邮件阅读沙盒

电子邮件是典型的“上古异构协议 + 现代前端高危攻击面”交汇点。从入站解析、发信富文本生成到浏览器内展示，GentleMail 构建了一套闭环的数据清洗与隔离管线：

1. 四级渐进式反垃圾策略（src/lib/spam.ts）

Cloudflare Email Routing 在边缘前置已经直接拒掉了 SPF+DKIM 双挂、DMARC 策略拒收以及在实时黑名单中的发件人。真正进入 Worker handleInbound() 的邮件，会依次经过 spamVerdict() 的四重判断：

  1. 用户个人规则绝对优先：查询 sender_rules 表（精确地址优先于 @domain 域级规则），只要用户在前端点过“Not spam”，即标记为 allow 跳过后续一切规则；点过“Spam”则自动写入 block 规则；
  2. 上游垃圾标记：检测 X-Spam-Flag: YES；
  3. 软失败 DMARC 兜底：当对方域名策略为 p=none 或 p=quarantine 导致未在网关层被硬拒，但 Authentication-Results 仍包含 dmarc=fail 时，自动移入 Spam 并给出中文友好归因提示；
  4. 可配置的分数阈值：当管理员设置环境变量 SPAM_SCORE_THRESHOLD（如 5 或 4）且邮件携带的 X-Cf-Spamh-Score 达标时归入 Spam。被判定为垃圾的邮件不会触发 Webhook，并在 30 天后由每小时 Cron 批量连带 R2 附件一并物理清除。

2. 发信侧：Lexical 编辑器 + HTMLRewriter 标签栈配平（src/lib/compose-html.ts）

PR #32 刚刚为 Webmail 接入了基于 Meta Lexical（0.53.0）的富文本编辑器，但作者没有盲信浏览器 POST 上来的任何 HTML。cleanComposerHtml() 先用 Cloudflare 原生流式解析器 HTMLRewriter 丢弃 script、style、iframe、svg、math、xmp、noembed、textarea 等 30 个危险或原始文本包裹标签，并仅保留 14 个安全格式化标签（p、br、strong、em、u、s、sub、sup、a、ul、ol、li、blockquote、code），剥离所有 class/style（仅在白名单内回填邮件客户端兼容的内联样式）。

更有意思的是紧随其后的三个自研后处理函数：

  • balance(html)：用标签栈闭合所有未闭合标签并丢弃孤立闭合标签，防止发信正文里一个漏掉闭合的 <a> 标签把后面的邮箱签名和引用回复全部吞进超链接；
  • keepSpaces(html)：把连续空格与 Tab 转换成邮件客户端不会折叠吞掉的 &nbsp;；
  • composerText(clean)：手写状态机将清洗后的 HTML 同步生成干净可读的纯文本版本（段落换行、- / 1. 列表缩进、> 引用前缀以及 文本 (链接) 展开）。

3. 阅信侧：三层防线死锁恶意 HTML（src/app/pages/files.ts）

打开任意一封接收到的邮件正文时，前端并没有把 HTML 直接拼进主页面 DOM，而是通过独立的 /body/:id 路由渲染在沙盒化的 <iframe> 中，叠满三层互为备份的纵深防御：

  1. 边缘解析剥离：在输出前再过一遍 HTMLRewriter，剥除所有 on* 事件属性、srcdoc、formaction 与 javascript:/vbscript: 协议链接，并将内联 cid: 图片引用改写指向受鉴权的 /attachments/:id?inline=1；
  2. 严苛动态 CSP：下发 script-src 'none'、form-action 'none'、base-uri 'none'，且默认仅放行 'self' 与 data: 图片（防止跟踪像素泄露阅读时间与 IP），只有用户主动点击“Open with images”附加 ?images=1 参数时才临时放开 https: http:；
  3. 双重 Sandbox 约束：不仅外层 <iframe sandbox> 不授予 allow-scripts，/body/:id 的 HTTP 响应头本身也携带 Content-Security-Policy: sandbox allow-same-origin allow-popups allow-popups-to-escape-sandbox——哪怕用户右键在新标签页直接打开 /body/:id 原始地址，浏览器依然无法执行其中的任何脚本。至于 HTML、SVG 等高危附件类型，/attachments/:id 统一强制 Content-Type: application/octet-stream 与 Content-Disposition: attachment 触发下载而不做内联预览。

五、配套生态、部署门槛与实战客观评估

除了核心 Worker，Softwaiz/gentlemail 还自带了零外部运行时依赖的 npm SDK（packages/sdk，包名 gentlemail）。翻看 packages/sdk/src/webhooks.ts，它的 verifyWebhook() 直接基于标准 WebCrypto API 实现 X-GentleMail-Signature: v1=<HMAC-SHA256> 恒定时间比对，并内置了默认 300 秒时间戳容差窗口（tolerance）防重放，同时兼容 Fetch Request（Workers/Deno/Bun/Next.js）与 Node 原生 http/express.raw() 的 { body, headers } 传参。

不过在实际动手部署前，有几项硬性前提与工程边界需要提前知晓：

[!WARNING] 部署门槛与边界避坑提示

  1. 必须具备 Cloudflare Workers Paid（5 美元/月）与域内 DNS：免费版 Worker 无法满足部分配额且 outbound send_email 绑定依赖 Workers Paid 套餐（内含每月 3,000 封免费出站发信，超出部分按每千封 0.35 美元计费）。此外，Cloudflare 每个域名仅支持一个 Email Routing Catch-All 规则，若你的主域名已绑定其他邮件转发 Worker，建议划出专门子域（如 mail.example.com）接入。
  2. 静态加密与账户安全基线：用户登录密码采用 100,000 次迭代的 PBKDF2-SHA256（Workers WebCrypto 最大支持迭代数），Session、API Key、OAuth Code/Token 与 MFA 恢复码在 D1 中全部仅存储 SHA-256 哈希，即便数据库泄露也无法反推出明文密钥。同时支持标准 RFC 6238 TOTP 两步验证与防并发重放的 mfa_last_step 递增校验，管理员重设用户密码或重置两步验证时，会通过 endConnections(userId) 同步吊销该名下所有已连接的 AI 助手。
  3. D1 单点写入吞吐边界：由于整个系统刻意避开队列（Queues）与 Durable Objects 以换取“一键点击即部署”的极简运维体验，面对日均数万封级高频并发入站场景时，单 D1 实例的写入锁竞争会成为上限；但对于个人独立站、中小团队支持邮箱、SaaS 通知发信与 AI 助理收发中枢而言，这套零 VPS 维护成本的方案几乎达到了效率与安全性的最优平衡。

总体来看，Softwaiz/gentlemail 是一份极佳的 Cloudflare 全栈工程范本：没有堆砌华而不实的中间件，却把原生 Bindings、SQLite 字节边界、OAuth 2.1 状态机与浏览器沙盒打磨得滴水不漏。如果你正好需要一套完全掌控在自己账户下、能用自然语言或 API 驱动的多域名邮局，非常值得直接部署或参考它的源码设计。
