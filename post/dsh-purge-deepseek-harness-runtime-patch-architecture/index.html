47,000 行 JS 造出宿主解耦与内置红队演练台：重读 dsh-purge v1.1.71 核心架构与安全边界

2026-11-05 21 min read # AI安全 # 网络安全 # 开源项目 # 架构设计 # DeepSeek

在大模型智能体评测里，最容易把人带偏的并不是模型拒绝回答，而是宿主运行时（Harness）在到达云端推理前偷偷拦截了请求。最初我在看社区早期版本的 dsh-purge 时，还以为它只是一个改写系统提示词的轻量补丁脚本；直到最近我拉取了 mmparko/dsh-purge 完整存档镜像（对应上游 YuJunZhiXue/dsh-purge 停更归档前的 v1.1.71，快照 6c1d638，约 4,995 Star、612 Fork）并逐个审计了全仓 47,154 行核心代码，才意识到它早已演变成一套覆盖 82 项热补丁、Electron Asar 侧边解包、可逆 Hooks 旁路 以及 内置红队演练台（56 个专用工具 + 25 张 SQLite 表 + 23 份 Runbook 技能） 的完整本地运行时工程底座。

这篇复盘我基于 mmparko/dsh-purge 主干源码与 MIRROR-NOTICE.md 归档记录，站在第一人称审计视角，彻底重写并升级我此前对 dsh-purge 的架构分析：从“宿主-模型”解耦与 82 项补丁矩阵讲起，深入五层提示词实时组装防线、Windows/macOS 跨端原子落盘细节、近乎严苛的 net-scope.js 私网合规边界，以及 v1.1.71 最核心的内置红队演练台多智能体编排引擎。

一、 架构跃迁：为什么需要把「宿主」和「模型」彻底拆开？

在官方 DeepSeek Harness（简称 DSH）的默认运行时中，用户消息并不是直达大模型的。@deepseek-ai/* 体系里的 persona-prefix、工作区基线（Workspace Baseline）、模板插值引擎（仅白名单放行 cwd、model、provider）、Hooks 审批拦截（UserPromptSubmit / Stop / pre-step）以及串行 Bash 沙箱会层层包裹上下文。

这种耦合架构在做受控科研评测或红队能力基线测试时会带来三个直接痛点：

  1. 假阳性拒答混淆视听：一旦宿主层面的 Hooks 或安全文案拦截了工具调用，终端上呈现的往往和模型自身拒答无异，评测者无法分辨究竟是模型能力边界还是宿主门禁触发了拒绝；
  2. 模板插值器脆弱崩溃：如果在提示词或参考代码里带入未注册的双花括号 {{，DSH 0.2.x 的插值引擎会直接抛出 malformed 异常并整段丢弃系统提示词；
  3. 跨端孤岛与权限失衡：官方 dsh web 与 Electron 桌面 EXE 各自拥有独立的 $DSH_HOME、Profile 与包树，桌面端核心逻辑还被封死在 resources/app.asar 中，手动改源码极易在下次 npm 或客户端更新时被静默覆盖。

dsh-purge v1.1.71 给出的解法非常克制且彻底：不 Fork 上游代码仓库，而是借助 DSH 原生 Cordis 微内核总线、82 项分域可逆热补丁与运行时事件钩子，将宿主策略和模型推理彻底拆分成正交平面。

通过上面的架构变更对比（Architecture Delta）可以看到，打入 dsh-purge 之后，原本混杂在系统上下文头部的宿主身份、非白名单双花括号报错、以及未受控的 Hooks 拒绝逻辑均被精准剥离或重写，取而代之的是受控的提示词优先级仲裁、中立化的能力选用协议以及本地静态合规网关。

二、 五层运行时堆栈与 82 项热补丁工程细节

把 lib/ 下共计 4.7 万行代码摊开来看，dsh-purge 的清洗（Purge）能力并非靠几个粗糙的字符串替换，而是构筑了一套从操作系统文件系统一路向上延伸至 LLM 上下文组装的五层纵深架构。

1. L1 宿主探测、Asar 侧边解包与 POSIX 权限保留原子写入

DSH 的安装形态五花八门，包括全局 CLI、独立 Profile（web 与 desktop 严格隔离）、便携包以及封装在 app.asar 中的官方桌面端。我在 lib/core.js、lib/extract-asar.js、lib/desktop.js 和 lib/settle-policy.js 中读到了非常老道的跨平台工程防御：

  • 多路径回溯探测链：按 $DSH_HOME / $DSH_BASE → dsh 启动器相邻 .dsh → npm prefix -g / npm root -g → 嵌套 @deepseek-ai/dsh/node_modules/@deepseek-ai → 系统 ~/.dsh 顺序收敛定位，绝不写死盘符；
  • Electron Asar 解包与 4 秒静默防抢锁：针对官方桌面端，extractAsarToSide 会将 app.asar 安全解包到侧边目录后再实施替换。而 lib/settle-policy.js 更专门针对桌面端设置了一个 DESKTOP_SETTLE_DELAY_MS = 4000 的退避窗口——因为在桌面端启动早期，官方宿主内部的 Fiber._reload 仍在挂载 desktop-office，如果此时贸然解包或 taskkill 重启，会直接引发 Cordis 抛出 INACTIVE_EFFECT 致命异常；
  • Windows Script Host 中文路径转义（lib/official-update.js）：Windows 下的 WSH 若遇到无 BOM 的 .vbs/.js 重启脚本会按系统 ANSI 代码页读取，遇到含中文的用户名路径必挂。wshLiteral() 专门将所有非 ASCII 字符（> 0x7f）编码为 \uXXXX，确保整份重启脚本纯 ASCII 落盘；
  • POSIX 权限保留式原子写入（atomicWriteSync）：写入前先捕获目标文件的原始 mode（例如 dsh CLI 可执行文件必备的 0755），经临时文件 fs.writeSync + fs.fsyncSync 强制刷盘并重命名替换后，在 rename 前后两度调用 restoreMode 回刷权限，根除了新文件因默认 umask 降级为 0644 导致 Permission denied 的隐患。

其中最令我拍案叫绝的是 lib/hooks-deny.js 对 HOOK_DENY_PATCH_IDS = [30, 31, 64, 65] 的可逆设计：

  • 这 4 条补丁分别作用于 Claude/Codex Hooks 的 deny → allow 旁路、Stop Hook steer 禁用以及 pre-step 拒绝绕过。插件没有简单粗暴地删除原代码，而是替换成一个特征死字符串哨兵 __dsh_purge_deny_disabled__；
  • 一旦用户在设置里关闭 hooksDenyBypass，restoreHookDenyOfficial() 会用一张包含 R1a、R1a2、R1b、R2a、R2b、R3、R5a、R5b 的精确反向替换表（REVERSES），将文件无损写回官方原生形态；
  • 该模块甚至专门注释了一条 Windows 竞态修复（#M11）：由于 libuv 在 Win32 底层使用 MoveFileExW(MOVEFILE_REPLACE_EXISTING)，直接 fs.renameSync 即可原子覆盖，于是作者果断删掉了旧版“先 unlink 再 rename”的逻辑，彻底消灭了目标文件短暂消失的竞态窗口。

3. L3–L5 提示词组装四重兜底、前缀绕过与原位回退

在多轮对话或首次新建会话时，宿主自身的 system-prompt/assemble 瀑布流极易因为插件未热挂载、缓存未就绪或 Preset 切换而读到空串，导致模型突然脱口而出“我是 Claude / 我是 DeepSeek 助手”。为此 lib/index.js 在 installHungPromptGlobal() 中构建了一套四重兜底链：

  1. refreshHungOperator：带 200ms mtime 节流缓存的完整同步解析；
  2. hungOperatorPrompt：进程生命周期内的内存钉子；
  3. readPromptInjectFileSync：绕过缓存直接读取磁盘 prompt-inject.md；
  4. defaultOverrideText：解包插件内置加密默认插槽，确保任何极端边界下都不返回空串。

同时，为了抢占系统提示词第一顺位并避免被宿主解析器误杀，lib/identity.js 与 lib/capability-protocol.js 还藏着三个精妙的细节：

  • 绕开前缀重排陷阱（dshpg-capabilities）：DSH 宿主内部的 renderPrompt 存在一步 filter(s => s.name.startsWith("dsh-purge"))，会把所有以 dsh-purge 开头的段按插入序强制挪到最前。旧版把能力选用协议命名为 dsh-purge:capabilities，结果直接跑到了主注入段前头造成渲染反转！新版特意改名为 dshpg-capabilities（dshpg-* 前缀），才完美稳住了 GLOBAL_PROMPT_ORDER = -100000 的主注入顺位；
  • 非白名单 {{ 智能拆分：escapeDshInterpolation() 仅放行 {{cwd}}、{{model}}、{{provider}}，其余任何双花括号全部原地拆分为 { {，防止代码示例或 JSON 触发模板引擎 malformed 崩溃；
  • ChatML 行级规整与三态基线策略：normalizeChatmlLayout() 强制 <|im_start|>system: 独占一行并自动补齐缺失的 </project_instructions>，再配合 strict（一律剥离 DSH workspace baseline）、fallback（存在用户 prompt-inject.md 或勾选本地 AGENTS.md/CLAUDE.md 时剥离）和 always（保留）三种策略，彻底理顺了多源规则的覆盖关系。

在会话交互侧，lib/rewind.js 则绕开了新建分支导致工作区污染的老路，配合官方 session.fork({ atSeq }) 与补丁 #56/#58/#75/#77，实现了原位回退（/rewind 与“回退一次 / 回退上一轮”）：撤回最近一轮对话并归档旧会话，把原始输入自动填回输入框，让测试人员可以在零污染状态下反复微调提示词。

三、 双重合规红线：net-scope.js 静态熔断与演练台独立授权

很多社区“破甲/红队”工具最容易踩进法律与滥用泥潭，而 dsh-purge 源码里让我印象最深的，反而是它用硬编码逻辑给自己套上的两道物理级安全锁。

1. net-scope.js：把公网/敏感目标死死拦在模型与沙箱门外

在 lib/net-scope.js 中，插件直接在 agent/pre-step（step === 1）最高优先级挂载了 installRegionGate(ctx)：

  • 只看本轮新用户句 + 100KB ReDoS 上限：currentTaskText() 会跳过 assistant 回复、工具回包（looksLikeToolResult）以及 <system-reminder> 标签，防止上一轮扫描结果里的域名误伤下一轮对话；面对用户粘贴超大日志的场景，ATTACK_SCAN_CAP = 100 * 1024 直接截断正则扫描窗口，避免零宽环视正则（如 渗透(?!测试)、(?<!防御)攻击(?!面)）触发灾难性回溯卡死 Node 事件循环；
  • 良性网络排障豁免（#73）：单纯询问代理配置、Clash/v2ray、DNS 解析或本机 IP（isBenignNetworkTopic）且不含攻击意图时直接放行；
  • 私网回环放行 vs 大陆/港澳及金融机构硬阻断：一旦命中攻击意图，hostsInTask() 会抽取文本中的 URL、IPv4、IPv6（特意用 lookbehind/lookahead 排除了 HH:MM:SS 时间格式误报）和域名（剔除 .js、.md、.mo 等代码文件后缀）。非 RFC1918 私网 / 本地回环（localhost、127/8、10/8、172.16/12、192.168/16、::1、fe80::/10、fc00::/7）的地址，只要命中 SUFFIXES（覆盖 .cn、各省市 .bj.cn、.hk、.mo 及 .中国、.香港、.澳门、Punycode IDN 后缀）或 BANK_HOSTS（覆盖全球主要商业银行、央行、SWIFT、国际清算银行与主流加密交易所主域及子域），就会被立即判死；
  • 「自己的服务器」精确白名单：用户如果要在自己名下的中国大陆/港澳服务器上做授权演练，在对话里口头声明“这是我的服务器”或贴私钥均无效。必须在侧栏保存至 $DSH_HOME/net-scope-allow.txt——entryHost() 在落盘时会自动丢弃一切私钥、密码、CIDR 网段和通配符 *，只留存单个精确 IP 或完整主机名（可选 user@host）；
  • 紧凑流式熔断写入（parkDenial）：被拦下的请求既不进入模型也不触碰 Bash 沙箱，而是直接由插件向当前会话追加 user/message → step/start → assistant/message → step/end，输出固定的“不行，这是严令禁止的”。这里还有个修过的硬核 Bug（#84）：denialStream() 必须逐条构造 { type: "chunk", time, chunk } 紧凑记录，而不能直接写批记录，否则宿主持久化读取时访问 undefined.length 会当场崩溃。

2. drill-grant.js：跨端隔离的三重法律勾选门禁

进入“演练台”之前，前端面板必须展示完整合规免责声明、等待倒计时结束、滚动至文末并勾选三项确认。通过后，writeDrillGrant() 会将授权凭证写入当前宿主独立的 $DSH_HOME/dsh-purge/drill-grant.json——Web 端与桌面端互不共享，插件升级覆盖 node_modules 时无需重复弹窗，但执行“卸载”时会连同该授权文件一并清理。

四、 v1.1.71 重头戏：内置「演练台」多智能体编排与 SQLite 事实库

如果说早期的 dsh-purge 还聚焦在“清洗”，那么整合进来的 lib/redteam/（16 个子模块）、presets/redteam/ 与 skills/redteam/（23 份实战 Runbook） 则让它变成了一座完整的本地攻防演练指挥台（其演练台架构溯源自双用途开源项目 Jueze-2019/dsh-redteam-mode，同样仅限授权靶标与离线环境，仓库本身不含任何漏洞利用载荷）。

拆解 presets/redteam/agent.cordis.yml 与 lib/redteam/ 源码，我梳理出了这套编排引擎最值得借鉴的四项设计：

1. 主控指挥官（Lead）与五大叶子角色（Leaf）严格分权

  • 指挥官只调度不动手：主智能体被硬性约束只能执行四件事——任务规划、原生 subagent 派活、核查库内子代理回报、增量汇报。系统明确禁止主控自己调用扫描器，也严禁使用 Agent Teams 的 spawn_teammate（因为角色稿、并发槽位与叶子限制全部挂在原生 subagent 路径上）；
  • 首行角色标签自动注入（role-section.js）：指挥官派发子任务时，Prompt 第一行必须声明 redteamRole: <code>（限定为 recon、assess、vuln-scan、exploit、internal 之一）。role-section.js 通过监听 agent/inbox/claimed 事件捕获该标签（并用容量 400、每次淘汰最早 100 条的 FIFO Map 防止长开进程内存泄漏），在组装子会话提示词时动态加载对应角色稿；
  • 硬摘除再委派工具防递归失控：对子代理只靠提示词劝“不要往下派活”并不可靠。agent.cordis.yml 直接把子会话 maxDepth 设为 1，并在 toolFilter.deny 中精准摘掉 subagent_fork、workflow、ralph（同时注释提醒绝对不能把 subagent 本身写进 deny，因为它是该行自己注册的 scoped 工具，写进全局过滤会导致 tools.restrict() 直接报错 unknown global tool）；
  • 并发槽位硬闸门（redteam_agent_slot）：同一靶标最多并发 3 个 执行智能体，派活前需先查 status 并 acquire 占位，满额即停而非硬塞。

2. anchor-gate.mjs：两阶段思考锚点门与上下文压缩复位

为了让模型在演练首轮就进入高效工具调用状态而不至于长篇空谈或被工作区长文档拖慢，presets/redteam/anchor-gate.mjs 在 agent/pre-step 和 agent/request 上架设了一套状态机门禁：

  • 它扫描历史事件与首段 reasoning 块，利用 classifyReasoning() 统计思考文本中的 we 与 let me 词频来识别是否处于精简锚定态（Bootstrap 阶段默认限制 maxBootstrapSteps: 2、bootstrapMaxTokens: 8192）；
  • 一旦模型成功调用工具并越过引导门槛，状态切换为 promoted = true：不仅撤除 maxTokens 上限，还会把原本冗长的 agent-instructions 全文重写为简短的 <system-reminder> 文件指针（instructionHint），大幅节省后续轮次的 Token 消耗；
  • 最关键的是，当宿主触发上下文压缩（compaction/end）时，状态机立即调用 resetToControlled(state) 复位，重新拉起护栏，防止模型在压缩后丢失行为锚点。

3. 基于 node:sqlite 的 25 张事实表与 FTS5 编译期探测降级

整个演练台没有任何云端同步或遥测，所有战果全部沉淀在 $DSH_HOME/redteam 下的本地 SQLite（WAL 模式 + busy_timeout = 5000）：

  • 25 张结构化数据表：涵盖 scan_run、segment、asset、asset_name、port、service、fingerprint、observation、edge（资产拓扑关系）、tag、vuln、score_point、stage、score_hit、credential、access_session、webshell、tunnel、http_evidence、attack_file、attack_step、shot、poc，外加 asset_fts 与 poc_fts 两张全文检索虚拟表；
  • 极其严谨的 FTS5 降级策略（schema.js）：注释里直白指出，Node 22.14 自带的 node:sqlite 没有编译 FTS5（建表直接报 no such module: fts5），而 Node 22.23 才有。因此启动时会先在 :memory: 库试探建一张 __fts5_probe 虚表（并留有 REDTEAM_NO_FTS5=1 测试开关），一旦探测缺席就自动降级为 LIKE 查询，保证不因 Node 小版本差异导致整库建表崩盘；
  • 56 个专用模型工具 + HTTP 侧栏桥接：lib/redteam/tools.js 暴露了从资产建图、PoC 检索、HTTP 原始证据存证、得分点核算到战报导出的 56 个 redteam_* 工具，并通过 POST /redteam/api 实时驱动右侧栏渲染，真正做到“没落库的发现等于没发生”。

4. 技能根优先级隔离与离线降级预检

为了避免随包分发的 23 份技能模板（里面包含 <你的VPS_IP> 这类占位符）覆盖用户在自己 $DSH_HOME/skills 里填好的真实配置，agent.cordis.yml 特意关闭了 includeDefaultRoots，只扫描两个自定义根，并把用户目录排在前面：

customSkillDirs:
  - !!js dshHomePath('skills')
  - !!js dshHomePath('redteam/skills')

同时，lib/redteam/index.js 在启动阶段如果检测到环境变量 DSH_HOME 与宿主 dshHomePath() 发生路径分叉，还会顺手把随包技能同步到所有真实存在的候选 home，彻底治好了“技能已装却列表不可见”的跨端顽疾。

五、 工程实战避坑与开源存档启示

结合代码库里的真实注释、发布记录与本地校验脚本，我整理了部署或研究 dsh-purge 时最容易踩中的几个坑：

  1. Web 端与官方桌面端完全隔离：两者的 node_modules、cordis.patch.yml、$DSH_HOME 与 drill-grant.json 彼此独立。必须分别执行 dsh plugin --profile web add dsh-purge 与 dsh plugin --profile desktop add dsh-purge，并在各自窗口的“清洗”页点击“应用”；
  2. 极简（Minimal）/ PTC 模式与标准模式行为不一致：如果同一任务在标准模式正常、在极简模式被拦，多半是旧版本 preset 中的 run_code 或 Plan 拦截文案未洗净，需要升级至 1.1.61+ 并完全退出宿主重启应用，让新进程重新加载补丁；
  3. Node 版本与 Windows 闪窗边界：插件基础要求 Node >= 18，但在 Windows 下要享受 lib/hide-console.js 带来的无 CMD 闪窗体验需要 Node >= 22；而演练台的 node:sqlite 原生模块同样依赖现代 Node 构建；
  4. 镜像校验完整性：由于原作者 YuJunZhiXue 已宣布暂停维护，我在使用 mmparko/dsh-purge 镜像时对照 MIRROR-NOTICE.md 核验了快照基线——upstream-snapshot-6c1d638 与镜像 master 除了新增的 MIRROR-NOTICE.md 外文件树逐字节一致（master 源码包 SHA256：4acda024330d43b7beaf220f308e10eb27cf253fd4135942e3e5930b1dace106），保留了全部 73 个原版发布 Tag 与 26 个 PR 归档 Tag，研究时可优先基于该快照做静态对照。

六、 总结与思考

重读完 dsh-purge v1.1.71 的这四万七千行代码，我最大的感触是：一个最初看似“提示词注入小插件”的项目，之所以能演进出接近工业级基础设施的工程质感，是因为作者把每一个真实环境里的脏活累活都啃到了底——从 Win32 MoveFileExW 的竞态消除、WSH 的 \uXXXX ANSI 编码兜底、Node node:sqlite FTS5 编译期探测，到绕开宿主 startsWith("dsh-purge") 前缀重排的 dshpg-* 命名技巧，处处都是真刀真枪踩出来的系统工程经验。

更重要的是，它在解锁宿主限制的同时，把 net-scope.js 私网防线、drill-grant.js 三重授权与本地化零遥测 SQLite 事实库做成了不可绕过的底层契约。对正在构建大模型智能体运行时、插件微内核或本地受控安全评测平台的开发者而言，这份代码库本身就是一份不可多得的实战参考样本。
