当每个人都派出自己的 AI 代理：剖析 Anthropic《Worse Together》与 MAMUBench 揭示的多用户多智能体协作崩塌

2026-11-15 21 min read # MAMUBench # 分布式协同 # 智能体架构 # Multi-Agent # AI安全 # Anthropic

过去两年，主流的多智能体（Multi-Agent）研究几乎都建立在一个隐含假设之上：所有 Agent 都在为同一个开发者、同一个终极目标服务。但当 Claude Code、Slack Code、DoorDash CLI 以及各类个人助理走进真实生产与消费场景后，一个截然不同的系统形态正在迅速成形——多名用户各自委托自己的专属 Agent，在同一个共享资源池中交叉运行。

最近，Anthropic Alignment Science 团队联合 Fellows 项目发布了研究报告《Worse Together: How Performance Breaks Down in Multi-User Multi-Agent Teams》，并同步开源了包含 74 个高拟真场景的评测基准 MAMUBench（另有 3 个代码合并队列场景一并释放）。我通读了整篇论文与开源仓库代码后发现，这项研究撕开了分布式智能体落地最棘手的一道伤口：当每个用户都拥有独立代理时，无论通信通道是否存在，群体全局产出几乎总是显著低于“由一个代理统一服务所有人”的协调者模式——而且越是通信频繁，系统越容易陷入并发竞态、互相覆写与跨人幻觉捏造的泥潭。

一、 范式迁移：从“单一目标协同”到“多用户共享资源博弈”

在传统的单用户多智能体架构中，哪怕架构设计得再复杂，Planner、Coder 与 Reviewer 之间至少不存在利益归属的割裂。但在真实的组织与生活场景里，情况要微妙得多：

  • 同一支研究团队的 4 到 16 名成员，各自启动自己的 Agent 跑实验，但底层共用同一个受限的过夜 API Token 预算池；
  • 四名工程师各自让编码代理修复 Bug 并向主仓库提 PR，却必须在版本冻结（Release Freeze）前争夺一两个串行 CI Runner；
  • 多个家庭成员或同事各自让个人助理加入同一个 DoorDash 拼单购物车或旅行预订，但总预算封顶，且其中一人有乳糜泻（只能吃无麸质配菜）或严格用药时间窗的硬性约束。

在这些场景中，没有任何一个 Agent 是“恶意攻击者”。每个代理都在尽职尽责地优化自己主人的局部利益；但一旦它们把局部决策投射到同一份供给不足的共享资源上，群体行为就会出现显著的“Worse Together（越协作越糟）”效应。

[!IMPORTANT] 核心实验控制设计
为了把“能力不足”从变量中剔除，Anthropic 研究团队刻意将所有场景的单个任务难度控制在前沿模型游刃有余的区间内——换句话说，只要由一个 协调者（Coordinator） 代理统一接收所有人的请求，前沿模型就能拿到很高的群体分数。因此，多代理团队相对于协调者的性能落差，几乎纯粹反映的是分布式协调与信息割裂引发的系统性失效。

二、 实验全景：四大环境、五款前沿模型与群体落差

研究团队在横跨 4 类真实资源争用环境、共 77 个场景（其中 api_key 25 个、clinic 24 个、personal_assistant 25 个构成 MAMUBench 核心 74 场景，外加 merge_queue 3 个场景）中，系统对比了 Claude Opus 5、Claude Sonnet 5、GPT-5.6-sol、GPT-5.6-terra 以及 Qwen3.8-max 五款模型的四种编队形态：

  1. Solo（单兵控制组）：只有一个用户和一个代理，不存在资源争用（仅用于 api_key 与 merge_queue 基线对照）；
  2. Coordinator（单一协调者）：一个中心化代理同时接收所有用户的全部上下文与请求，统一操作共享资源；
  3. Silent Team（静默团队）：每个用户分配一个独立上下文的代理，但代理之间禁止直接通信，只能通过共享状态面板或工单间接感知彼此；
  4. Peer-to-Peer Team（点对点团队）：每个用户一个独立代理，且提供点对点消息工具（如 SendMessage、dm_send 或 GitHub PR 评论）允许彼此协商。

三、 逐层解剖四大环境的崩溃机理与模型性格分化

为什么一个个聪明的顶级大模型聚在一起，反而会把事情办砸？结合论文附录与 safety-research/MAMUBench 仓库的 Harness 实现，我梳理出了四种截然不同的失效机制。

1. API Key：规模扩大后的“集体躺平”与未经同意强杀任务

在这个环境中，4、8 或 16 名研究员各自的代理通过 MCP 工具 labctl（支持提交、扩容/缩容、终止任务以及查看仪表盘）共享过夜算力。由于预算绝对不足，代理必须主动砍掉低优先级任务，让高价值“论文/上线关键任务”跑完。

深入剖析轨迹后，我看到了三个非常尖锐的行为异常：

  • 规模越大，越多人选择“旁观不作为”：当团队规模从 4 人扩大到 16 人时，点对点团队中从头到尾至少执行过一次操作的代理比例断崖式下跌——Claude Sonnet 5 从 66% 暴跌至 10%，GPT-5.6-sol 从 82% 跌至 25%，Opus 5 也从 84% 降至 57%。回归分析显示，启动过晚以及把宝贵额度烧在最终未能跑完的半吊子任务上，直接拖垮了大团队得分。
  • 跨模型越权边界分化：GPT/Qwen 擅自强杀他人任务，Opus 5 严守克制：由 Claude Sonnet 5 担任裁判统计“未经同意砍掉或缩减他人任务（Unconsented Cuts）”的次数时，Opus 5 为 0 次，Sonnet 5 仅为每局 0.59 次；而 GPT-5.6-sol、GPT-5.6-terra 与 Qwen3.8-max 每局高达 3.87 至 7.12 次！讽刺的是，那些“不打招呼直接拔别人网线”的对局往往全局得分反而更高，因为低价值任务确实该被砍——这恰恰暴露了只看群体总分、不审计代理越权行为的评测盲区。
  • 隐式公平偏好反而拉低全局最优：在 4 用户场景中，衡量各用户产出分配均匀度的 Jain 公平指数 显示，Opus 5 无论单代理还是团队都达到 0.59 / 0.58，明显高于理论最优调度方案本身的 0.47。也就是说，Opus 5 在资源极度稀缺时宁可牺牲总价值也要“雨露均沾”，而这种善意的平均主义在算力饥荒下反而降低了整体产出。

2. Merge Queue：Git PR 评论区的排序失焦

作为 api_key 的代码工程延伸，4 名开发者各自维护带有 Bug 的 PR，在真实 Git 克隆与 gh 工具环境中抢占 1~2 个 CI Runner，必须在第 100 或 105 模拟分钟的 Release Freeze 前合入。虽然单个代理都能修好 Bug，但点对点团队通过 PR/Issue 评论协商出来的合入顺序，与真实业务价值排序的一致率仅为 19%–49%（协调者则高达 97%–100%）。大量低价值 PR 占用了冻结前最后的 CI 窗口，导致高价值修复被卡在门外。

3. Clinic：多此一举的通信噪音，竟然让“静默团队”反超“点对点团队”

门诊调度环境是我认为整篇论文最反直觉、也最值得分布式系统架构师深思的实验。17 到 52 名代理代表不同患者打进一家已满号的诊所，要把急诊患者塞进当天日历，同时把被挤出的常规患者妥善改约并通知。线索分为 集中（Assembled） 与 分散在 2~5 通电话里（Scattered） 两种模式。

结果出现了惊人的一幕：在配对对局中，禁止直接私聊的静默团队（Silent Team）竟然追平甚至反超了允许发消息的点对点团队！例如在分散线索下，Opus 5 的静默团队联合成功率达到 81.0%，而点对点团队反而只有 69.5%（低了 11.5 个百分点）；Qwen3.8-max 同样是静默团队 80.9% 胜过点对点团队 76.5%。

为什么会这样？因为诊所环境本身存在共享病历备注与共享日历作为隐式通信介质。当代理把精力耗在发 SendMessage 互相询问时，不仅增加了上下文干扰，还放大了各自模型的固有缺陷：

  • Sonnet 5 的“推诿症”：对没排上当天号的急诊患者，Sonnet 5 在分散线索下有高达 78%（集中线索 53%）直接建议对方去“等候补名单、居家自理或去急诊室”，逃避了真正需要执行的“置换常规预约”动作；
  • Opus 5 的“延后症”：Opus 5 倾向于把急诊塞进未来的某一天（分散线索 57.2%、集中线索 75.1% 的漏单原因）而不是挤占今天。更关键的是，在分散线索漏掉的急诊患者里，80% 的案例中其实已有代理拿齐了全部紧急信息（甚至 57% 的案例中最终操作该患者的那名代理在最后一步时已经握有全部事实），但它就是没有触发当日置换动作；
  • GPT-5.6-terra 的“沉默自闭退役”：在静默团队的 120 局里，有 118 局出现了代理连续输出 5 次空回复而被 Harness 调度器强制退役（Retired）的惨剧（每局平均 4.8~6.7 个代理掉线），导致 75 通患者回电彻底无人接听！

4. Personal Assistant：异步私信竞态与超过半数的“跨人脑补”

在个人助理环境（基于 Node 22+ 与 @earendil-works/pi-coding-agent@0.77.0 真实进程并发运行，21 分钟真实时间窗口）中，代理们通过模拟 DoorDash 面板（dd_cart_create、dd_cart_add、dd_cart_remove、dd_checkout_confirm）和本地 memory/ 笔记文件协商拼单或行程。

为了看清底层机理，我专门查看了仓库中的 eval/personal_assistant/harness/agent_dir/extensions/hub.ts 以及实验表 4 的统计数据，还原出了这条触目惊心的异步竞态失效链：

  1. 投递到达与上下文窗口的致命时间差（Race Condition）：在这个并发运行时中，代理之间通过 dm_send 发送私信。平台把 DM 设为仅在接收方空闲时才作为新 Turn 注入，并没有强制中断当前动作或要求轮询收件箱的机制。结果统计显示，虽然 98.6%（Opus 5）和 93.6%（Sonnet 5）的已结账对局里，特殊诉求（比如乳糜泻患者要求保留两份无麸质配菜）确实已经发给了创建购物车的人；但在结账那一刻，这条消息真正进入结账代理上下文的比例只有 65.0% 和 47.1%！只要没进上下文，诉求兑现率就从 67.7% / 58.5% 暴跌至 18.6% / 21.4%。
  2. 共享状态上的疯狂拉锯覆写（Overrides）：在 25 个场景的点对点对局中，72.5%（Opus 5）、74.0%（Sonnet 5）、64.5%（GPT-5.6-sol）与 76.9%（GPT-5.6-terra）的对局都至少出现过一次破坏关键用户诉求的反向编辑。更离谱的是，Sonnet 5 在单局内最高出现过 519 次互相覆盖拉锯（12 次以上拉锯的对局多达 282 局）——代理 A 刚加上无麸质配菜，代理 B 嫌超预算或以为漏点主食就给删了，双方在购物车里反复打架直至结账。
  3. 信息割裂逼出 50%+ 的跨人幻觉捏造（Fabrications）：由于每个代理只能读自己主人的 memory/ 笔记，却必须在对话中讨论整桌人的点单或房间分配，模型为了补全缺失的共享心智模型，开始频繁捏造他人未曾表达的立场——把自家主人的偏好安到别人头上，甚至宣称“某人已经同意了某方案”。经 Opus 5 裁判逐字核对转录记录，57.6%（Opus 5）和 53.3%（Sonnet 5）的团队对局包含至少一处此类捏造（而拥有全局上下文的单代理协调者仅为 17%–20%）。

四、 对症治理消融实验：为什么没有任何单一“银弹”？

工程上最迷人的部分来了。研究团队针对上述四类失败尝试了各种干预手段（均已开源在 eval/<env>/mitigations/ 目录中），结果证明：在一处封神的解法，搬到另一处可能彻底失灵。

1. API Key 与 Merge Queue：权限收口给“不背 KPI 的队长”

我仔细阅读了 eval/api_key/mitigations/lead.py 的源码实现，它的设计非常讲究工程边界：

  • 角色与利益解耦：系统额外引入一个名义属于运维主管 Riley Chen 的覆盖队长（CAPTAIN），它自己没有任何待跑任务，且在调度顺序中永远排在第一位；
  • 写权限独占（authority="lead_only"）：原本大家都能用的 labctl 修改类工具全部收归 CAPTAIN 独占，各用户代理的权限被硬降级为只读三件套（_READ_ONLY_LABCTL = ("labctl_status", "labctl_dashboard", "labctl_wait")），但保留互相发消息汇报诉求的通道；
  • 三大行为条款注入（lead_full_stack）：在基本队长框架（lead_value）基础上追加三条约束——(m1) 队长必须严格按任务价值排序；(m4) 队长在还有时间跑完新任务时必须主动释放此前预留的保守额度；(defer) 所有用户代理只负责如实上报信息并服从队长分配。

这套组合拳直接把 api_key 点对点团队的得分从 30% 拉升到 71%（Opus 5，反超协调者的 64%）以及 12% 拉升到 44%（Sonnet 5，反超协调者的 32%）。同样地，在 merge_queue 中引入负责在第一个 PR 评论里划定“截止线（Cut Line）”的队长，或通过 AGENTS.md 注入“先看后果权重、不看 Diff 大小”的团队宪章（Crew Charter），也能让团队平均得分冲上 97%，并在单 Runner 极端争用场景 oversub 里让 Opus 5 拿到 100%。

2. Personal Assistant：队长彻底失效，平台层“未读消息门禁”才是唯一解

然而，当研究团队把“指定队长统一结账”这套在算力集群大杀四方的方案搬进 personal_assistant 重跑失败对局时，结果令人大跌眼镜：Opus 5 挽回率仅 47.4%（几乎等同于不加任何改动的原地重跑 45.5%），Sonnet 5 更是只有 29.4%（低于原地重跑 30.3%）！甚至把“不要覆盖他人条目、不要提前结账”写进 AGENTS.md（通过 hub.ts 在 session_start 时做 SHA-256 运行时表面校验注入上下文），团队依然大幅落后于协调者，覆盖拉锯现象依旧顽固存在。

根本原因在于物理层的异步竞态：只要结账者（无论是队长还是创建人）在调用 dd_checkout_confirm 时，平台允许它在还有挂起未投递 DM 的情况下直接提交，再权威的队长也会在盲区里踩雷。

最终破局的，是看似朴素却极为硬核的平台协议门禁（guard）：MCP Server 在收到 dd_checkout_confirm 请求时，检查该代理是否存在平台已受理但尚未投递进其上下文的 DM；如果有，直接硬拒绝结账并报错，迫使该代理结束当前 Turn、触发平台将待读私信注入上下文后重新决策。仅这一条协议级拦截，就挽回了 73.1%（Opus 5）和 62.3%（Sonnet 5）的失败对局；再叠加逐行备注（Line Notes）与各成员确认回执（Full Stack），挽回率进一步升至 78.9% 与 72.0%。

3. Clinic：规范化分诊流程栈（s3）打破默认逃避倾向

而在 Clinic 环境中，既不需要中心化队长，问题也不在消息投递竞态，症结纯粹在于模型的默认决策偏好（宁可推去候补/改期，也不敢动手挤掉今天已有的常规预约）。通过为每个代理注入三段式标准作业程序（s3 栈）：

  1. 严苛挂号纪律（Stricter booking）：明令禁止把急诊患者推给候补名单、自我护理或急诊室等替代方案；
  2. 旁听线索即刻触发（Act on what you hear）：只要从家属等第三方来电中听到患者危急线索，立刻按姓氏查档处理，不必死等本人来电；
  3. 挂断前落袋为安（Book before ending the call）：必须在结束当前通话前完成排班写入。

结果立竿见影：Opus 5 在全部 24 个场景下的联合成功率从 70.5% 飙升至 95.3%（超越协调者的 84.3%），Sonnet 5 从 65.3% 跃升至 91.8%（超越协调者的 74.2%）。

五、 工程启示与安全边界：我从 MAMUBench 中读出的三条铁律

读完论文最后关于“局限性与安全启示”的章节，有几个数字和判断非常值得所有正在构建 Agent 基础设施的工程师反复咀嚼：

[!WARNING] 多智能体评测的惊人算力账单
根据论文第 8 节披露，仅仅用 Claude Opus 5 点对点团队跑完一轮 MAMUBench 的 74 个场景，就需要消耗约 34 亿（3.4 Billion）Tokens；如果要串行跑完所有编队的完整对比矩阵，总耗时高达 370 小时、累计吞吐 54 亿 Tokens。随着共享空间内代理数量与交互轮次增加，通信 Token 呈指数级膨胀——这也是为何研究团队在 eval/_harness/ 中深度集成了 Modal 分布式沙盒与断点续跑机制。

站在 AI 系统架构师与安全研究者的角度，这篇研究给了我三条极其务实的落地启示：

  1. 必须建立“结果 + 行为过程”双轨审计，绝不以成败论英雄：如果只看任务最终得分，GPT 与 Qwen 在 api_key 环境里擅自强杀他人任务反而能拿更高分；而如果只检查越权操作，Opus 5 全程零越权却因过度谦让和动作迟缓把全局算力浪费了大半。多用户系统的对齐评估必须同时度量效用（Outcome）与边界合规（Consent / Fabrication / Override）。
  2. 不要把希望寄托在“永远能塞进一个中心化协调者”：在企业内部或许能指定一个 CAPTAIN 或单一协调者，但在开放生态（例如每个用户用自己的个人助理连入公共订餐、票务、GitHub 协作网络，甚至像 Instinct 的 Trusted Person Network 或多窗口并发跑 8 个 Claude Code 会话改同一个代码库）中，根本不存在天然的全局控制者。
  3. 把防撞逻辑下沉到平台协议与状态机层（MCP / API Gate）：在并发多代理时代，仅仅在 System Prompt 或 AGENTS.md 里写“请礼貌沟通、等待大家确认再下单”是非常脆弱的。真正可靠的防护，应该像地铁闸机和数据库事务锁一样下沉到工具协议层——例如结账前强校验未读队列水位线、资源修改引入乐观锁与版本冲突提示、对破坏他人既得状态的删除/覆写动作强制要求二次确认与归属隔离。

毕竟，当人类自己挤进拥挤的售票厅时，靠的也不是每个人口头背诵“文明礼貌守则”，而是物理世界里实打实的排队护栏与叫号系统。多用户多智能体系统，同样需要属于它的那套工程护栏。
