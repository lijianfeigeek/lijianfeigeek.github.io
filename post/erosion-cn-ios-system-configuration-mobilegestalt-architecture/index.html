从 worse_query 逃逸到跨容器系统工程：深入 Erosion-CN v0.9.2 的原位落盘、CSStore2 图谱与国行底层重构

2026-11-11 31 min read # worse_query # MobileGestalt # Apple 智能 # 系统加固 # 沙盒逃逸 # 逆向工程 # iOS

随着针对 iOS 26 与 iOS 27 的 worse_query 0-Day 沙盒逃逸漏洞公开，社区迅速涌现出利用特权借调直接修改系统底层配置的工具。然而在真机实测中，上游原版 Erosion 频繁遭遇“手机一重启修改全部失效反弹”、“内置 Plist 编辑后相机取景彻底黑屏”、“0 字节截断导致白苹果软砖”、“高 Inode 主力机扫盘卡死数分钟”以及“国行双卡基带冲突”等一系列灾难性故障。

开源分支 Kianuni/Erosion-CN 在演进至 v0.9.2（截至 2026 年 11 月 16 日 commit 2b36c33）的过程中，早已超越了简单的汉化修补：它不仅重构了零 0 字节原位落盘协议、dyld 内存动态偏移解析与双重原厂金库，还进一步构建了基于 LaunchServices CSStore2（"bdsl" + NSURL Bookmark TLV）的 <50ms 容器图谱引擎、基于 APFS clonefile() 的零锁 SQLite 遥测快照管道，以及覆盖 30 余项二进制 CacheData 槽位的双写与双向自愈防线。

[!NOTE] 源码审计与版本追踪基线
本文最初基于我对 Erosion-CN 初版防白苹果架构的真机审计，现已同步扩容至 v0.9.2（commit 2b36c33，2026-11-16）。文中引用的所有源码路径、函数名、字节偏移、CacheData 槽位索引及分流域名清单，均来自我对仓库内 Swift 与 Objective-C/C 核心源文件的逐行核验。

在移动操作系统安全对抗的漫长历史中，修改系统配置（如启用内部特性、解锁地区限制、调整硬件渲染策略）向来属于越狱与内核提权工具的专利。苹果通过沙盒扩展机制（Sandbox Extensions）、强制访问控制（MACF/Seatbelt）以及守护进程容器隔离策略，构筑了极其严密的信任边界。

然而 worse_query 0-Day 漏洞以纯用户态手法撕开了这层边界：无需内核漏洞（No tfp0 / No PPL Bypass），只要一个具备标准 App Group 权限的普通侧载应用，就能诱导高特权守护进程 containermanagerd 签发内核级沙盒扩展令牌，自由读写原本严防死守的系统共享容器。但“拿到权限”只是起点，如何在不弄砖设备的前提下安全写入、跨版本精准定位字节偏移、以及零阻塞提取系统跨容器数据，才是决定一个底层研究工具能否进入生产级可用状态的分水岭。

一、全栈架构与特权借调：worse_query 的越界物理学

在深入具体的写入协议与跨容器引擎之前，我先顺着 Erosion-CN v0.9.2 的代码依赖关系，将整套系统拆解为六层协同防御体系：

1.1 App Group 符号链接欺骗与只读令牌收敛

在 iOS 沙盒模型中，普通侧载应用被隔离在自身的 Data 容器内，唯一的合法跨进程共享通道是 App Group（com.apple.security.application-groups）。在 Erosion/Exploits/worse_query.m 中，核心越界链路通过以下 6 步完成特权借调：

  1. 获取当前应用自身 App Group 物理目录下的 Library/Caches 路径；
  2. 通过 dlopen 动态打开 /usr/lib/system/libsystem_containermanager.dylib，解析 container_query_create、container_query_set_class、container_query_set_part、container_query_get_single_result 等内部符号；
  3. 构造 class = 7（SystemGroup / Shared Container）、part = 3（Library/Caches）的查询句柄；
  4. 在临界区内移除合法 Caches 目录并布置指向受保护系统目标容器的符号链接（Symlink Redirection）；
  5. 触发 containermanagerd 查询解析，后者未严格阻断自建软链接而沿着符号链接将目标系统容器误判为合法宿主，签发一份内核级的 sandbox_extension_token；
  6. 在用户态调用 sandbox_extension_consume(token) 获取读写句柄，并立即清理恢复现场。

在 v0.7.2 之后的安全加固中，Erosion-CN 对 Erosion/Exploits/WorseQuerySwift.swift 进行了关键重构：

  • 读写权限最小化（requireWrite: false）：对于 Powerlog、VoiceMemos、osanalytics 等只读遥测与探测场景，显式传入 requireWrite: false——只要 fm.isReadableFile(atPath:) 校验通过即保留并复用只读令牌，不再因目标目录仅允许 mobile 只读而误判失败，同时也杜绝了不必要的可写句柄常驻暴露；
  • 双锁句柄池隔离：通过 exploitLock 串行化符号链接临界区竞争，再通过 handleLock 维护 activeHandles 缓存字典；当句柄失效或被释放时严格调用 worse_query_release 归还内核令牌，避免沙盒扩展槽位泄漏。

1.2 动态权限签名自适应（Mach-O CSBlob 回退解析）

市面上常用的侧载工具（SideStore、AltStore、Feather、Sideloadly、Impactor 等）在重签 IPA 时，往往会依据个人账号 Bundle ID 重写 Entitlements 中的 App Group 标识符。上游原版硬编码 group.com.jbdotparty.Erosion.WQ，在绝大多数自签环境下启动即报 Error -1 崩溃。

WorseQuerySwift.swift 引入了双层自适应探测逻辑：

// 1. 首选方案：通过 Security.framework 动态读取当前进程任务权限
if let task = SecTaskCreateFromSelf(nil),
   let value = SecTaskCopyValueForEntitlement(task, "com.apple.security.application-groups" as CFString, nil),
   let groups = value as? [String], !groups.isEmpty {
    signedGroups = groups
}
// 2. 次选方案：若 SecTask 返回受限，直接映射主二进制解析 Mach-O LC_CODE_SIGNATURE
else if let fallbackGroups = Self.readMachOAppGroups(), !fallbackGroups.isEmpty {
    signedGroups = fallbackGroups
}

当 SecTask 受限时，readMachOAppGroups() 会直接按 FAT_MAGIC / FAT_MAGIC_64 与 MH_MAGIC_64 匹配当前架构切片，定位 LC_CODE_SIGNATURE 载荷，并校验大端魔数 0xfade0cc0（Embedded SuperBlob）与 0xfade7171（Embedded Entitlements XML），提取真实生效的 group.* 数组并按优先级验证容器可打开性。这一机制让应用在任何合规重签环境下都能零配置正常启动。

二、防白苹果硬核门禁：零 0 字节原位覆盖写入协议

拿到系统容器的读写权限之后，最严峻的挑战在于如何确保修改持久生效且永不弄砖设备。上游原版在文件写入层犯下的两个低级错误，正是真机测试中“重启反弹”与“白苹果无限循环”的元凶。

2.1 剖析两大致命 Bug：为什么原版会“重启反弹”与“0 字节软砖”？

  1. 临时文件替换导致重启反弹：原版中 mgWriteAtomically 开关判断疏忽，实际走了 Cocoa 高级 API replaceItemAt。它在同目录下先生成临时文件再重命名替换，这不仅改变了 com.apple.MobileGestalt.plist 的 APFS Inode，更将文件 POSIX 属主从系统专用的 _mobilegestalt 改写为普通沙盒用户 mobile。设备冷重启时，系统启动守护进程检测到 Inode 与安全属主异常，直接丢弃缓存并从硬件熔丝重置出厂值。同时，原版在 iOS 27 上错误注入了非缓存键 RegionInfo（zHeENZu+wbg7PUprwNwBWg），直接触发开机缓存整包合法性校验重置。
  2. ftruncate(fd, 0) 悬空窗口引发白苹果：原版在覆写系统文件前直接执行 ftruncate(fd, 0) 清空文件。从清空到新数据写完的毫秒级窗口内，磁盘上的 com.apple.MobileGestalt.plist 是一个 0 字节空文件。一旦此刻发生 Jetsam 内存强杀、看门狗超时或意外断电，重启后系统服务读取到空文件会直接 Panic，手机陷入只能 DFU 刷机救砖的白苹果死循环。

2.2 WriteHelpers.swift 的防线：pwrite + F_FULLFSYNC + 原位回滚

在 Erosion/Helpers/Functions/WriteHelpers.swift 中，Erosion-CN 彻底摒弃了上层文件替换封装，以底层 POSIX 原语重构了零 0 字节窗口原子写入协议：

核心代码执行链如下：

func writeFileAtomically(_ data: Data, to url: URL, allowEmpty: Bool = false) -> (Bool, String) {
    if !allowEmpty && data.isEmpty {
        return (false, "安全拦截：禁止向目标文件原位写入 0 字节空数据！")
    }
    // 1. 预先抓取原文件二进制快照 og，用于失败回滚
    guard let og = try? Data(contentsOf: url) else {
        return (false, "无法读取原文件备份数据，已中止原位写入！")
    }
    // 2. 以 O_NOFOLLOW 防止符号链接劫持，打开原有文件描述符
    let fd = url.path.withCString { open($0, O_RDWR | O_CLOEXEC | O_NOFOLLOW) }
    guard fd >= 0 else { return (false, "打开文件失败") }
    defer { close(fd) }

    do {
        // 3. 绝不先行清空！直接从偏移 0 原位覆写
        try pwriteAll(fd, data, startOffset: 0)
        // 4. 仅当新数据更短时，写完后再裁剪尾部冗余字节
        if data.count < og.count {
            guard ftruncate(fd, off_t(data.count)) == 0 else { throw fileWriteErr.truncate(errno: errno) }
        }
        // 5. F_FULLFSYNC 向 Apple Silicon NVMe 主控下发硬件落盘屏障
        guard fullFsyncSafe(fd) else { throw fileWriteErr.sync(errno: errno) }
        // 6. 重置指针逐字节读回验证
        guard lseek(fd, 0, SEEK_SET) == 0 else { throw fileWriteErr.verificationFailed }
        let verify = try readAll(fd)
        guard verify == data else { throw fileWriteErr.verificationFailed }
    } catch {
        // 7. 任何环节报错，立即用内存 og 快照在原 fd 上刷回并落盘
        if (try? pwriteAll(fd, og, startOffset: 0)) != nil {
            _ = ftruncate(fd, off_t(og.count))
            _ = fullFsyncSafe(fd)
        }
        return (false, "原位写入或物理落盘校验失败，已执行原位回滚")
    }
    return (true, "succeeded")
}

这套协议同时锁定了四大系统不变量：

  • Inode 与属主 100% 不变：始终操作原有 fd，_mobilegestalt 属主与 ACL 丝毫无损，冷重启绝不反弹；
  • 零 0 字节真空期：任意微秒断电，文件均保持合法非空结构；
  • 物理介质固化：绕过普通 fsync 仅刷入磁盘缓存的局限，通过 fcntl(fd, F_FULLFSYNC) 强制写入物理 NAND 颗粒；
  • 闭环读回自愈：写后立即 readAll(fd) 逐字节比对，出现任何差异即刻原位刷回原件 og。

三、CoreFoundation 类型救赎与整体架构演进矩阵

在 Erosion-CN 解决持久化的同时，另一个高频真机灾难是：使用内置 Plist 编辑器修改配置后，打开系统相机取景器直接黑屏。

3.1 相机黑屏根因：NSNumber 类型湮灭

在 com.apple.MobileGestalt.plist 中保存着大量布尔标记与浮点数（例如相机各焦段光学倍率 1.0、2.0、5.0 的 <real> 字段）。在 Objective-C / Swift 运行时中，NSNumber 同时承载布尔、整数与浮点类型。原版 PlistManager 重新打包字典时，粗暴地将 NSNumber 转成整型 <integer>，导致原本期待 kCFNumberFloatType 的 AVFoundation 与相机 ISP 在初始化时触发强类型校验失败，取景管线直接中断黑屏。

在 Erosion/FileManager/Viewers/Plist/PlistManager.swift 中，Erosion-CN 引入了两层无损护栏：

  1. 底层 CoreFoundation 运行时精确鉴型：优先通过 CFGetTypeID(cfObj) == CFBooleanGetTypeID() 识别真布尔值，再通过 CFNumberIsFloatType(num) 精准区分浮点 <real> 与整数 <integer>；
  2. 未修改项 100% 原样直通（Lossless Pass-through）：在 PlistItem.getRawValue() 中，只要 !isModified，直接返回内存中保存的原始对象指针 rawVal，绝不对未编辑的相机参数或二进制节点做二次解包重构（同时 v0.7.2 还修复了编辑页 @Binding 原地变异导致保存回旧值的状态同步缺陷）。

为了直观呈现从上游原版到 Erosion-CN v0.9.2 的全链路工程演进，我整理了如下对比拓扑：

四、零硬编码自适应：libMobileGestalt.dylib 内存动态解析与真机核验探针

如果说 CacheExtra 是表层字典配置，那么 CacheData 二进制块则是决定硬件能力与区域限制的真正深水区。

4.1 PAC 指针剥离扫描与 slotCount × 9 几何不变量

在 com.apple.MobileGestalt.plist 中，CacheData 是一段连续的二进制字节流，结构上严格分成两段：

  • 数值段：每个槽位固定占 8 字节（UInt64），总长 slotCount × 8 字节（布尔槽位 queryType == 11 第 0 字节为 0x00 或 0x01，高 7 字节严格为 0x00）；
  • 有效位段：紧随其后每个槽位占 1 字节有效性标志位（validity == 0x01），总长 slotCount 字节；
  • 严格校验约束：CacheData.count == slotCount * 9。

由于苹果在不同芯片与 iOS 小版本编译 /usr/lib/libMobileGestalt.dylib 时，描述符表的槽位数量与序号都会动态漂移，硬编码偏移（如盲写 0x1A8）极易踩坏相邻射频或硬件校准位。

为此，Erosion/Tweaks/MobileGestalt/MGImageReader.m 与 MGCacheLayout.swift 联手构建了一套零硬编码只读解析器：

  1. Mach-O 段只读提取：在应用运行时通过 _dyld_get_image_header 定位已加载的 libMobileGestalt.dylib，拷贝 __TEXT.__cstring 字符串池、__AUTH_CONST / __DATA_CONST / __DATA 的 __const 段以及 __cfstring 段中的 36 位 CacheUUID（不进行任何危险的 ObjC/CF 指针强转解引用）；
  2. arm64e PAC 指针标签剥离：在扫描 64 字节查询描述符表时，对指针执行 rawPtr & 0x0000_7FFF_FFFF_FFFF 位掩码剥离 bits 63:47 的指针认证（PAC）高位签名，精准反查 22 位混淆 Base64 键名对应的 +0x3A 处 Int16 槽位索引（slotIndex）和 +0x3C 处 UInt32 查询类型（queryType）；
  3. 五重防呆校验门控：validatePlist() 强制核验 CacheUUID 唯一匹配本机运行库、CacheData 总字节数精确等于 slotCount * 9、目标槽位有效位 validity == 1、高 7 字节填充全 0，且 CacheExtra 中不得存在相互打架的同名覆盖键。任何一项不满足，立即锁死写入按钮。

4.2 30+ 槽位全量双写晋升与 MGInspectorView 实时核验探针

在 v0.7.2 到 v0.8.0 的逆向深挖中，作者定位到 libMobileGestalt.dylib 内的 _MGCacheSetValueForKey 存在一条关键短路机制：对于有硬件设备树（IODeviceTree）背书且 slot >= 0 的属性，系统查询时会直接读取 CacheData 槽位，完全忽略 CacheExtra 中的同名键值！

为此，Erosion-CN 在 MGCacheLayout.swift 中完成了一次大规模的槽位晋升与扩展：

  • 将灵动岛、AOD 全天候显示、液态玻璃低功耗渲染、80% 充电上限、开机提示音、车祸检测、PWM 防频闪、相机控制键、操作按钮、轻点唤醒、台前调度等 14 项既有功能全面晋升为动态 CacheData 槽位双写，彻底突破 _MGCacheSetValueForKey 短路；
  • 进一步挖掘并纳入了涵盖影像/健康进阶能力（混音 Audio Mix、空间音频录制、FaceTime 空间音频、按下快门瞬间抓拍 ResponsiveShutter、健康高血压趋势评估 HypertensionNotifications）以及 日韩快门静音 3 槽联动、高低功耗双麦并发、CarPlay Ultra 多屏、120Hz 触控投递、AirPods 临床助听器 3 槽联动、美版血氧专利解除、睡眠呼吸暂停检测 等共计超过 30 个经过 slot >= 0, queryType == 11 严格验证的二进制硬件槽位。

同时，在 Erosion/Tweaks/MobileGestalt/MGInspectorView.swift 中新增了 真机生效核验与槽位探针（MGInspectorView），提供三大视图模式：

  • 核心核验：只读调用系统库 MGCopyAnswer，将 原机备份 (OriginalGestalt)、当前待写配置 (CacheData / CacheExtra) 与 真机实时返回值 (MGCopyAnswer) 三源同屏比对；
  • 全量槽位表：完整列出本机动态解析出的 720+ 个二进制 CacheData 槽位，支持按修改差异过滤、显示 0xXXXX 十六进制偏移，点击任意行即可现场触发 MGCopyAnswer 探测；
  • 自由键名探针：支持输入任意 22 位混淆键或明文键（如 ProductType、RegionCode），毫秒级对照内存生效值与磁盘缓存状态。

4.3 v0.9.1 关键修复：Personal Translator (#266) 基线锁止与双向自愈

在社区实机排查中，部分用户反馈照片“快速消除”正常，但点击“高质量消除 / 扩图 / 重构”或相机轮盘切入 SIRI 模式时 0 秒瞬间报错（连转圈都没有）。

通过 MGInspectorView 交叉比对 iPhone 15 Pro Max (iPhone16,2) 与 iPhone 18 Pro Max (iPhone19,7) 原厂 CacheData，源码审计揭示了一个极其隐蔽的硬件基线规则：

  • 在所有原生支持 Apple 智能的 iPhone（iPhone 15 Pro 至 iPhone 18 Pro Max）原厂 CacheData 中，Personal Translator（M1n2sAqf33NAOgZRGxQYBA，槽位 #266）出厂默认即为 true (0x01)，而实验性的 Audio Intelligence（rb2tKZxlj0Gm2tBmUQSLqQ，槽位 #178）出厂默认均为 false (0x00)；
  • 早期版本在跨 iOS 系统 OTA 升级（CacheUUID 变更导致基线快照失效）或非 18 Pro 机型一键配置时，可能误将 #266 降级写成 false (0x00)（或强开了 #178），导致 GenerativeModels / ModelCatalog 在本地预检阶段 0 毫秒直接熔断报错。

Erosion-CN v0.9.1 在 GestaltStore.swift 与 MGInspectorView.swift 中彻底锁死了全系原生 AI iPhone 的原厂基线（#266 = true、#178 = false，免疫跨版本备份不匹配与污染缓存），并在「Apple 智能激活四要素体检」面板中实现了双向偏移检测与一键配齐 / 修复自愈能力，恢复出厂或重建缓存时自动清理本地残留槽位快照。

五、突破全盘扫盘瓶颈：CSStore2 极速图谱与 APFS clonefile() 跨容器引擎

从 v0.8.0 到 v0.8.6，Erosion-CN 完成了一次极具技术含金量的架构跃迁——它跳出了单纯修改 MobileGestalt 的单一工具范畴，演进为一个高性能的跨容器系统分析与数据提取平台。

5.1 三级容器寻址降级链：告别 5 分钟高 Inode 卡死

在传统基于 worse_query 的文件管理器中，若想列出本机已安装应用的数据容器路径与名称，通常只能依赖 pathleak.m：从 inode = 1 到 max_inode 逐个调用内核 fsgetpath() 暴力撞库，再读取每个容器的 xattr 扩展属性。在早期版本中，当遇到长期使用、累计 APFS Inode 突破 2 亿 的主力机时，pathleak 扫描上限保护失效，打开应用列表动辄卡死 5 ~ 6 分钟！

Erosion-CN 通过 Erosion/Exploits/CSStoreResolver.m 与 CSStoreEngine.swift 构建了一套三级 <50ms 秒级寻址引擎：

  1. 第一级：MCM 瞬时容器列举（<5ms）
    csstore_mcm_list_containers() 动态调用 libsystem_containermanager.dylib 的 container_query_iterate_results_sync，遍历 class 1..14；在允许直接列举的系统版本上可在 5 毫秒内直接拿到全机容器目录清单。
  2. 第二级：CSStore2（"bdsl"）6 布局解析 + 自顶向下最近邻发现
    当 containermanagerd 收紧遍历接口时，CSStoreEngine 先通过 probeMaxInode() 在临时目录写入探针文件获取当前设备真实最大 Inode，随后 csstore_scan_latest_paths() 自顶向下（从 maxInode 倒序）以 32768 为分片、最多 4 个并发 Worker 线程配合 20s 超时熔断调用 fsgetpath，秒级锁定系统最新创建的 com.apple.LaunchServices-*.csstore 二进制数据库（大小限定 0x1000 ~ 64MB），并持久化路径签名以便后续直接校验 statSignature 零扫盘直读。
    拿到 .csstore 数据并验证 "bdsl" 魔数后，csstore_parse_data() 会一次性并发尝试 6 套预设内存布局（27.0、26、27.2、27.2b、27.2c、27.2d），通过位集（Bitset）高效索引字符串表，精确解码出应用容器 UUID、PluginKit 插件 UUID、Bundle ID 与本地化显示名称。
  3. 第三级：无 Schema 依赖的 NSURL Bookmark TLV 兜底抢救（v0.8.6 新增）
    针对 iOS 26.3.x 等新版固件修改 CSStore2 结构体字段偏移导致 6 套布局均未命中的情况，CSStoreEngine.salvageFromCSStoreBytes() 会直接扫描二进制流中的路径前缀与 NSURL minimalBookmark ("book") 通用 TLV 序列（[uint32 len][uint32 type = 0x00000101][4-byte padded UTF-8][0x24 00 00 00 01 01 00 00][36-byte UUID]），不依赖任何易变结构体偏移直接抢救出全部合法的 Application、PluginKitPlugin、InternalDaemon 与 AppGroup 36 位 UUID 路径，并辅以内置中文名对照表和 pathleak.m 最终兜底。

5.2 SQLiteSnapshotHelper：基于 APFS clonefile() 的零锁数据库快照

系统级服务（如电池遥测 powerlogHelperd、语音备忘录 VoiceMemos、Safari 浏览器）在运行时往往会对自身的 SQLite 数据库持有 WAL 写锁。如果直接从第三方进程打开系统路径下的数据库文件，不仅极易因数据库锁死报 SQLITE_BUSY，更可能触发 WAL/SHM 恢复写入从而破坏正在运行的系统守护进程状态。

在 Erosion/Tweaks/Diagnostics/SQLiteSnapshotHelper.swift 中，Erosion-CN 给出了教科书级的解决方案：

@_silgen_name("clonefile")
private func apfs_clonefile(_ src: UnsafePointer<CChar>, _ dst: UnsafePointer<CChar>, _ flags: UInt32) -> Int32
  • 写时复制（Copy-on-Write）零锁瞬时克隆：调用 Apple APFS 文件系统底层私有/系统调用 clonefile()，将目标 .db / .PLSQL 主文件及其伴随的 -wal、-shm 事务日志瞬间零拷贝克隆至应用私有的临时沙盒目录，并 chmod 0600；
  • 沙盒内安全 WAL 重放回退：优先以 SQLITE_OPEN_READONLY | SQLITE_OPEN_NOMUTEX 打开副本并执行 SELECT name FROM sqlite_master LIMIT 1; 探活；若原库处于高并发写入状态导致只读模式无法读取最新 WAL 页，则仅在私密沙盒副本上移除 -shm 并以读写模式回放 WAL，对系统原始路径做到绝对的 0 字节物理触碰。

依托这套快照基础设施与 CSStore2 极速寻址，Erosion-CN 落地了五大跨容器实战模块：

六、本土化深水区与网络协同：双卡 eSIM 兼容、安全防呆与 AppleFlow 分流注入

解决底层 I/O 与跨容器能力后，面对国内真机最棘手的硬件兼容与网络策略冲突，Erosion-CN 在 v0.8.1 – v0.9.2 交出了一套完整的高可操作性方案。

6.1 双模式地区解锁与国行 18 Pro 系列“空卡写卡法”

国行版 iPhone 18 Pro 与 18 Pro Max（A3715 / A3718）采用了全球独有的“正反双实体 SIM 卡槽 + 内置 eSIM 芯片”三通道复用主板，而美版 LL/A（A3472 / A3473）为无卡槽纯 eSIM 机型。若粗暴写入美版无卡槽监管型号，基带开机检测到卡托内插着双实体卡会直接触发冲突，临时屏蔽「添加 eSIM」与 EID 甚至导致背面副卡失效。

为此，GestaltStore.swift 在 MGRegionUnlockMode 中提供了双模式细化切换：

  • 完整美版 LL + LL/A（默认）：同步修改 RegionCode = LL、RegionInfoFromSysconfig = LL/A 并自动映射对应美版监管型号（usRegulatoryModelNumber），确保海外 Apple 智能、快门静音与健康区域特性最完整；
  • 仅改区域代码 LL（保留 CH/A 后缀与双卡兼容）：仅将 RegionCode 设为 LL，完整保留原厂 CH/A 销售地区与监管型号，兼顾基础 Apple 智能准入与国行双卡基带稳定性。

对于需要在国行 18 Pro 系列上实现“双实体卡 + 多张海外 eSIM”共存的场景，社区实测验证了“空卡写卡法”：① 先拔出 SIM 卡托保持空卡，开启「解除地区限制」+「解除国行底层限制」并空卡冷重启；② 连 Wi-Fi 挂全局海外节点扫码写入海外 eSIM；③ 写卡完成后若仅需正面单实体卡可直接插回共存；若需使用背面第 2 张实体卡，进 Erosion-CN 单独关闭「解除国行底层限制」（并将地区模式切换为仅 LL），应用重启后再插回双实体卡托，已写入 eUICC 的海外 eSIM 依然完整保留可用。

6.2 四重硬件防呆锁与伪监管 403 死锁体检

“并不是开关开得越多越好。”Erosion-CN 在真机踩坑中归纳并内置了四重自动化防呆护栏：

  1. DeviceSupportsSiriHub 拦截：该槽位属于带屏家居中枢硬件专属标记，在 iPhone / iPad 上强开会导致 assistantd 无限卡死在“正在添加 Siri 支持内容”，现已默认锁止并提供一键清理；
  2. Personal Translator (#266) / Audio Intelligence (#178) 双向守护：如前所述，防止 ModelCatalog 校验断路破坏照片「高质量」消除与相机 SIRI 模式；
  3. 空间音频与四麦克风硬件解耦：将 spatial-facetime-audio 与 spatial-audio-recording 彻底拆分为两个独立开关，对 iPhone 15 Pro 及更早的三麦克风旧机型自动锁定关闭空间音频录制，防止语音备忘录出现无效“录音室”档位导致录音中断；
  4. 伪监管 403 死锁体检（ConfigView.swift）：永久禁用高危的个人设备 IsSupervised=true 开关（但保留无害的锁屏防丢铭牌 AssetTagInformation），并通过 isGenuineMDMCloudConfig() 检查 CloudConfigurationDetails.plist 是否存在 ConfigurationSource、AnchorCertificates 等真实企业证书键——自动保护真实企业 MDM，而对早期改机工具遗留的“伪监管残留”提供保留锁屏文字的一键清除，防止后续 OTA 升级卡死 Setup Assistant 403 远程管理白屏。

6.3 跨容器分流注入（同步 AppleFlow v1.0.1）与单包双语热切换

许多用户在解锁完 MobileGestalt 后，常卡在最后一步网络分流上：要么因为将 guzzoni.apple.com 代理或 Fake-IP 化，丢失国行普通话「询问来电原因」并报 Siri 错误；要么因为通用规则集漏掉了 PCC（Private Cloud Compute）盲签名域名，导致照片高质量消除报 PrivateCloudComputeError Code=32033。

Erosion/Tweaks/CrossContainer/AppGroupHubView.swift 在 v0.9.2 中全面同步了配套开源项目 AppleFlow v1.0.1 的生产级规则，支持一键导出 Surge / Loon / 小火箭（.sgmodule） 与 Stash（.stoverride YAML） 双格式（甚至可通过 worse_query 将模块直接注入本机 Surge AppGroup 的 Documents/Profiles/Modules 目录）：

  • Siri 主网关直连保活：将 guzzoni.apple.com、*.siri.apple.com、dejavu.apple.com、sequoia.apple.com、*.smoot.apple.com 设为 DIRECT，并注入 skip-proxy / always-real-ip（Stash 为 fake-ip-filter），保障普通话来电询问与 Siri 零延迟响应（系统地区设为「台湾」、首选语言「简体中文」、Siri 设为「中文（普通话 - 中国大陆）」即可完美共存）；
  • PCC 盲签名与精准视觉智能分流：置顶覆盖 gspe1-ssl.ls.apple.com、*.issuer.apple.com、ropes.apple.com、mask-api.icloud.com、mask.icloud.com、mask-h2.icloud.com、*.app.apple.com、apple-relay.*，并收窄泛域名，精确匹配 lens.google.com、gemini.google.com、chatgpt.livekit.cloud、sora.com、claudeusercontent.com 等生产域名（需走支持 UDP 443 QUIC 的美区节点）。

此外，自 v0.9.0 起，Erosion-CN 通过 LocalizationManager.swift 在单一 IPA 内完整打包了 1,305 条 简体中文 (zh-Hans) 与 英文 (en) 词条，支持非中文系统自动切换英文以及在设置页内实时热切换，并在 v0.9.2 设置页集成了 AppleFlow、WQGuard、Camlo、Enkard 生态矩阵。

七、双重原厂金库与终极可逆性：跨卸载自愈与无损送修

所有系统调优工具的终极生命线，是可逆性（Reversibility）。个人 Apple ID 自签证书只有 7 天有效期，一旦证书过期或误删应用，保存在沙盒 Documents 内的原厂备份 OriginalGestalt.plist 就会随沙盒被 iOS 彻底抹除；重装后若直接抓取已经被修改的系统缓存，就会造成“脏基线二次归档”的永久性丢失。

Erosion-CN 在 GestaltHelpers.swift 中建立了一套横跨沙盒生命周期的双重原厂金库（Dual-Vault）与两级回退状态机：

  1. 沙盒 + 系统级隐藏金库双写：首次捕获纯净原厂配置时，除了在沙盒保存 OriginalGestalt.plist 与 .sha256 摘要，还会借助 worse_query 特权在系统共享容器 /private/var/containers/Shared/SystemGroup/systemgroup.com.apple.mobilegestaltcache/Library/Caches/ 下固化 .erosion_factory_vault.plist 与 .erosion_factory_vault.sha256，并严格标记 isExcludedFromBackup = true 防止随 iCloud/Finder 备份迁移污染新设备；
  2. 跨卸载重装自愈与污点拦截：即便 7 天过期卸载重装，初始化探针也能自动读取系统隐藏金库并校验 SHA-256，瞬间无损找回初始原厂快照（若检测到首开时系统已被其他工具改脏，也会主动发出警告）；
  3. 两条官方售后级无损还原路径：
    • 路径 A（一键原厂回退）：核对 SHA-256、CacheVersion、CacheUUID、CacheData 长度与真实内核 ProductType 后，调用 pwrite + F_FULLFSYNC 原位刷回原厂参数，同步清空本地自定义开关、锁屏铭牌、伪监管残留与拨号盘缓存；
    • 路径 B（硬件熔丝原生重建，送修天才吧终极兜底）：点击菜单中的 「清除并重建缓存」 删除系统 com.apple.MobileGestalt.plist 并立即冷重启，内核与启动守护进程会直接从主板 SysCfg 硬件熔丝重新拉取生成 100% 原生、零修改痕迹的全新缓存，随后删除侧载应用即可毫无争议通过 Apple 官方 AST2 硬件诊断检测。

八、总结与技术反思

从初版聚焦“零 0 字节写入与相机防黑屏”，到 v0.9.2 演进为集 CSStore2 秒级寻址、APFS clonefile() 零锁快照遥测、30+ CacheData 硬件槽位双写与 AppleFlow 分流协同于一体的全栈工具箱，Erosion-CN 为我展示了底层系统工具走向成熟工程化的完整脉络：

[!NOTE] 工程反思：防御性编程决定工具的生命周期
在高度封闭的 iOS 系统中，漏洞本身（worse_query / fsgetpath）只是撬动权限的杠杆；真正决定工具究竟是“随时白苹果的玩具”还是“上万台真机零崩溃的生产力底座”的，永远是对系统不变量的敬畏——绝不留 0 字节文件窗口、绝不猜硬编码内存偏移、绝不盲锁系统正在写入的 SQLite 数据库、也绝不透支设备的出厂可逆性。

如果你正在深入研究 iOS 26/27 的 containermanagerd 沙盒边界、LaunchServices CSStore2 二进制索引格式、或是 libMobileGestalt.dylib 的 PAC 描述符表结构，Kianuni/Erosion-CN 的整套源码绝对是一份不可多得的实战参考范本。

[!WARNING] 实战操作提醒
系统底层研究存在潜在稳定性风险，操作前请务必通过电脑完整备份设备重要数据；切勿在个人零售设备上强行写入企业监管标记，也切勿使用会剥离 App Group 权限的签名方式安装；此外，国行（CH/A）设备在 iOS 27.3 beta 1 上仍受本地生成式云端资格策略拦截，如需照片高质量消除与相机 SIRI 模式建议停留在 iOS 27.2.x。
