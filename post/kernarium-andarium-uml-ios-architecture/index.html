在 iOS 沙盒里跑起真 Linux 6.18 内核与 Android 17：深潜 Kernarium 与 Andarium 的 User-Mode Linux、Gadget 解释器及 KosmicKrisp 架构

2026-11-20 24 min read # 架构剖析 # 虚拟化 # Linux # Android # iOS # Metal

最近在 X 上刷到 @Techjunkie_Aman 演示的一款名为 Andarium 的 iOS 应用：它不仅把完整的 Android 17（LineageOS 24）装进了 iPhone 沙盒，还能直接运行 Termux、Winlator、通过 ADB 侧载 APK，甚至在 iPhone 18 Pro Max 上跑起 3D 赛车大作《Asphalt Legends》。与过去常见“套壳容器”或只做系统调用转译的用户态兼容层不同，Andarium 背后的开源核心项目 imxieyi/Kernarium 选择了一条更为硬核的道路——把真实的 主线 Linux 6.18 LTS 内核 通过 User-Mode Linux（UML） 技术直接编译为原生 arm64 代码嵌入 iOS 运行时，再用 iSH 风格的无 JIT 线程解释器与 Mesa KosmicKrisp 图形栈打通苹果 Metal 4。

为了摸清这套刚刚在 2026 年 11 月开源并迅速斩获 1,200+ Star 的项目究竟是如何跨过苹果 W^X 内存签名、4 KiB 与 16 KiB 页表错配以及 iOS 后台 Jetsam 杀进程的层层封锁，我完整拉取了 imxieyi/Kernarium 仓库源码（含 2026 年 11 月 20 日最新提交 b14aa9e 与 1.0b15-release），逐层精读了内核桥接 ABI、汇编 Gadget 引擎、Virtio-GPU 渲染管线以及内存休眠子系统。下面我将以第一视角，全面拆解 Kernarium 与 Andarium 背后的真实工程版图。

[!NOTE] 代码审计基线与真实状态说明
本文所有技术细节、文件命名、ABI 常量与参数均源自 2026 年 11 月 20 日对 imxieyi/Kernarium 公开源码仓库（GPL-2.0-or-later）及 @Techjunkie_Aman 帖文的直接调研。值得关注的是，基于 Kernarium 运行时构建的 Andarium 此前一度成功上架 App Store，但随后因触及苹果审核指南 Guideline 2.5.2 & 1.1（“允许用户在 iOS 平台上复刻 Android 操作系统”）而被下架；目前开发者已开放 TestFlight 公测与 GitHub Releases 侧载 IPA 分发，而通用 Linux 发行版宿主应用 Kernarium 仍处于早期开发阶段。

一、为什么不模拟硬件，也不用纯用户态垫片？Kernarium 的“中间路线”

在免越狱 iOS 设备上运行 Linux 或 Android，开发者长期被困在“性能、兼容性与过审红线”的三角困局里：

  • 全系统硬件模拟（如 UTM / QEMU）：必须模拟 CPU 特权态、中断控制器与 MMU 页表遍历，一旦离开外接调试器的 JIT 授权，退回纯解释执行后性能会断崖式暴跌；
  • 纯用户态系统调用垫片（如 iSH 或 Twoyi Neo）：虽然避开了硬件模拟开销，但必须用 C/C++/Rust 在 Darwin 用户态手工重写一整套 Linux 系统调用、/proc 虚拟文件系统、Binder IPC 与信号语义，遇到 Docker Namespaces、FUSE、Loop 挂载或深度定制的 Android 17 SELinux 策略时往往寸步难行。

当我在阅读 Kernarium 根目录的 README.md 与 docs/architecture.md 时，立刻看出了作者 Yi Xie（imxieyi）的破局思路：把系统调用与内核态逻辑直接交给真正的 Linux 内核原生执行，只对客体用户态指令进行无 JIT 翻译。

这套架构最精妙的平衡点在于：

  1. 内核原生直跑，零指令翻译开销：Linux 6.18 LTS 内核本身就是以 ARCH=um SUBARCH=arm64 UML_HOST_OS=Darwin 编译出来的原生 arm64 二进制代码，被静态打包进 Xcode 签名框架的 __TEXT,__uml_elf 只读代码段。苹果只要求“运行时不能动态生成可执行页”，静态签名好的 Mach-O 代码段跑起来跟普通 Swift/C++ 函数一样，全部直接跑在 Apple Silicon 硬件核上！
  2. 用户态指令走纯数据流解释器 + 静态 AOT：Guest 里的普通 Linux ELF 或 Android APK 进程，因为没有经过苹果代码签名，不能直接跳转执行，于是交由“数据指针流驱动的 Gadget 线程解释器”和可逐页校验的静态 AOT 框架接管。

正好我最近也拆解过同样能把完整 Android 塞进免越狱 iPhone 的 两仪 Twoyi（Neo 运行时 + 2,852 个静态 AOT 单元 + gfxstream/MoltenVK）。把这两条目前站在 iOS 虚拟化最前沿的技术路线放在一起做拓扑对比，差异一目了然：

架构维度 用户态模拟内核路线（如 Twoyi Neo） 原生 User-Mode Linux 路线（Kernarium / Andarium）
内核本质 Darwin 用户态模拟层（vbinder / 虚拟 VMA） 真实 主线 Linux 6.18 LTS 原生编译入 __TEXT,__uml_elf
系统负载上限 深度聚焦 Android 13 容器 Android 17（LineageOS 24）+ KDE/Debian + Docker + Winlator
CPU 执行策略 2,852 单元系统白名单静态 AOT + 块解释器 14,512 行手写汇编 Gadget 解释器 + AOT + 可选 StikDebug JIT
GPU 渲染路径 gfxstream + MoltenVK → Metal Virtio-GPU（Virgl / Venus）→ virglrenderer → Mesa Zink / KosmicKrisp → Metal 4
多架构支持 arm64 Android arm64 + AArch32（armhf / armeabi-v7a）+ macOS x86_64 兼容切片

二、把真 Linux 6.18 塞进 iOS：128 TiB 软件 MMU 与 4K/16K 页表桥接

把原本为 Linux 宿主设计的 User-Mode Linux（UML）移植到 Darwin / iOS 上，绝不是改几个编译宏那么简单。阅读 kernel/common/README.md 和 kernel/common/abi/darwin_uml_abi.h 后，我梳理出了它必须啃下的三块硬骨头：

1. 4 KiB 客体页与 16 KiB 苹果宿主页的严丝合缝

Apple Silicon 与 iOS 的硬件虚拟内存页是 16 KiB，而所有 arm64 Linux 发行版与 Android 17（LineageOS 24）用户态生态都默认运行在 4 KiB 页粒度上。为了防止每次内存访问都被 16 KiB 对齐坑死，Kernarium 在宿主机虚拟地址空间里划出了一片 128 TiB 的稀疏软件 MMU 客户任务地址范围：

  • 一次性保留、绝不 munmap 释放窗体：首次启动时，runtime::reserve_process_native_window 保留原生内核窗口，iOS 设备与模拟器上受限于 14 GiB 签名虚拟地址上限，Guest 最大物理内存天花板锁定在 9,152 MiB（512 MiB 起步，64 MiB 步进）；后续在进程内重启客体时只通过 MAP_FIXED 覆写映射，绝不调用 munmap，防止系统其它 mmap(NULL) 趁虚抢占保留槽位。
  • 按需物理页提交与 Wired 锁定：启动参数里的 mem= 仅仅是上限而非预分配。内核分配物理页前才通过 darwin_uml_physmem_commit 提交给宿主，并在物理 iOS 设备上实时 Wire（锁定） 物理页，释放时再通过 _release 归还进程足迹。
  • 4 页聚合共享规则（vmap_group_order = 4）：针对内核态 init_mm 映射，每 1 个 16 KiB 宿主槽位对应 4 个连续的 4 KiB Guest PTE。只有当这 4 个 PTE 全部存在、来自同一底层存储文件且 16 KiB 对齐、权限完全一致时，宿主机才会把它们合并为同一块共享内存页；否则退化为私有副本并在同步点刷新——这也是为什么 io_uring 和 vmalloc 必须按 4 页对齐分配，才能与用户空间安全共享零拷贝环形缓冲区。

2. 脱离 fork 的多核 vCPU 载体调度

iOS 沙盒严禁 fork() 派生子进程。Kernarium 的应对方式是在 darwin/runtime 里为每个配置的 vCPU 预先创建一条持久化 pthread 载体线程（命名为 uml-vcpu-N-carrier，并伴随 uml-irq-notify 中断通知线程和 uml-rtc-alarm 闹钟线程）。Linux 客体内部创建成百上千个线程或 Docker 容器进程时，宿主机上并不会新建任何线程，所有 Linux 任务上下文都停留在客体内核栈上，在这些有限的 vCPU 载体之间自由迁移调度。

甚至为了榨干每一点调度性能，我在 kernel/common/README.md 里还注意到一个极其精细的 Darwin 底层优化：在 iOS 上频繁调用 pthread_getspecific() 读取当前 CPU 编号开销太高，Kernarium 的 uml_curr_cpu() 会在载体上线时自检 Darwin pthread 内存布局，验证通过后直接内联读取线程私有键，一旦布局不匹配立刻报错熔断，避免静默踩内存。

3. 全功能内核设备矩阵：为何能跑 Docker 与 Winlator

正因为跑的是完整的主线 Linux 6.18.x（仅针对 Darwin 宿主剥离了 arch/um/os-Linux 依赖，保留完整 Linux 子系统），Kernarium 顺理成章拿到了用户态垫片难以企及的内核能力：

  • 完整 Namespaces、SELinux 与虚拟文件系统：支持 ext2/3/4、erofs、xfs、Loop 设备与 FUSE，并在 SMBIOS 3.0 表里自报厂商为 Kernarium、处理器为 Kernarium Virtual CPU（同时严格禁用了 /dev/mem 以防暴露 0 地址上的内核镜像）。
  • 全套 vhost-user 半虚拟化设备：在 darwin/device/ 下独立实现了 UBD 虚拟磁盘（支持 discard 空间回收）、Console 控制台、Input 多点触控/键鼠、Audio 音频、Camera 相机、GNSS 定位（透传 NMEA 定位流）、vsock（直接打通宿主机到 Guest 内部 adbd 的字节流通道，且宿主机不暴露监听端口）以及基于 libslirp 的用户态 TCP/IP 协议栈。
  • 严谨的防穿透与零弹框网络设计：阅读 darwin/README.md 时，我发现它的网络实现考虑到了极细的苹果隐私权限陷阱——它特意关闭了 SLiRP 自带的 DNS 代理（否则查询局域网路由器会触发 iOS 弹出“本地网络权限”提示框），而是通过宿主系统解析器代答；同时主动拦截 Guest 对宿主机本机接口及 127.0.0.1 的所有 TCP/UDP 探测，防止沙盒内逃逸探测宿主机服务。

三、CPU 执行引擎的艺术：14,512 行汇编 Gadget、StikDebug JIT 与逐页哈希 AOT

内核直接原生跑在硬件上解决了特权级开销，但 App Store 和 TestFlight 依然死死卡着“不允许普通进程在运行时生成并执行新机器码”的红线。Kernarium 的 CPU 层（darwin/cpu/arm64/）给出了三轨并行的答案。

轨道 A：iSH 风格、但完全重写的纯数据 Gadget 线程解释器

在 darwin/cpu/arm64/gadgets/NOTICE.md 中，作者明确向 Theodore Dubois 的 iSH（"asbestos" 引擎）致敬，同时强调除“函数指针数组 + 内联操作数”的核心思想外，所有解码器、Gadget 银行、TLB 几何布局和翻译缓存全部为自研重写。

我统计了 darwin/cpu/arm64/gadgets/engine.S 与 engine/*.inc 下的代码规模，足足有 14,512 行汇编：

  • 绝对固定的代码段布局：所有 Gadget 汇编通过 UML::GadgetRegionLayout 强制排列在 __TEXT,__text 最前端（16 KiB 页对齐），各子段甚至精细校准了 64 字节缓存行相位（如 GADGET_PHASE_BANK 48，文档注释坦言这是在 iPad 真机上实测避免标量混合指令跌入慢速路径的经验值）。
  • 翻译块只是纯数据，零可执行内存：解码器把 Guest 的 A64、A32 或 T32 指令流翻译成由“函数指针 + 打包操作数”组成的纯数据流，存储在普通只读/读写数据堆中。由于不涉及任何 MAP_JIT 或 RX 页动态生成，它天然可以通过 App Store 与 TestFlight 审核。
  • 编译器级微优化压榨极限吞吐：
    • 单基址寄存器复用链（same_base.inc）：若同一基本块内连续多次通过同一基址寄存器向同一方向访存且中途未修改基址，首个指令作为 Leader 将转换后的宿主机基址缓存进专用寄存器 x25，后续 Follower 只要偏移不跨页即可直接复用 x25 完成访存，省去重复软件 TLB 查询。
    • 序言/尾声批量头（run_heads.inc）：针对函数开头的连续 SUB SP + 成对寄存器压栈，或结尾的批量出栈 + RET X30，直接合并成一条快路径 Head 批量执行，对齐且不跨页时一步到位；甚至还利用 AUTIASP 在无指针认证开销时零成本跳过。
    • 严格禁碰 x18 寄存器：architecture-audit 脚本会扫描全部宿主源码与生成机器码，禁止任何地方触碰 Darwin 平台保留寄存器 x18（因为 XNU 在线程中断时会随时清零 x18）。
    • 多核共享译码体与有界缓存驱逐：多个 vCPU 执行同一个地址空间时默认共享翻译体（gadget_shared_space.hpp）；每个进程受全局字节预算约束，当某个进程占满缓存触发驱逐时，会优先保护 175 ms 内正在其他 vCPU 上活跃运行的地址空间，避免“刚翻译完就被另一颗核踢掉”的乒乓抖动。

轨道 B：开发版专属的真机 JIT（brk #0xf00d 与 StikDebug）

在支持 JIT 的 macOS（含基于 FEXCore 的 x86_64 用户态兼容切片）以及挂载了调试器的 iOS 开发版中，Kernarium 可以切换至原生 JIT 引擎。

值得注意的是，darwin/cpu/jit_memory/executable_memory.cpp 是全仓库唯一被允许触碰可执行内存分配的孤岛文件。在物理 iOS 设备上，由于没有 MAP_JIT，它会在镜像附近 1 TiB 范围内申请一块可执行区域并映射一份可写别名，随后执行 brk #0xf00d（携带参数 x16 = 1、地址 x0 和长度 x1），请求外部调试器 StikDebug 向每一个 16 KiB 页写入一个字节完成系统级解锁祝福（Bless），完成后再通过 x16 = 0 让调试器安全分离。而在面向 App Store 和 TestFlight 打包时，scripts/check-app-store-bundle.py 会像安检门一样扫描二进制文件，一旦发现 UML_IOS_DEBUGGER_JIT 符号或 brk 指令立即报错中止打包。

轨道 C：UmlArm64Aot.framework 静态 AOT 与密码学逐页校验

为了给 Android 17（LineageOS 24）等庞大系统提速，Kernarium 在 tools/aot/ 下也构建了一套静态 AOT 管线：提前把 Android 核心系统库与启动镜像中已编译的 Java 字节码（boot*.oat）重写为纯只读的原生汇编块，封进 UmlArm64Aot.framework（零数据段、零重定位、可多进程共享只读映射）。

但我对比代码后发现，Kernarium 对 AOT 执行的安全性要求到了近乎偏执的程度：

  1. 必须带 EROFS 不可变位（immutable）：内核通过桥接 ABI 29 在传递 guest_code 标志位时，只有当页面明确来自只读的 EROFS 文件系统页缓存、而非匿名页或写时复制（CoW）页时，才允许进入 AOT 路径。
  2. CommonCrypto 整页 CC_SHA256 硬核验签：第一次踏入某页代码前，宿主机必须调用苹果硬件 SHA-256 指令集对整个 4 KiB 客户页做全量哈希计算，与框架内嵌的摘要逐字节比对通过后才放行；更绝的是，若另一进程或内核通过 ptrace / process_vm_writev / IC IVAU 篡改了同一物理页帧，darwin/memory/mmu/code_holders.hpp 里的物理帧持有者记录会立刻推进全局 Epoch，废除所有地址空间对该页的共享校验缓存（UML_AOT_SHARED_VERDICTS），彻底杜绝“挂羊头卖狗肉”的过时代码执行。

四、彻底抛弃 MoltenVK！Mesa Zink / Venus + KosmicKrisp 直驱 Metal 4

如果说真内核 + Gadget 解释器决定了它“能跑什么”，那么图形栈就决定了它“能不能玩《Asphalt Legends》和 Winlator”。

查阅 docs/graphics.md 时，最让我惊喜的是：Kernarium 彻底放弃了传统的 MoltenVK，转而集成了 Mesa 官方最新的原生 Vulkan-to-Metal 驱动——KosmicKrisp。整个 Apple 端构建被强制要求不链接 OpenGL.framework、EAGL 或外部 Vulkan Loader，而是由 virglrenderer 与 Mesa 内部直连：

  1. 桌面 OpenGL 4.6 / GLES 3.2 通路：
    Guest Mesa → Virtio-GPU / Virgl → vhost-user → virglrenderer → Mesa Zink（无界面 EGL）→ KosmicKrisp → MTLTexture → AppKit / UIKit
  2. Guest 原生 Vulkan 1.4 透传通路（支持 Winlator / DXVK 与高端 Android 游戏）：
    Guest Linux Vulkan → Mesa Venus → virglrenderer（capset 4）→ 直连 Mesa KosmicKrisp → Metal 4

为了支撑这套管线在沙盒内稳定运行，作者在底层打通了大量极易被忽略的细节：

  • 1 GiB 专属共享内存孔径：Guest 主机可见的 Vulkan 内存并不占用 Linux 物理 RAM，而是由宿主机分配共享内存，通过内核协商的 VHOST_USER_PROTOCOL_F_SHMEM_MAP 映射到一段固定 1 GiB 物理地址孔径（UML_VHOST_USER_SHMEM_SIZE），同时严防恶意 Guest 越界写入宿主机地址空间。
  • 硬件纹理压缩防崩溃拦截：iOS 端 GPU 一旦收到 BC / RGTC / BPTC 压缩纹理会直接触发进程强行中止，因此运行时会向 MTLDevice.supportsBCTextureCompression 查询能力并在 iOS 上主动屏蔽这些扩展；但对移动端原生支持的 ETC1 / ETC2 / EAC / ASTC LDR 则直接透传给 KosmicKrisp 硬件采样，避免客体 Mesa 在 CPU 上做高耗能的 RGBA8 解码。
  • 独立视频硬件编解码：除了 GPU 渲染通道，Kernarium 还专门拉起了一条不依赖 GPU 上下文的 Virtio-video 专线，把 Linux 客体的 V4L2 有状态编解码节点直接桥接到苹果原生的 VideoToolbox（支持 H.264 与 HEVC 硬件加速），并在 Debian 桌面镜像中附带了一个轻量级 virtio_gpu_gbm.so 后端，专门解决 Debian 原生 libgbm 无法分配 NV12/P010 平面视频缓冲区的问题。

[!IMPORTANT] 为什么 X 评论区里有人问“为什么只支持 iOS 27？”
我在检查 cmake/toolchains/Apple.cmake 时找到了最直接的工程答案：该项目的苹果平台部署基线被硬性锁定在 27.0，并且 Andarium 启动时会主动探测宿主 GPU 是否具备 Metal 4 家族特性（主要对应 A14 及以上芯片，也是驱动 Mesa KosmicKrisp 的硬前提）。由于 Xcode 的 iOS 模拟器缺乏 Metal 4 硬件设备，模拟器构建只能通过编译期宏 UML_GPU_SOFTWARE_RENDERER 回退到 Mesa llvmpipe CPU 软渲染，专门用于 UI 自动化测试（该宏会在真机/商店打包审计时被严厉禁止）。

五、iOS 沙盒保活与 Jetsam 生存工程：GPU 门控、锁剥离与分片休眠

在电脑上跑虚拟机崩溃了大不了重启进程，但在内存管制极度严苛的 iOS 上，只要后台持有一把文件锁、触碰一次被系统收回的 Metal 设备，或者内存瞬间越过 Jetsam 阈值，系统就会毫不留情地一刀劈死整个 App。在 docs/architecture.md 后半部分，我看到了一整套堪称“教科书级别”的 iOS 生存护盾设计：

1. 显式算出来的 GPU 与 Jetsam 内存预算公式

iOS 会给每个 App 分配一个进程总内存上限 LLL。Kernarium 在每次启动前只计算一次固定预算，决不让虚拟机内存和 Metal 显存互相踩踏导致 OOM：

B=max⁡(L−A−G−E−S,  352 MiB)B = \max(L - A - G - E - S,\; 352\text{ MiB}) B=max(L−A−G−E−S,352 MiB)

其中 GGG 为客体内存、EEE 为 CPU 译码缓存等客体侧宿主开销、AAA 为宿主 App 自身开销、SSS 为预留安全余量，最终为宿主机 GPU 划定显存池上限 BBB（最低保底 352 MiB）。在 darwin/runtime/guest_memory_budget.hpp 的注释里，作者甚至记录了真实设备测试数据：例如在 6 vCPU 手机上启动《Asphalt Legends》时，Gadget 缓存峰值会冲到约 240 MiB。因此默认设置会把初始 Guest 内存压在 4 GiB 以内并确保留给 GPU 至少 992 MiB～1 GiB 空间，同时 vCPU 数量默认且最多不超过宿主机物理核数与 8 核上限。

2. 退后台时的“四重防死工程”

当用户上滑切换应用、Andarium 或 Kernarium 退入后台时，底层会在短短几秒内依次触发四步精密操作：

  1. 关闭 GPU 请求门控（set_gpu_hold）与排空相机流：iOS 退后台后会立刻剥夺进程的 Metal GPU 访问权，一旦此时有残留的渲染指令打向 Metal，Vulkan 设备会永久进入 DEVICE_LOST 状态。因此退后台边缘会先通知相机停止录制（最多等待 2 秒），随即将 GPU Gate 设为关闭状态（总耗时控制在 3 秒内），让未送出的渲染帧安全留在虚拟环里。
  2. 内核同步与冷页缓存主动裁剪：通过管理控制台向 Linux 内核下发 sync(2) 落盘确认与 page_cache_trim 指令，先让 Guest 把冷文件页归还给宿主。
  3. 释放所有宿主机磁盘文件锁（flock）：这是极易踩中的暗坑——iOS 系统会直接终止在挂起期间仍持有宿主文件锁的进程。因此在物理 iOS 上，Kernarium 由自己的 platform/guest_files 注册表在内部维护全文件锁，一旦确认内核进入系统挂起（Suspend），立刻释放锁并在恢复时重新加锁，同时严格校验磁盘文件的 inode、大小、修改时间防止外部篡改。
  4. Mach 线程挂起与哈希分片休眠（guest_hibernation）：由于 iOS 真机上提交给客体的物理内存是 Wired（不可压缩、不可回收） 的，4 GiB 驻留内存退后台必死无疑。Kernarium 会利用 Mach 内核调用安全挂起所有 uml-* 与内核线程（且严格避开持有 malloc/libc 内部锁的线程，防止死锁），然后将已提交的物理页分块计算哈希写入应用临时目录（$TMPDIR 下的无链接临时文件），写完一块就立刻解除该块的物理内存占用；切回前台时再逐片校验哈希还原内存并唤醒 Linux 内核。

3. 零侵入的黑匣子：uml-stall-watch 与 19.2 KB 飞行记录仪

为了排查真机上的偶发卡顿与后台被杀原因，每个构建都内置了一个极轻量的 uml-stall-watch 线程——当所有 vCPU 都在空闲等待时它完全休眠、零耗电；一旦有载体跑出空闲态超过阈值，它便以 50 ms 周期只通过 libsystem_kernel 系统调用采样热降频状态、低电量模式、主线程响应和宿主等待点，把诊断指标原地覆写进一个定长 19,200 字节 的会话黑匣子（uml-session 8，划分了 8 KiB 内存历史槽、4 KiB 卡顿槽、网络槽、存储槽与相机诊断槽）。哪怕进程在后台被 Jetsam 悄无声息地杀掉，下次启动时只需读出这份文件上残留的 running 状态，就能精准还原被杀前最后一秒发生了什么。

六、实操边界与客观评价：它离日常主力还有多远？

把 Kernarium 与 Andarium 的工程全貌盘完后，我认为这是近年来苹果生态开源社区里技术密度最高、架构最纯粹的底层系统工程之一，但普通开发者与玩家在上手前也需要看清它的真实边界：

  1. 生态与合规红线：Andarium 从 App Store 上架又被 Guideline 2.5.2 & 1.1 下架的经历已经证明，在官方商店公开分发完整 Android 虚拟机依然存在极高政策风险；目前最稳妥的体验路径是通过 TestFlight 或导出签名 IPA 侧载安装，配合 Kernarium 测试通用 Linux 桌面（KDE / Phrog / postmarketOS）。
  2. 硬件与系统门槛极高：项目把部署基线锁定在 iOS 27.0+ 与 Metal 4（A14+），老旧设备无法跨越；而无 JIT 的 Gadget 解释器虽然过审且跑日常 Linux 命令行、Termux 与轻量 3D 游戏完全可行，但在纯软件解释模式下运行重度桌面应用或 Winlator 转译 PC 游戏时，依然受限于单核翻译吞吐（若想要极限性能，仍需配合 StikDebug 开启 JIT）。
  3. 自行构建门槛：如仓库 README.md 所提示，虽然在 macOS 上用 CMake + Xcode 就能编译 Darwin 运行时和 iOS App，但若想从头自行构建 LineageOS 24 / Android 17 系统镜像，仍需要一台强力的 x86_64 Linux 构建机；普通用户体验最省心的方式是直接拉取 Releases 里的预构建镜像与产物包。

但无论如何，Kernarium 用一套“原生 Linux 6.18 UML 内核 + 14,512 行纯数据 Gadget 解释器 + 逐页 SHA-256 AOT + Mesa KosmicKrisp 直驱 Metal 4 + Mach 分片休眠”的组合拳，把 iOS 沙盒虚拟化的工程天花板又向上捅穿了一大截。如果你也在研究跨内核虚拟化、无 JIT 执行引擎或苹果 Metal 图形桥接，这份仓库里的 docs/architecture.md、docs/graphics.md 和 docs/optimization-history.md 绝对值得你花一个周末细细精读。
