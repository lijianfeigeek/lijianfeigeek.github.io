把千万级地图瓦片装进单个静态文件：Protomaps PMTiles v3 的 Hilbert 索引、列式压缩与零后端 Range 架构深潜

2026-11-25 27 min read # PMTiles # GIS # 空间索引 # HTTP Range # 工程架构 # 开源剖析 # Serverless

在 Web 地图工程领域，瓦片分发长期被困在“两难选择”里：要么部署一套 PostGIS 加动态瓦片服务（如 Martin、Tegola）并持续维护容器扩缩容与缓存预热，要么把全球千万级瓦片切碎成海量 /{z}/{x}/{y}.mvt 静态小文件直接扔进对象存储，忍受动辄数天的上传耗时、高昂的 PUT 请求账单，以及无法原子切换版本的灾难。最近我拉取并精读了 protomaps/PMTiles 仓库的规范文档与多语言参考实现源码，发现它通过一份精悍的二进制归档规范，把整个地图瓦片基础设施压缩成了“单个静态文件 + HTTP Range 请求”。

PMTiles v3 的核心实现并不臃肿——规范文档 spec/v3/spec.md 仅 475 行，TypeScript 客户端、Python 读写与转换工具、C++17 单头文件解码库、OpenLayers 适配器与 Serverless 边缘代理加起来也不过四千余行代码。但正是这几千行代码，用 127 字节文件头、16 KiB 必达根目录契约、Hilbert 空间填充曲线聚类、列式 Varint 编码与基于引用计数取消的 SharedPromiseCache，彻底重构了云原生空间数据分发范式。这篇文章把它的二进制结构、算法细节与边缘网络实战工程拆透。

[!NOTE] 源码审计与实测基线声明
本文所有字节偏移、数据结构、协议字段与代码细节，均对照自 protomaps/PMTiles 仓库至 commit aec8fa1（2026-09-16，python pmtiles 3.8.1，js/pmtiles 4.5.0）。我在本地完整执行了 Python 单元测试（unittest 24 项用例全部通过）、C++17 头文件单测（g++ -std=c++17 -O2，8 组测试共 6,910 条断言全部通过），并直接用 MmapSource 解析检验了仓库 spec/v3/ 目录下自带的 3 个真实 .pmtiles 归档样本。JavaScript 包测试因当前环境未安装全局 tsx 与 node_modules 依赖，相关结论来自 TypeScript 源码与测试套件的静态逐行核验。

一、架构范式跃迁：为什么瓦片服务只需要单个静态文件

在 PMTiles 出现之前，离线打包格式里的事实标准是 Mapbox 的 MBTiles——本质上是一个包含 tiles 表与 metadata 表的 SQLite 数据库文件。MBTiles 在本地单机非常好用，但它有一个致命的云原生短板：SQLite 的 B-Tree 页面依赖随机读取与文件锁，无法直接通过 HTTP 在对象存储上按字节切片查询。要把 MBTiles 放到线上，面前就必须架一层应用服务器（Tile Server）去读盘、查表再吐出瓦片。

另一条路是把瓦片彻底解包成 /{z}/{x}/{y}.mvt 静态目录树直接丢进 S3 或 Cloudflare R2。这条路虽然省去了动态服务器，却制造了海量小文件噩梦：全球 Z0～Z15 级别瓦片动辄数千万甚至上亿个文件，不仅上传同步慢如蜗牛、覆盖更新极易造成“新旧瓦片混杂”的地图撕裂，还会在对象存储上产生惊人的按次请求费用。

PMTiles（推荐 MIME 类型为 application/vnd.pmtiles）的做法直接借鉴了栅格影像领域的 COG（Cloud Optimized GeoTIFF） 思想：把所有索引和瓦片二进制块紧凑拼装成单个 .pmtiles 文件，把原本位于服务端的路由与查询逻辑，下沉为客户端对静态文件的 HTTP/1.1 Byte Serving（Range: bytes=offset-end） 精确切片请求。

回顾仓库里的历史规范 spec/v2/spec.md 与现行 spec/v3/spec.md，我能清楚看到作者在协议演进上做的减法与取舍：

架构维度 PMTiles v2（已废弃） PMTiles v3（当前规范 v3.6） 工程收益解析
文件头尺寸 固定 512,000 字节（约 500 KiB 预留空间） 固定 127 字节 + 根目录（总计 <= 16,384 字节） 首包探测流量直接下降 96.8%，一次 16 KiB 请求即可完成冷启动

二、127 字节文件头与 16 KiB 必达契约：v3 二进制布局解剖

把 spec/v3/spec.md 和 js/src/index.ts、python/pmtiles/pmtiles/tile.py 对照着读，PMTiles v3 的文件布局克制得像教科书。整个归档文件由五大物理分段顺序构成（除 127 字节文件头必须位于字节 0 之外，其余分段理论上允许按偏移重排，但根目录必须落在前 16,384 字节内）：

1. 127 字节文件头的精确字节映射

前 127 个字节全部采用 小端序（Little-Endian） 编码，每一个字节都经过了严密对齐（具体定义见 spec/v3/spec.md 第 3 章与 cpp/pmtiles.hpp 第 55～177 行）：

  • 字节 0..6（7B）：固定 UTF-8 魔数 PMTiles（0x50 0x4D 0x54 0x69 0x6C 0x65 0x73），解码时先校验前两字节 0x4d50 或完整 7 字节；
  • 字节 7（1B）：版本号 0x03，所有实现遇到高于 3 的版本会直接拒绝解析并抛错；
  • 字节 8..95（11 × uint64，共 88B）：依次存放 Root Directory、JSON Metadata、Leaf Directories、Tile Data 四大区块的起始偏移量（Offset）与字节长度（Length），以及三大统计计数——Num of Addressed Tiles（RLE 展开前的逻辑总瓦片数）、Number of Tile Entries（目录条目数）、Number of Tile Contents（实际唯一 Blob 数据块数）；
  • 字节 96..99（4 × uint8）：状态与枚举字段，包括 Clustered（0x01 表示瓦片区严格按 TileID 连续排放且首条从 offset 0 开始）、Internal Compression（目录与元数据压缩算法）、Tile Compression（瓦片载荷压缩算法）以及 Tile Type；
    • 值得注意的是，Tile Type 除了常见的 MVT（0x01）、PNG（0x02）、JPEG（0x03）、WebP（0x04）、AVIF（0x05，v3.1 新增），在最新的规范 v3.5 中还正式加入了 0x06 MapLibre Vector Tile（.mlt）；而在 JSON 元数据规范 v3.6 中也正式定义了地形高程编码 encoding: "terrarium"（用 (red * 256 + green + blue / 256) - 32768 还原米级高程）。
  • 字节 100..126（27B）：MinZoom、MaxZoom、经纬度包围盒（MinLon、MinLat、MaxLon、MaxLat）、初始中心缩放与中心坐标（CenterZoom、CenterLon、CenterLat）。为了避免浮点序列化误差，所有经纬度均乘以 10,000,000（1e7）后存入有符号 32 位整型 int32（精度约 1.1 厘米，远超地图视口定位需求）。

2. 为什么是 16,384 字节？以及 writer.py 如何二分逼近目录分裂

规范里最精妙的工程约束之一，是第 4 章定下的死线：Header（127B）与压缩后的 Root Directory 总长度绝对不能超过 16,384 字节（16 KiB），即压缩后根目录最大 16,257 字节。

这样设计的意图非常直白：客户端在初始化一个陌生 .pmtiles URL 时，根本不需要先发一次 HEAD 或只读 127 字节再发第二次请求去读根目录——它直接乐观地发起 Range: bytes=0-16383。对于中小型数据集（或者全球低层级索引），这单独 1 个 16 KiB 的 HTTP RTT 就把 Header 和整棵索引树全部吞进了内存！

为了在本地印证这套机制，我直接用 Python 仓库的 MmapSource 与 Reader 解析了 spec/v3/ 目录下的 3 个官方真实归档文件，输出如下：

而当全球 Z0～Z15 数据集包含数千万张瓦片、单靠根目录塞不下 16,257 字节时，写入器（python/pmtiles/pmtiles/writer.py 的 optimize_directories() 与 cpp/pmtiles.hpp 的 make_root_leaves()）会启动一个极其干净的迭代探测算法：

# 源码摘自 python/pmtiles/pmtiles/writer.py (lines 43-53)
def optimize_directories(entries, target_root_len):
    test_bytes = serialize_directory(entries)
    if len(test_bytes) < target_root_len:
        return test_bytes, b"", 0

    leaf_size = 4096
    while True:
        root_bytes, leaves_bytes, num_leaves = build_roots_leaves(entries, leaf_size)
        if len(root_bytes) < target_root_len:
            return root_bytes, leaves_bytes, num_leaves
        leaf_size *= 2

当全量目录超过 16,257 字节时，写入器从 leaf_size = 4096 起步，每 4,096 条切分打包成一个独立 Gzip 压缩的叶子目录（Leaf Directory），只在根目录里留下指向每个叶子目录起始 TileID 且 run_length = 0 的指针条目；如果根目录还是超标，就把 leaf_size 翻倍（8192、16384……）重新试压，直到压缩后的根目录稳稳落入 16 KiB 首包窗口内。值得一提的是，规范 v3.3 明确强烈不建议嵌套多层叶子目录，客户端（js/src/index.ts:967、cpp/pmtiles.hpp:619、reader.py:49）在循环中都把最大检索深度死死限制在 depth <= 3，防止恶意构造的畸形文件触发无限网络跳转。

三、空间局部性与极限压缩：Hilbert 曲线、列式 Varint 与 RLE 游程去重

为什么 PMTiles 要费尽心思把二维瓦片坐标 (z, x, y) 映射成一维整数 TileID，又为什么不采用工程上最简单的 Z-Order（莫顿码，位交叉即可得出）而偏偏选择了数学上需要旋转翻转的 Hilbert 空间填充曲线？

1. Hilbert 曲线与 JS 26 级缩放精度边界

地图浏览有一个天然的访问特征：用户在地图上缩放或拖拽时，总是连续请求空间上彼此紧邻的一片瓦片网格。莫顿码虽然计算简单，但在象限边界处会出现剧烈的空间跳跃（例如从右下角突然跳到左上角）；而 Hilbert 曲线具有极强的连续性与局部保距性——二维平面上挨在一起的瓦片，映射到一维曲线上大概率也是连续编号的。

当写入器按照 TileID 升序把瓦片一块接一块写入 Tile Data 区（即 Clustered = true）时，相邻瓦片在物理文件里的字节偏移也是紧紧挨在一起的。这带来了两个直接的物理层红利：

  1. 对 RLE 极其友好：广袤海洋或大面积空白区在平面上是连续的，在 Hilbert 曲线上同样连成超长连续 TileID 片段，直接触发游程合并；
  2. CDN 与磁盘预取友好：边缘节点拉取大块缓存分片或内核 Page Cache 预读时，紧邻的几张瓦片往往顺带被预热进了同一段缓存块。

在阅读多语言实现时，我还发现了一个非常值得记录的跨语言数值精度边界差异：

  • 在 Python (tile.py:47) 与 C++ (pmtiles.hpp:420) 中，TileID 使用无符号 64 位整数（最大 6148914691236517204），因此理论支持到 z <= 31；
  • 但在 JavaScript/TypeScript (js/src/index.ts:78) 中，由于 JS Number 只有 53 位安全整数尾数（Number.MAX_SAFE_INTEGER = 9,007,199,254,740,991），为了不引入慢速 BigInt 拖垮高频位运算，代码中明确将最大缩放级别限制在 z <= 26（26 级时全球单边瓦片数已达 67,108,86467,108,86467,108,864，地面分辨率已达亚毫米级），并在 toNum(low, high) 和 tileIdToZ 中巧妙地用 32 位高/低位拼接和 Math.clz32 避开了 32 位按位运算溢出陷阱。

2. 为什么要按“列”序列化目录？

在 spec/v3/spec.md 第 4.2 节中，一个拥有 n 条记录的目录并不是按 [entry0, entry1, ...] 的结构体数组逐行写入的，而是拆成五个独立的连续字段数组（列式布局）：

  1. n（条目总数，Varint）；
  2. TileIDs[n]：存储相邻 TileID 的差值 entry[i].tileId - entry[i-1].tileId（Delta 编码）；
  3. RunLengths[n]：每个条目的连续覆盖瓦片数（0 代表叶子指针）；
  4. Lengths[n]：每个瓦片或叶子块压缩后的字节长度；
  5. Offsets[n]：如果当前块紧接在上一块之后（entry.offset == prev.offset + prev.length），直接写入 0；否则才写入 entry.offset + 1。

这种设计在经过 Gzip 压缩后威力极其惊人。对于一个正常排布的地图库而言，绝大多数瓦片的 RunLengths 都是 1，绝大多数 Offsets 都是 0（因为瓦片区紧密连续排放），绝大多数相邻 TileID 差值都是 1 或小整数！按列排布后，整个字节流里会出现大段大段重复的 0x01 0x01 0x01... 和 0x00 0x00 0x00...，LZ77 压缩算法只需极小的字典开销就能把上万条目录压进 16 KiB 之内。

与此同时，cpp/pmtiles.hpp 第 484 行在反序列化时还加了一道非常老辣的防内存爆炸安全校验：

// 源码摘自 cpp/pmtiles.hpp (lines 482-486)
// Sanity check to avoid excessive memory allocation attempt:
// each directory entry takes at least 4 bytes
if (num_entries_64bit / 4U > decompressed.size()) {
    throw malformed_directory_exception();
}

因为每条目录至少需要 4 个 Varint（至少 4 字节），如果解压后的缓冲区大小连 num_entries / 4 都不到，说明遭遇了伪造超大 num_entries 企图诱发 std::vector::resize 耗尽内存的畸形文件，直接拒绝分配并抛出 malformed_directory_exception。

3. 查找算法：带范围与叶子判定语义的二分搜索 findTile

无论在 JS、Python 还是 C++ 中，目录查找函数 findTile 的逻辑高度一致。它在已按 tileId 升序排列的 entries 上做标准二分查找：如果精确命中 entries[k].tileId == tileId，直接返回；如果循环结束仍未精确命中（此时 n 指向小于目标 tileId 的最大索引下标），代码会紧接着做两项额外判定（js/src/index.ts:274-281）：

  1. entries[n].runLength === 0：说明 entries[n] 是一个叶子目录指针，且它的起始 TileID 覆盖了直到下一条记录之前的所有编号，直接返回该叶子指针，进入下一层目录拉取；
  2. tileId - entries[n].tileId < entries[n].runLength：说明目标瓦片正落在这条 RLE 合并区间内（例如一个 runLength = 5000 的纯海洋瓦片条目），直接命中复用同一个 offset 和 length！

四、前端并发引擎与云存储边缘陷阱：FetchSource 与 SharedPromiseCache 源码深潜

协议层写得再漂亮，一旦把 .pmtiles 丢上公网 CDN、对象存储，再接进高频拖动缩放的 WebGL 地图前端，立刻就会撞上一连串浏览器缓存、CORS 预检和并发竞态的“脏活累活”。阅读 js/src/index.ts（第 339～1022 行）与 js/test/abort.test.ts，是我整趟源码审计里收获最意外的部分。

1. 为什么客户端和 Serverless 必须用两套不同的 Cache 实现？

打开 js/src/index.ts，你会发现里面同时提供了两个实现 Cache 接口的类：SharedPromiseCache（浏览器默认）和 ResolvedValueCache（Serverless 专用）。源码第 639 行的注释直接点破了玄机：

"Runtimes such as Cloudflare Workers cannot share promises between different requests."

在浏览器端，地图首屏加载会同时并发请求视口内的 12～24 张瓦片。如果缓存里只存“已完成的响应”，这 24 个并发调用在冷启动瞬间会同时击穿缓存，发出 24 次重复的 bytes=0-16383 首包请求！SharedPromiseCache 把 正在进行中的 Promise 直接存进 Map，让 24 个调用共享同一个在途网络请求，做到真正的 Request Coalescing（请求合并）。而在 Cloudflare Workers 这类无服务器边缘运行时中，跨请求共享一个未决 Promise 会触发运行时隔离报错（Cannot perform I/O on behalf of a different request），因此 Cloudflare Worker 和 AWS Lambda 适配器都显式换成了只在完成后才落入缓存的 ResolvedValueCache。

2. 引用计数级联取消（PendingFetch.refs）

更精细的控制发生在用户快速拖拽缩放地图时：MapLibre GL JS 会立刻触发旧视口瓦片的 AbortController.abort()。如果一个正在拉取中的 叶子目录 被 3 个并发瓦片请求共用，第 1 个瓦片移出视口被取消了，能直接把底层的 fetch() 掐断吗？绝对不能——另外 2 个瓦片还在等这个叶子目录！

SharedPromiseCache 在第 804～855 行实现了一套严谨的引用计数追踪器 trackSignal：

  • 每当有带 AbortSignal 的调用方搭上同一班在途 PendingFetch，pending.refs++；
  • 当某调用方触发 abort 事件时，执行 --pending.refs；只有当 pending.refs <= 0（所有等待者全部放弃）时，才会真正调用 pending.controller.abort() 切断底层 HTTP Range 请求，并将该 Key 从 cache 与 pendingFetches 中安全驱逐；
  • 如果先后任意一个调用方没有传入 signal（signal === undefined，见 abort.test.ts:315-370 测试用例），相当于直接把这条请求“钉住（Pin）”，其他带信号调用方无论怎么取消都不会中断底层请求。

3. FetchSource 源码里的四大浏览器与 CDN 实战坑

FetchSource.getBytes() 只有短短九十行代码，却几乎是一部血泪踩坑史的浓缩：

  1. 绝不发送 If-Match 请求头，改用响应 Etag 事后侦测 + EtagMismatch 自愈重试：如果在 Range 请求里带上 If-Match，不仅会导致浏览器每次请求瓦片都先发一次 CORS OPTIONS 预检请求、让延迟翻倍，还会直接导致 Chromium 彻底禁用该请求的本地缓存！PMTiles 的解法是：不发 If-Match，而是要求对象存储 CORS 暴露 ETag 响应头，每次收到 206 响应时比对内存缓存的 header.etag（同时忽略 W/ 开头的弱 ETag）。一旦发现 CDN 上的 .pmtiles 文件被覆盖替换（ETag 变更或偏移越界报 416），立即将 this.mustReload = true（强制下一轮 fetch 使用 cache: "reload" 绕过旧缓存），抛出 EtagMismatch，再由 PMTiles.getZxy() 外层 catch 捕获后调用 invalidate() 刷新 Header 与目录并自动重试一次！
  2. 低于 16 KiB 极小归档的 416 降级自救：如果一个测试归档总大小只有几 KB，首包请求 bytes=0-16383 在严格遵循 RFC 的服务器上会返回 416 Range Not Satisfiable。代码第 426～439 行会立刻解析响应头 Content-Range: bytes */<actualLength>，把 Range 收缩成 bytes=0-<actualLength-1> 重新拉取。
  3. 防“静默下载整包”的 200 熔断器：有些 CDN（源码注释点名了早期的 DigitalOcean CDN）对 Range 请求可能返回 200 OK 而非 206 Partial Content。但如果上游对象存储根本没开启 Byte Serving，它也会返回 200 OK 并把几十 GB 的整包文件往浏览器灌！FetchSource 在第 461～467 行做了硬性防御：只要收到 200，就检查 Content-Length——如果缺失或者大于请求的 length，立刻执行 controller.abort() 掐断 TCP 连接并抛错，避免把用户流量和浏览器内存打爆。
  4. Windows 版 Chromium 缓存腐败规避：源码第 368～373 行检测 User-Agent，只要同时满足 Windows 和 Chromium 内核浏览器（Chrome / Edge / Opera / Brave），强制将 cache 设为 "no-store"，绕开 Windows 下 Chromium 对同一 URL 不同字节范围请求共享磁盘缓存条目时偶发的静默数据错乱 Bug。

五、Serverless 边缘代理与全生态集成

虽然前端用 pmtiles:// 协议直连对象存储最省钱，但总有些场景需要暴露标准的 /{name}/{z}/{x}/{y}.mvt 与 /{name}.json（TileJSON）接口——例如兼容只认标准 XYZ 链接的旧版 GIS 客户端、桌面 QGIS，或者需要做 Token 鉴权与自定义缓存头控制。

PMTiles 仓库在 serverless/ 目录下给出了 Cloudflare Workers 和 AWS Lambda 两套生产级边缘代理实现，我把它们的关键设计差异对比如下：

对比维度 Cloudflare Workers (serverless/cloudflare/src/index.ts) AWS Lambda (serverless/aws/src/index.ts)
底层存储驱动 原生 env.BUCKET.get(key, { range: { offset, length }, onlyIf: { etagMatches } }) @aws-sdk/client-s3 GetObjectCommand，透传 Range、IfMatch 与 RequestPayer: "requester"（支持 Requester Pays 桶！）
本地目录缓存 ResolvedValueCache(25, undefined, nativeDecompress) ResolvedValueCache(undefined, undefined, nativeDecompress)（注：512MB 内存配置下空函数约占 70MB）
响应边缘缓存 调用 Cloudflare 原生 caches.default，并通过 ctx.waitUntil(cache.put(...)) 异步写入边缘节点 依赖 API Gateway / CloudFront 外层缓存，动态计算响应体 SHA-256 作为强 ETag
二进制压缩与编码 直接透传解压后的 ArrayBuffer，按类型设 application/x-protobuf、image/webp 等 专门应对 API Gateway 坑：由于 API Gateway 判断二进制响应过于依赖客户端 Accept 头，Lambda 主动用 zlib.gzipSync 重压一次并 Base64 返回（isBase64Encoded: true）
缺失瓦片状态码 越界缩放返回 404，范围内空白瓦片返回 204 No Content 越界缩放返回 404，范围内空白瓦片返回 204

而在客户端地图库适配与生态工具链方面，仓库其余目录同样各司其职：

  • MapLibre GL JS 兼容垫片（js/src/adapters.ts）：Protocol 类用了一个非常巧妙的 v3compat 高阶包装器——检测第二个参数是否为 AbortController 实例，自动同时兼容 MapLibre v4（基于 Promise + AbortController）与旧版 MapLibre v3（基于回调函数 + { cancel } 对象），还贴心地提供了 errorOnMissingTile 开关控制空矢量瓦片是返回空 Uint8Array 还是抛错触发超缩放（Overzooming）。
  • OpenLayers 双源封装（openlayers/src/index.ts）：PMTilesRasterSource 继承自 DataTileSource，加载完图像后立即 URL.revokeObjectURL(src) 防 Blob 内存泄漏；PMTilesVectorSource 继承自 VectorTileSource 并内置默认 512 瓦片尺寸与 MVT 格式解析。
  • 栅格重投影管线（python/rio-pmtiles/rio_pmtiles/worker.py）：基于 rasterio + mercantile 从 GeoTIFF/COG 生成 PMTiles 时，会根据当前目标层级智能挑选最接近的源影像 Overview 金字塔层级（OVERSAMPLING_FACTOR = 4），并在读取像素窗口前先用 src.read_masks(1, window=tile_window).any() 跳过全透明/无数据区域，大幅缩短遥感影像切片耗时。
  • 零依赖 C++17 单头文件（cpp/pmtiles.hpp）：仅 641 行，直接复用了 Mapbox protozero 的展开式快速路径 decode_varint_impl（单字节走内联快路径，多字节走分支展开路径），并通过 PMTILES_MSB 宏兼容大端序架构；同时支持把解码后的瓦片重排成 colmajor_cmp（TMS 列优先序）供上游工具消费。

在通读核心源码与规格定义的过程中，我也梳理出了 4 个在实际选型和二次开发前必须注意的工程局限与细节坑：

[!WARNING] 源码审计发现的 4 项技术边界与坑点

  1. Brotli 与 Zstd 压缩在默认运行时中尚未开箱即用：虽然 spec/v3/spec.md 第 3.3 节定义了 Gzip (0x02)、Brotli (0x03) 和 Zstd (0x04) 枚举，但我在 js/src/index.ts 的 defaultDecompress、Cloudflare Worker 的 nativeDecompress 以及 AWS Lambda 的 nativeDecompress 中看到的均只有 None/Unknown 与 Gzip 实现——遇到 Brotli 或 Zstd 归档会直接抛出 "Compression method not supported"，必须由调用方显式注入自定义 DecompressFunc；而 python/pmtiles/pmtiles/tile.py:152 的 deserialize_directory 更是直接写死了 gzip.decompress(buf)。生产制图若追求最高兼容性，内部与瓦片压缩仍应首选 Gzip（或对 WebP/AVIF 栅格瓦片设置 TileCompression = None）。
  2. JS 客户端的 z <= 26 硬天花板与 Python hash() 的进程内局限：前端 JS 因 53 位安全整数限制止步于 Z26，而 Python writer.py:102 在做内容去重时使用的是内置 hash(data)（在同一进程单次构建内是有效的，但若跨进程增量构建则因 Python 随机化 SipHash 盐值而不可比较）；同时 mbtiles_to_pmtiles 会先把全库所有瓦片 ID 列表读入内存排序，构建超大全球库时建议直接使用官方 Go CLI 工具 go-pmtiles 或 Tippecanoe 原生输出。
  3. 原地覆盖更新的 ETag 抖动窗口：PMTiles 是不可变单文件归档。如果你在生产环境用同一个文件名（如 planet.pmtiles）原地覆盖上传新版地图，正在浏览旧版地图的用户会在下一次目录或瓦片 Range 请求时撞上 EtagMismatch（触发 SharedPromiseCache.invalidate() 并自动重载整套索引）。更稳妥的生产实践是配合版本化文件名（例如 basemap-20261125.pmtiles）做不可变部署与长效 CDN 缓存。
  4. Web 浏览器直连强依赖正确的对象存储 CORS 配置：在 FetchSource 模式下，静态存储桶不仅需要允许 Range 请求头，还必须通过 Access-Control-Expose-Headers 显式暴露 ETag（以及 Content-Range、Content-Length），否则浏览器 JS 拿不到强 ETag、小文件 416 降级和 200 体积熔断都会失去关键上下文信号。

把所有代码过完一遍后，我愈发觉得 PMTiles 的设计哲学非常迷人：它没有发明任何晦涩难懂的密码学或复杂分布式协议，只是把空间填充曲线、列式编码和 HTTP 诞生二十多年的 Range 机制精准地拧在了一起。当别人在为瓦片集群、数据库索引膨胀和几千万个零碎对象的同步脚本焦头烂额时，它只用一个静态文件和一次 16 KiB 的首包预取，就把地图服务彻底变成了云原生世界里最安静的静态资产。
