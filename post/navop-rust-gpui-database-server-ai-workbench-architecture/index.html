把 15 种数据库、SSH/RDP 远程终端与 MCP 代理装进零 WebView 原生窗口：95 万行 Rust + GPUI 工作台 Navop 源码级架构全解

2026-11-26 28 min read # SSH终端 # 数据库客户端 # GPUI # 系统架构 # Rust # MCP

在日常后端研发与基础设施运维中，我的桌面常年被迫同时挂着四五个重型软件：用 DataGrip 或 Navicat 查表对比结构，用 Termius 或 Xshell 连跳板机敲命令传 SFTP，遇到 Windows 服务器切去 Microsoft Remote Desktop，写 SQL 或排查线上慢查询时又要把报错日志和表结构来回复制粘贴给终端里的 Claude Code 或 Codex。更糟的是，一旦其中两三个工具基于 Electron 或 JVM 构建，光闲置渲染进程就能吞掉数 GB 内存，而连接凭据、SSH 隧道与上下文更是散落在完全割裂的孤岛里。

最近我完整拉取并精读了开源项目 feigeCode/navop（由早期 OnetCli 演进重构而来）的全量源码。在 74 个 Workspace 成员、953,219 行 Rust 2024 代码的庞大体量下，它没有使用任何 WebView、Electron 或内嵌浏览器，而是直接基于 Zed 的 GPU 加速界面框架 GPUI，在单一原生进程内把 15+ 种数据库客户端、Redis/MongoDB、SSH/SFTP 终端、Windows 原生 RDP/VNC 远程桌面、双平面热插拔扩展以及面向外部 AI 代理的 Public MCP 服务彻底融为一体。这篇文章我将从源码实现出发，把它的五层原生合成栈、一仓三品编译级切分、零远端写入 Shell 状态机与连接级 AI 安全硬闸门逐层拆透。

  • Workspace 规模实测：根目录 Cargo.toml 共声明 74 个成员包（含 69 个 crates/* 内部包、3 个 apps/* 产品入口包与 2 个 tools/* 诊断探针包）；

一、五层零 WebView 原生底座：单进程 gpui-fast 如何同时驯服百万行表与原生 RDP？

很多宣称“高性能桌面端”的跨平台应用只是把 Node.js 后端换成了 Tauri（Rust），前端视图层依然塞在系统的 WKWebView 或 WebView2 里，一旦同时打开十几个分屏终端、滚动十万行宽表或嵌入远程桌面帧缓冲，DOM 布局重排与 IPC 序列化开销依然会迅速触顶。

翻开 Navop 的根目录 Cargo.toml（第 85～116 行与第 414～446 行），我看到了一条极其坚决的技术路线：从底层网络传输、终端状态机、SQL 解析器到顶层像素栅格化，100% 运行在同一个 Rust 2024 进程与唯一一份 GPU 渲染上下文之上。

在这张五层架构栈背后，有三个极易在大型 GPUI 工程中踩爆的深水区问题，Navop 给出了非常扎实的代码级解法：

1. 32 条 [patch.crates-io] 强收敛：全进程死守唯一一份 gpui-fast

熟悉 Zed 生态的开发者都知道，GPUI 目前迭代极快，社区衍生出了 gpui-component（现改名 gpui-kit）、gpui-pre 与独立发版的 gpui-fast。如果主程序、UI 组件库与脚本扩展宿主分别拉取了不同微版本的 GPUI，Cargo 会在同一个二进制里编译出两套互不兼容的 gpui::App 和 Window 类型，直接导致编译失败或双事件循环死锁。

Navop 在 Cargo.toml 底部通过 script/patch-local-gpui-pre.py 生成了整整 32 条 [patch.crates-io] 补丁映射，将 gpui-pre-*（提供 0.3.126 兼容转发 Shim）与 gpui-fast-* 全部强行锚定到自维护的 feigeCode/gpui-fast（release/v0.1.14 分支）。无论是内建的数据库表格、终端分屏，还是第三方扩展页面，在运行期共享的永远是同一个 GPU 纹理图集与帧调度器。同时在 [profile.release] 中开启了 lto = "fat"、codegen-units = 1、strip = true 与 panic = "abort"，仅关闭栈展开一项就直接省掉了约 27 MB 的 __eh_frame / __gcc_except_tab 二进制元数据。

2. 攻克 Windows 原生 RDP 的“浮层吞菜单（Airspace）”顽疾

在桌面客户端里内嵌远程桌面，最难啃的骨头莫过于 Windows 原生 RDP ActiveX 控件。普通做法是创建一个 Win32 子窗口（HWND）叠在主窗口客户区上方，但这会立刻引爆经典的 Airspace（空域遮挡）灾难：原生子窗口永远浮在自绘 GPU 画布最顶层，导致标签页右键菜单、顶部下拉弹窗、侧边抽屉全部被远端桌面画面“吃掉”。

我在 docs/gpui-pre-airspace-surface-forwarding.md 与 crates/windows_rdp_host 中读到了作者对 GPUI 底层渲染器做的三处精妙手术：

  1. DirectComposition 视觉树挂载修复：在 gpui/src/window.rs 的 ManagedPlatformSurface 装饰器中补齐了上游遗漏的 4 行 set_window_content 转发，将原生 RDP 子窗口通过 CreateSurfaceFromHwnd 变成 DirectComposition 树中的一个普通节点，并通过 place_below(id, overlay_surface) 压在 GPUI 的浮层表面之下。
  2. 绕开 IDCompositionVisual3 接口缺失陷阱：GPUI 在 Windows 上默认通过 v1 版的 DCompositionCreateDevice 创建合成设备，其视觉对象仅实现 IDCompositionVisual。上游原本在 set_visible 中强转 cast::<IDCompositionVisual3>()?.SetOpacity2(...)，每次隐藏都会必现 0x80004002（E_NOINTERFACE），进而被上层误判为合成表面损坏而退回普通子窗口。Navop 在 fork 中改用绑定/解绑表面内容（visual.SetContent(None)）来表达不可见态，彻底消灭了 v1 设备的 COM 接口报错。
  3. 基于 deferred_draws 的帧级动态让位与断线保帧：在 Window 结构体新增 has_deferred_content()，每帧在 prepaint_deferred_draws 之后检测当前是否存在弹窗、右键菜单或 Prompt，动态通知原生表面让位；同时在 RDP 发生网络闪断自动重连期间（ConnectionFailure -> Reconnecting），强制保留最后一帧已渲染画面而不替换为文本覆盖层，配合 TabContainer 每一层的 .min_w_0().min_h_0().overflow_hidden() 截断固有尺寸冒泡，彻底根治了重连瞬间窗口标题栏最小化/关闭按钮被挤压跳变的顽疾。

3. 双异步运行时铁律：严禁 GPUI 后台线程裸跑 Tokio 套接字

GPUI 自带一套确定性的前景与后台执行器（cx.spawn / cx.background_spawn），但绝大多数 Rust 数据库驱动（tokio-postgres、mysql_async、tiberius）与 russh 都强依赖 Tokio Reactor（I/O 驱动与定时器）。

在早期版本中，一旦视图层图省事直接把 SQL 导出或首页 SSH 资源采集包进 cx.background_spawn，代码跑到 tokio::time::timeout 时就会立即抛出 there is no reactor running Panic；在 macOS 上，这个跨过 extern "C" 渲染回调边界的 Panic 会直接转化成整个应用瞬间闪退（SIGABRT）。为此，Navop 在 AGENTS.md 与 crates/db/src/manager.rs 中确立了硬性隔离边界：凡涉及 Socket、Timer 或外部进程的异步任务，一律由状态管理层经 one_core::gpui_tokio::Tokio::spawn_result 投递到全局 Tokio Runtime，并在核心私有方法入口用 tokio::runtime::Handle::try_current() 做防御性断言，UI 视图层只允许订阅进度 Channel 更新状态。

二、一仓三品的编译级手术：为什么抛弃 Feature 软开关，改走 domain_api 纵向切分？

作为一个覆盖“数据库 + 服务器运维 + AI”的全能工作台，全量版 Navop 功能极全，但也有不少纯粹的 DBA 只想要轻量干净的 SQL/Redis 客户端，或者纯系统运维只需要 SSH/SFTP/RDP 终端。因此，同一份源码需要同时构建出三个独立发行产品：Navop（全量版）、Navop Shell（终端运维版）与 Navop Data（数据工程版）。

直觉上最容易想到的方案是在 Cargo.toml 里加两个 #[cfg(feature = "database")] 和 #[cfg(feature = "shell")]。但我在 docs/design/navop-product-split.md 中看到了一组非常残酷的实测对比数据：如果只在顶层外壳把依赖改成 optional = true，Navop Shell 依然会编译 51 个 Crate（占全量代码的 96.3%，仅仅缩减了 3.7%）！

为什么单纯加 Feature 开关几乎完全失效？根因有两条：

  1. Cargo Workspace 的特性并集传染（Feature Unification）：在同一个 Workspace 内执行构建或检查时，Cargo 会对共享依赖包的 Feature 求并集，包级条件编译很难保证某个二进制的编译图里彻底不含异域代码；
  2. 跨层隐式硬依赖穿透：在旧架构中，terminal_view 依赖 workspace_explorer，后者依赖 remote_file_editor，再往下引用了 extension-runtime——而 extension-runtime 与 navop_runtime 当时非可选地硬编码依赖了 db、db-value 和 db_view！只要编译一个终端窗口，顺藤摸瓜就会把二十万行的数据库引擎与 SQL 编辑器整包拖进二进制。

为了实现真正的编译图级物理隔离，Navop 作者没有做肤浅的 UI 隐藏，而是动了一次彻底的控制反转外科手术：

  1. 先拆底座耦合：把工具运行时拆成零域依赖的 runtime_core 以及按域隔离的 runtime_database、runtime_redis、runtime_sftp；把扩展宿主对数据库的硬引用剥离为可选网关；
  2. 抽象唯一契约层 crates/domain_api：这个包只有几十行纯粹的 Trait 与值类型（不依赖任何 db* 或 terminal*），定义了领域向外壳注册能力的全部接缝——Domain、ConnectionOpener、ConnectionFormProvider、TabOpener、SettingsSectionProvider 与 RuntimeMcpProviders；
  3. 纵向领域切片 + 45 行薄入口装配：新建 crates/shell_domain 与 crates/data_domain 各自实现 domain_api::Domain，再由 apps/ 下的三个薄二进制包通过 Cargo 依赖边决定链接谁。

打开 apps/navop-shell/src/main.rs，整个独立产品的入口干净到只有 45 行：

// apps/navop-shell/src/main.rs
use std::sync::Arc;
use domain_api::{AppIdentity, Domain, Product, ProductFeatures};

struct ShellProduct;

impl Product for ShellProduct {
    type Assets = navop_app::AppAssets;

    fn identity(&self) -> &'static AppIdentity {
        &AppIdentity::SHELL // 独立数据目录 navop-shell 与钥匙串 com.navop.desktop.shell
    }

    fn features(&self) -> ProductFeatures {
        ProductFeatures::SHELL
    }

    fn assets(&self) -> Self::Assets {
        navop_app::AppAssets::new()
    }

    fn domains(&self) -> Vec<Arc<dyn Domain>> {
        vec![Arc::new(shell_domain::ShellDomain)] // 编译图完全不含 data_domain / db_view
    }

    fn mcp_managed_by_app_kit(&self) -> bool {
        true
    }

    fn init(&self, cx: &mut gpui::App) -> anyhow::Result<()> {
        navop_app::init_app(cx)
    }
}

fn main() {
    navop_app::run_with(ShellProduct, env!("CARGO_PKG_VERSION"));
}

经过这轮解耦，Navop Shell 的编译闭包直接从 778K 行骤降至 559K 行（净砍 30.8%），符号表里连半个 db_view 的影子都不会出现；同时三个产品拥有各自独立的配置目录、SQLite 库与系统钥匙串命名空间（避免多产品并存时发生 Schema 版本倒挂或锁竞争），而全量版 Navop 则刻意保留了历史 macOS Bundle ID com.onetcli.app，确保老用户升级时钥匙串授权与自动更新零感知平滑过渡。

三、双平面扩展架构：异构驱动能力平面与 nsh 脚本化 UI 平面的正交分野

市面上支持二十多种数据源的数据库工具（如 DBeaver）之所以重，是因为依赖整套 JDBC 虚拟机生态。在纯原生 Rust 体系下，如何既保留高频数据库的极致性能，又支持达梦（DM）、人大金仓（KingbaseES）、南大通用（GBase 8a/8s）、OceanBase、openGauss、TDengine、Apache IoTDB 等庞杂的信创与专有生态，甚至还能免重启热装 Docker、Kafka、Kubernetes、RocketMQ 管理面板？

阅读 crates/db/src/ipc/registry.rs、crates/extension-api 与 docs/extension-resource-plugins/nsh-migration-plan.md 后，我发现 Navop 将扩展机制清晰地劈成了 能力平面（Capability Plane）与 UI 平面（UI Plane）两条正交轨道：

扩展维度 核心宿主模块 运行时载体与隔离机制 覆盖场景与典型生态
内建高速驱动 crates/db/{mysql,postgresql,sqlite,duckdb,mssql,oracle} 编译进主二进制或可选内嵌，零序列化损耗 MySQL、MariaDB、PostgreSQL、SQLite、DuckDB、SQL Server、Oracle
IPC 进程外驱动 crates/db/src/ipc/registry.rs (IpcDriverRegistry) 独立子进程 + 本地 Socket（默认 5000ms 超时），由 driver.json 声明 SQL 方言与分页语法 达梦 DM、金仓 KingbaseES、GBase、OceanBase、openGauss、ClickHouse、TDengine、IoTDB
WASM 组件扩展 crates/extension-wasm + crates/extension-api/wit 基于 WebAssembly Component Model（WIT 契约），严格按 ExtensionKind 惰性编译 语法高亮（Tree-sitter 语言包）、跨平台轻量级连接器与渲染扩展
长驻资源服务 crates/extension-plugin-adapter (ActivationManager) 引用计数租约（Lease）共享单一 ProcessRpcSession，RuntimeMonitor 健康轮询自愈 Docker、Kubernetes、Kafka、RocketMQ、Nacos、MQTT 后台资源采集与事件流
脚本化 UI 平面 nsh-platform-gpui (AppView + HostChannel) 每标签页独立 QuickJS 引擎线程渲染 TSX 组件树，回推同一 gpui-fast 渲染管线 31+ 个复杂中间件运维工作台、自定义工具箱与 AI 动态生成界面

这里有两个极值得借鉴的架构取舍：

1. 为什么在 UI 扩展上“反转方向”，把 Navop 做成标准 nsh 宿主？

在早期版本中，Navop 曾自研了一套 gpui-shell JS Builder 链式 API（形如 v_flex().child(h_flex().child(...))），并基于 extension.json 手写了一套权限与引擎版本门禁。但写完 31 个扩展页面后，作者发现链式 Builder 只要嵌套超过 4 层就彻底失去可读性，导致做出来的扩展页面全是单调的“平铺列表 + 徽章 + 按钮”；而且主线程栈上的 17 处 with_current_app 不变量极易引发重入崩溃。

于是在 2026-10-30 的 v2 重构方案中，作者果断推翻了“把外部引擎塞进自家扩展格式”的思路，反向将 Navop 改造成 nsh（基于 QuickJS + GPUI 原生组件集的 TSX 应用框架）的标准宿主：

  • UI 表现力跃迁与线程解耦：扩展开发者直接用熟悉的 TSX 与 Tailwind 风格编写界面，底层映射到 nsh/base 的 71+ 个原生 GPU 组件（含百万行虚拟化 DataTable、LSP 编辑器、DiffView、DockArea 与图表库）。每个 NshTab（Entity<AppView>）运行在独立的 engine 线程上，关闭标签页时 view.stop() 被后台化丢进 background_executor 异步回收，绝不卡顿主界面。
  • 四类类型化宿主桥接（HostChannel）：抛弃丑陋的 Base64 错误信封，将宿主能力收敛为 host.call("navop.resource.invoke", ...)（受 capabilities.host 函数名白名单与配额约束，连接断开自动 drop-reject 取消在途 Promise）、nativeModule（工作台状态流）、nativeComponent（嵌入 navop.terminal 等真原生控件）以及 set_theme / set_locale 主动推送。
  • Ed25519 信任链与双层能力收敛：借助 nsh 的 .nshpkg 签名包与 TrustStore，原生获得证书签发、列表撤销、两阶段健康装载（首帧渲染无 Fatal 后才调用 accept_package 记录单调递增的 build 号，天然阻断降级回滚攻击），以及 declared ∩ granted 双层能力交集（默认全拒，未知能力自动丢弃）。

2. 惰性加载防卡死：卸载一个数据库驱动为什么曾让界面假死？

在 AGENTS.md 第 414 行记录了一次非常真实的踩坑：早期每当用户在扩展管理器里安装、重载或卸载一个普通数据库驱动时，统一刷新函数都会无差别调用 load_language_extensions_from_root——导致 GPUI 主线程同步读取并用 Cranelift / Wasmtime 重新编译全部 Tree-sitter 语言 WASM 包，界面直接卡死数秒！修复后的架构严格按 ExtensionKind 分流刷新：只有 Language 与 LanguageBundle 才更新 Manifest 后缀映射（且语法分析器延迟到首次打开对应后缀文件时惰性编译），其余扩展仅刷新轻量级的 ExtensionRuntimeCatalog。

四、服务器与堡垒机深水区：零落盘 PTY 注入、ExecSupervisor 与 JumpServer 突围

如果只看 README 截图，很容易以为 SSH 终端不过是调一下 russh 把字节塞进 alacritty_terminal。但真正把终端放到金融生产机、华为老旧交换机、JumpServer 堡垒机以及 AI 自动排障混合场景里跑一圈，处处都是暗礁。我把 crates/terminal 与 crates/ssh 中最硬核的三套机制浓缩成了下面这张状态机图谱：

1. 远端零文件写入（Zero Remote Writes）的运行时 Shell 注入

为了让终端支持工作目录跟随（OSC 7）、命令起止定位与退出码捕获（OSC 133），传统工具（包括早期版本）会在每次 SSH 登录时通过 exec 通道往目标服务器偷偷写入 ~/.config/.../shell_integration.sh 并修改用户的 .bashrc / .zshrc。在政企生产环境或客户交付现场，未经许可篡改服务器磁盘文件不仅严重违反安全合规审计，一旦 awk 脚本异常还会把用户的登录环境搞坏。

在 docs/design/ssh-runtime-shell-integration.md 中，Navop 彻底砍掉了所有远端落盘逻辑，改用一套精巧绝伦的纯内存 PTY 握手状态机（RuntimeShellIntegration）：

  1. 只读探针与单会话防火墙兼容（Issue #183）：先开一条 1 秒超时的只读 exec 通道探测 $SHELL 是否为 bash 或 zsh（自动跳过不支持 eval $'...' 的 ash / dash / fish）。更细节的是，像华为 USG 防火墙这类嵌入式设备只允许单个 SSH 会话，探测通道会直接触发设备返回 SSH_MSG_DISCONNECT 掐死整条连接！Navop 探测返回后会立刻校验 client.is_connected()，一旦发现传输层被设备掐断，立即自动作废当前连接并以 plain_channel_only 单通道无探测模式静默重连。此外，针对华为 VRP 等老设备在 ssh-rsa 主机密钥里发送冗余前导 0x00 或缺失正负符号位导致的 RFC 4251 mpint 解析报错，作者甚至专门维护了 feigeCode/SSH（ssh-encoding/v0.3.0-navop.3）容错补丁。
  2. 短探针防拆行 + 64KB 回显抑制 + 历史无痕清理：首段输出往往只是 PAM 登录 Banner，此时 PTY 尚未进入行编辑态，直接灌入 6KB 脚本会被截断成多行乱码。因此状态机先进入 Bootstrapping 发送几十字节探针，同时把用户此时的敲击全部收进 deferred 队列防丢字；收到探针回执后进入 Injecting，通过 ANSI-C 引号单行化发送 " : __ONETCLI_RUNTIME_SETUP_1; eval $'...'\r"，并将回显拦截在上限 64KB 的抑制缓冲中，直到捕获 OSC 1337;ShellIntegrationReady=1 才放行输出并重放用户按键。
    • Zsh / Bash 历史防污染细节（Issue #547）：Zsh 的历史数组只读，必须在 Bootstrap 短探针阶段就提前挂载 zshaddhistory 钩子拦下随后的 6KB 注入大行；Bash 则在脚本末尾用 history -d 按 sort -rn 倒序删除（升序删除会导致后续条目重编号而漏删），且匹配时避开双引号 $() 内的 case 右括号解析 Bug。
    • 子 Shell 继承防报错（Issue #217）：注册到 PROMPT_COMMAND 时先用 __ONETCLI_EXIT=$? 锁住真实退出码，再通过内建命令 command -v __onetcli_precmd_bash >/dev/null 2>&1 判断函数存在性，避免用户在远端执行 su 或嵌套 tmux 后满屏刷出“未找到命令”。
    • 双重超时看门狗（Issue #206）：单步注入设 5 秒超时，外层 Actor 再挂一道 30 秒握手看门狗，一旦远端彻底沉默，立即调用 force_release_input() 强制降级为 Plain 裸终端并重放积压按键，绝不出现“画面正常但键盘敲不进字”的幽灵锁死。

2. 可见终端的 AI 执行铁律：为什么绝不用 EOF 判定命令结束，也绝不在取消时乱发 Ctrl+C？

很多 AI 终端助手在用户的可见终端里跑一条 npm run dev & 或 nohup ./server & 就会永远卡在“运行中”，如果用户顺手点了一下 AI 对话框的“取消（×）”按钮，AI 又会鲁莽地往终端灌入一个 Ctrl+C（0x03），直接把用户正在跑的业务进程杀掉！

在 crates/terminal/src/exec_supervisor/ 中，Navop 用 ExecSupervisor 立下了三条干净利落的工程边界：

  • 以 Prompt Epoch 收口而非 EOF：后台子进程会继承 PTY 文件描述符导致永无 EOF，ExecSupervisor 完全依据 OSC 133 的 CommandFinished（133;D）或新提示符纪元（prompt_epoch 递增）判定完成，采集缓冲硬限 1 MB（TERMINAL_EXEC_CAPTURE_LIMIT_BYTES）。
  • 空提示符零 Ctrl+C 提交与非破坏性取消：当提示符处于干净的 Ready 态时直接提交命令；只有观测到用户留有未提交的半行输入时，才发一次 ETX 清理并等待新 InputStart。若用户在命令运行中途取消 AI 回合，系统只解除（detach）AI 侧的结果等待器并发出 TurnCancelled，绝不向终端发送任何控制字符；只有 AI 显式调用高风险独立工具 terminal.control(action=interrupt) 并通过状态原子校验处于 CommandRunning 时，才允许写入一次 0x03。
  • 嵌套 sudo -i 拒绝二次脚本重注入：当用户切入 sudo -i 子 Shell 丢失 OSC 133 钩子时，Navop 彻底删除了旧版重注入 4KB 脚本的 reintegrate 路径（防止整段脚本源码直接裸露打印在用户屏幕上），自动引导 AI 降级改用单行直写的 terminal.write_command 配合只读滚屏尾部采样的 terminal.read(lines=N)。

3. 企业堡垒机突围：BastionDirect 直连与 jms:// 免落盘拉起

针对国内企业广泛部署的 JumpServer（Koko） 堡垒机默认禁用 direct-tcpip 端口转发、导致传统 ProxyJump 直接报 AdministrativelyProhibited 黑盒错误的问题，Navop 在 v0.24.0 做了全链路重构：不仅从 russh 的 channel_open_failure 钩子中捞出服务端真实的拒绝描述提示用户，还原生内置了一等公民的 BastionDirect（堡垒机直连）模式——按 user#account#asset 模板直连堡垒机代理终端、SFTP 与命令执行，补齐了跳板机 SFTP 全链路的 MFA / TOTP 多轮交互认证，并完成了三端操作系统的 jms:// 深链接注册：在浏览器点击 JumpServer 资产“连接”即可秒级唤起 Navop，一次性连接 Token 仅驻留本次会话内存，绝不落库、绝不写日志。

五、把工作台安全开放给外部 AI：连接级三层硬闸门与 Loopback Public MCP

除了内置支持 /chat/completions 与 /responses 双协议（兼容无 Key 的本地 LM Studio / llama.cpp 网关以及 Claude Code、Codex、OpenCode 等 ACP 代理）的 AI 工作台外，Navop 最具想象力的设计在于 crates/public_mcp——它把整个桌面工作台变成了一台受控的本机 MCP Server，让外部 AI 客户端经由 @navop/mcp 桥接器直接调用宿主已建立的数据库连接、Redis 会话与 SSH 终端。

但这也立刻引出了所有工程师最担心的安全命题：我用 Navop 同时管着开发库和核心生产库，万一 AI 在排查问题时自作聪明，顺着 connections.open_session 或 ssh.exec 连上生产机执行了写操作怎么办？

1. 随云同步流转的连接级三层拦截闸门（StoredConnection::ai_access_level）

在 docs/design/connection-ai-access-policy.md 中，作者否决了“建一张本地独立权限表”的偷懒方案——因为一旦换一台电脑同步下来，本地权限丢失就会退回默认放行，造成“家里电脑禁写生产、公司电脑 AI 却能删库”的致命漏洞。

因此，ai_access_level（Allowed / ReadOnly / Denied）被直接定义为 StoredConnection 模型的一等字段，随云端加密同步与 v3 迁移包（Argon2id + AES-256-GCM）跨端携带，且反序列化遇到未知字符串时严格按 Denied（Fail-Closed） 处理。在运行时，它构建了三道滴水不漏的防线：

  1. 第一层（可见性剥离）：在 resource_pool.rs 与 @ 引用构建器中，Denied 连接及其派生的活动终端/Redis 会话直接从 AI 资源池中抹除，connections.list/find 对其完全隐身；ReadOnly 连接则被削掉 TerminalExec、TerminalInput 等写能力标签。
  2. 第二层（路由阻断）：ToolRuntimeMcpProvider 归一化目标参数时，不在池内的目标直接以 TargetNotInPool 短路失败，拿不到任何底层会话句柄。
  3. 第三层（ToolAccessGuard 终局硬闸门）：直接挂载在 ToolRegistry::call 执行入口（包含合并后的主注册表及内置 AI 的 database / redis / sftp 全部 4 个挂载点），无论请求来自外部 MCP 还是内部对话，都会把传入的数字 ID、连接名称或 session_id 反查回 connection_id——命中 Denied 立即熔断拦截，命中 ReadOnly 则仅放行 ToolAnnotations.read_only == true 的纯查询工具。

2. Loopback 发现隔离、工具名净化与二次审批边界

翻阅 crates/public_mcp/src/discovery.rs 与 AGENTS.md，还能看到三处经过真实线上事故锤炼的细节：

  • 回环强校验与开发态防劫持：DiscoveryDocument::validate_for_stdio_bridge 强制要求监听地址满足 addr.ip().is_loopback() 并核验 64 位十六进制随机令牌；同时通过 OnceLock 注入 DISCOVERY_PATH_OVERRIDE，将正式版、.navop-dev 开发版与 .portable 便携版的 public-mcp.json 彻底物理隔离——彻底根治了 2026-10-28 曾发生的“本机调试启动开发版实例意外覆盖正式版发现文件、劫持外部 MCP 客户端流量”的隐患。
  • 跨模型工具名双向净化（ToolNameAllocator）：Navop 内部工具 ID 采用点分命名（如 ssh.command.poll），Claude 能正常识别，但 Grok 等严格校验 [A-Za-z0-9_-] 正则的客户端会在注册函数阶段把带点工具整批静默丢弃（导致工具列表变为 0）。PublicMcpToolRegistry 在对外出口统一按内部 ID 排序后做确定性下划线净化，使 ACP 与 MCP 两侧工具名 100% 一致，且 tools/call 同时兼容净化名与原始点分 ID。
  • 权限档位与双边界透明化：支持 Safe（只读）、Confirm（非读操作强制弹出全局桌面安全确认 Dialog）与 Auto（自主放行）三档；当通过 ACP 接入外部代理处于手动确认模式时，权限卡片会显式告知用户“允许 ACP 请求后，实际触碰底层资源仍将弹出一次桌面安全确认弹窗”，消除了双重安全边界带来的交互困惑。

# 1. 克隆仓库并按需编译三款独立产品（需安装 Rust 2024 工具链与 CMake）
git clone https://github.com/feigeCode/navop.git
cd navop

# Linux 环境可先执行一键系统依赖引导（macOS 具备 Xcode CLT 即可直接构建）
# ./script/bootstrap

# 按需运行全量版 / 纯终端运维版 / 纯数据工程版
cargo run -p navop
cargo run -p navop-shell
cargo run -p navop-data

# 2. 接入 Navop CLI 与 Agent Skill（需先在应用「设置 > 通用 > MCP」开启 MCP Server）
npm install -g @navop/cli@latest
navop skill install --target codex --scope user

# 原生 MCP 客户端（如 Claude Desktop / Claude Code）可直接挂载 stdio 桥接：
# npx -y @navop/mcp@latest
