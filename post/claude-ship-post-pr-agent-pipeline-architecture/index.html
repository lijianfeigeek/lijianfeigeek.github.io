当代码产出暴增 12 倍之后：深度拆解 Anthropic Claude Ship 的三代理 PR 闭环、声明式策略门禁与安全边界

2026-11-25 23 min read # Claude Ship # 工程架构 # Code Review # Anthropic # DevOps # AI Agent # Claude Code

当 AI 编程代理开始接管大部分代码编写工作，软件工程的真正瓶颈就已经不再是“写代码的速度”，而是 Pull Request（PR）打开之后的漫长泥潭：CI 报错、评审意见来回拉锯、主干合入引发合并冲突、以及苦等资深工程师抽出时间点下那个 Approve 按钮。2026 年 11 月 23 日，Anthropic 正式发布了 Claude Ship（同步在 Claude Code 中推出 /ship 与 /steward 命令），试图把 PR 开启之后“审查—修复—审批”整条后半程流水线，重构为一套受控的代理协同系统。

为了看清这套系统的真实工程底座而非仅仅停留在产品新闻稿表面，我通读了 Anthropic 官方发布的 Claude Ship 公告、全部技术文档（包括策略语法参考、自定义分类器规范、沙盒权限与安全边界说明），以及 Claude Code 团队内部工程复盘与 Addy Osmani 撰写的实战指南。拆解完它的底层设计后，我发现 Claude Ship 真正值得研究的并不是“AI 也能点 Approve 了”，而是 Anthropic 在内部日均合并量从 2,500 暴增至 30,000+ 之后，摸索出来的一套收敛熔断机制、声明式风险分层策略（.claude/approvals.yml）以及不对称权限隔离架构。

[!NOTE] 资料核验与技术基线说明
本文所有架构细节、YAML 策略语法、CLI 命令行为、工程指标与计费/安全边界，均核验自 Anthropic 于 2026 年 10 月至 11 月发布的官方一手文档与工程博客，包括 Introducing Claude Ship（2026-11-23）、Claude Ship 官方技术文档（含 approvals-policy、pr-steward-security 与 ship-command 规范）、How the Claude Code team does code review 以及 Addy Osmani 的实战长文 A practical guide to shipping with Claude Code（2026-11-24）。文中不涉及任何未经实证的外部猜测。

一、为什么 Anthropic 要重造 “Post-PR” 流水线？

在人类逐行手写代码的年代，“是不是由人读过每一行 Diff”勉强算是一个有效的质量代理指标。但 Anthropic 公开的一组内部工程数据直接击穿了这个前提：在 Claude Code 内部，Claude 已经承担了约 90% 的代码编写；而在 Anthropic 的 Monorepo 中，每日落地合入的变更数量从 2026 年 5 月的约 2,500 次飙升到了 9 月的超过 30,000 次——整整 12 倍的吞吐量跃迁。

在这种量级下，要求人类工程师像过去一样逐行盯防每一个 PR 已经彻底失效。Anthropic 在工程博客里提出了一个非常犀利的观点：把评审问题从“有没有人读过这段代码”转化为“这次变更可能出什么错，哪一种检查（自动化或人类）最适合捕获它”。如果只是机械地把资深工程师从深度设计工作中拽出来抓低级逻辑漏洞，实际上是在浪费整个工程组织最稀缺的资源——人类的注意力与时间。

更微妙的是，人类时间的成本其实包含两半：评审耗时 + 修复线上故障耗时。如果盲目削减前者导致后者反弹，总体时间账单不仅没省下来，反而会恶性膨胀。因此，Claude Code 团队为内部演进设定了一条非常克制的北极星指标：绝大多数 PR 在不增加回滚率（Revert Rate）和线上事故率的前提下，最多只需要 1 名人类参与闭环（甚至可以是发起该变更的作者本人）。

数据验证了这套思路的有效性：6 月至 9 月期间，Claude Code 代码库每月合入的 PR 数量翻了一倍以上，而最终需要回滚的变更比例反而下降了超过 40%。Claude Ship 正是把这套内部跑通的 Post-PR 工程底座产品化之后的结果。

二、三代理协同架构：Review、Steward 与 Approvals 的职责切分

很多开发者第一眼看到 Claude Ship，容易把它误解成一个“大而全的全自动合并机器人”。但只要把它的官方文档拆开看，就会发现 Anthropic 刻意将后 PR 阶段拆成了三个职责正交、权限严格分离的独立代理，再配合本地终端的 /ship 与 /steward 命令形成双端联动：

组件名称 当前阶段 运行位置与身份 核心职责与设计红线
Code Review GA（正式可用） Anthropic 云端（claude[bot]） 结合完整代码库上下文进行多视角深度审查，经过代理间对抗投票过滤后以行内评论输出；分 Quick / Standard / Deep 三档
PR Steward Public Beta Anthropic 云端（claude[bot]） 盯守 CI 失败、合并冲突与人类/机器人评审评论并自动推 Fix Commit；硬性禁止批准（Approve）或合并（Merge）PR
Claude Approvals Public Beta Anthropic 云端状态检查（Check） 解析默认分支的 .claude/approvals.yml 与自定义分类器，裁决仍需多少人类席位；低风险场景下可由 claude[bot] 或 claude-approvals[bot] 自动批准
/ship & /steward 已随 CLI 推送 开发者本地终端 & 桌面端 无需等待管理员开通组织级服务即可单兵试用；以开发者个人身份与 GitHub 凭据运行，最长可持续盯守 PR 达 7 天

1. Code Review：从“高噪音挑刺”到“对抗投票去噪”

Code Review 早在 10 月中旬就已经 GA（正式可用），平均审查耗时从早期研究预览版的约 20 分钟压缩到了 6～10 分钟（提速约 3 倍）。但我认为它最核心的工程演进并不在速度，而在去噪架构。

在传统 AI Review 工具中，最让工程师崩溃的是满屏的“风格建议（Nit）”和误报（False Positive）。Anthropic 在引入研究预览版时，内部 PR 收到实质性评论的比例从 16% 跃升至 54%，随之而来的是巨大的噪音压力——尤其是当 PR 的修复者也是 AI 代理时，一条无关痛痒的 Nit 会触发一次多余的 Commit 和新一轮全量复审。

为此，Code Review 内部采用了“并行找错 + 对抗投票”的两阶段结构：多个评审代理同时从不同维度扫描代码，随后由另一组验证代理对每条发现进行对抗式核查与投票，只有达到阈值共识的问题才会被打上 Important、Nit 或 Pre-existing（原有历史问题）标签发出，纯粹的风格吹毛求疵或无意义诊断信息会被直接丢弃。管理员还可以按仓库重要度独立设置 Quick、Standard（默认）或 Deep 三个审查深度。

2. PR Steward：只修不批的“云端值守工兵”

PR Steward 是此次随 Claude Ship 推出的新角色。当 PR 遭遇 CI 挂红、与主干发生 Merge Conflict、或者收到来自 Code Review / 第三方静态扫描器 / 人类同事的修改意见时，PR Steward 会在 Anthropic 云端沙盒中拉起会话，尝试修复问题并直接向该 PR 分支推送新的 Commit。

Anthropic 在这里设计了几个非常接地气的工程细节：

  • 强制透明与可回退：每次自动推送后，PR Steward 必须在评论区写清楚“修改了什么”以及“如何撤销本次修改（How to undo）”。
  • 随时可人工接管（Steering）：开发者直接在 PR 评论区回复 @claude <具体指令> 即可纠正它的修复方向，或者直接评论 @claude stop 喊停值守。
  • 跨机器人身份隔离：如果一个 PR 本身是由 claude[bot] 打开的（例如产品经理在对话里让 Claude Tag 直接发起的修文档 PR），那么在策略允许自动批准时，为了避免同一个机器人既当运动员又当裁判员，系统会引入独立的 claude-approvals[bot] 身份来提交批准评审。

3. 本地单兵入口：/ship 与 /steward 的精巧设计

如果你所在的组织还没开通企业版全自动服务，或者管理员还在观望，个人开发者更新 Claude Code 后即可直接运行 /ship 和 /steward：

/code-review             # 推送前先在本地审查当前分支与未提交改动
/code-review --fix       # 直接把发现的问题修复到工作区（建议先 commit 以免 /rewind 漏掉）
/ship                    # 自动提交、建分支、推远端、开 PR、自审修复并开启最长 7 天本地盯守
/ship high +my-lint-bot  # 指定 high 强度，并额外监听第三方机器人的评论
/steward 41              # 对已经打开的 PR #41 直接启动盯守修复（跳过前置评审）
/ship stop               # 随时终止当前会话的后台盯守

这里有两个非常容易踩坑、但官方文档坦诚写出的工程限制：

  1. 本地 /code-review 不读取 REVIEW.md：本地 CLI 审查只加载 CLAUDE.md，而云端 Code Review 和 PR Steward 才读取默认分支上的 REVIEW.md。如果把关键业务规则只写进 REVIEW.md，本地跑 /ship 前置自审时是看不到的。
  2. 公有仓库与敏感文件防御：运行 /ship 时，它会像 git add -A 一样打包当前未提交改动（尊重 .gitignore），但如果检测到类似 .env 的疑似密钥文件名，或者触及 CLAUDE.md、REVIEW.md、.claude/、.github/ 等规则目录，/ship 会强制拒绝自动提交；在公有仓库中它也拒绝自动提交未暂存文件，必须由人类先手动确认并提交。此外，一个终端会话同一时间只能盯守一个 PR，且需使用独立 git worktree 或保持该分支处于 Checkout 状态——合上笔记本电脑会导致本地 Watch 中断。

三、深度拆解 .claude/approvals.yml：比 CODEOWNERS 更聪明的策略引擎

如果说 Code Review 和 PR Steward 解决的是“发现与修复问题”，那么 Claude Approvals 解决的就是整个研发体系里最敏感的问题：到底谁有资格点下 Merge 前的绿灯？

Anthropic 把它定位为“更聪明的 CODEOWNERS”。策略文件存放在仓库受保护默认分支的 .claude/approvals.yml（子目录也可覆盖，如 services/billing/.claude/approvals.yml）。先看一段官方推荐的起步模板：

# .claude/approvals.yml
version: 1
mode: observe
rules:
  - purpose: "默认变更需 2 人批准；若 Claude 审查通过，1 人即可且由 Claude 补齐批准"
    paths: ["**"]
    verdict:
      claude: comments
      seats: 2
    override:
      - if: "claude/code_review = pass"
        verdict:
          claude: approves
          seats: 1

  - purpose: "修改规则、鉴权、计费与 CI 工作流必须由非作者本人的人类同事审批"
    paths:
      - "**/.claude/**"
      - "**/REVIEW.md"
      - "**/CLAUDE.md"
      - "**/CODEOWNERS"
      - "src/auth/**"
      - "src/billing/**"
      - ".github/**"
    nested: inherit
    verdict:
      claude: comments
      seats:
        - count: 1
          from: [humans, "!pr/authors"]

这段不到 30 行的声明式 YAML，藏着 Anthropic 策略引擎的四大核心设计精髓：

  1. 多规则冲突时的“最严原则（Strictest Wins）”：当一个 PR 同时修改了普通业务文件和 .claude/approvals.yml 时，它会同时命中第一条通用规则和第二条规则。引擎会自动取最严格的 verdict——由于第二条没有 override，且明确指定 seats 来自 [humans, "!pr/authors"]（排除 PR 作者本人的人类席位），哪怕 Code Review 绿灯，Claude 也只能评论（claude: comments）而绝不能放行。
  2. nested: inherit 防子目录逃逸：大型 Monorepo 允许子团队在子目录放置独立的 .claude/approvals.yml 来自主提速。但通过 nested: inherit，根目录的高危规则（如保护 .claude/**、计费和鉴权代码）会被强行注入到所有子目录策略中，防止下级目录通过放宽配置架空全局安全基线。
  3. 语义分类器（Classifiers）作为动态条件：除了基于路径和 PR 元数据（改动行数、目标分支、作者身份）做静态判定，规则的 if 条件还可以接入内置分类器（如 claude/code_review、claude/diff）或存放在 .claude/classifiers/<name>/def.yml 的自定义自然语言分类器（例如判断 "这次 PR 是否涉及数据库 Schema 迁移？"）。需要注意的是，策略条件无法直接读取外部 CI 运行结果，因此 CI 检查依然必须作为 GitHub 原生 Required Check 独立挂载。
  4. 一个极其隐蔽的接入陷阱（踩坑预警）：一旦默认分支合并了 .claude/approvals.yml（哪怕还处于 mode: observe 灰度观测模式），如果你在规则里没有通过 advisory: [claude/code_review] 或 override 显式引用 claude/code_review，仓库原先开启的自动 Code Review 会直接停止触发！反之，只要策略里引用了 claude/code_review 或自定义分类器，哪怕全局关闭了 Code Review 或者策略处于 observe 模式，每次 Push 依然会触发按 Token 计费的模型调用。

四、五层纵深安全防御：如何防止代理“自己审自己、自己合自己”？

把代码修改权和某种程度上的 Approve 权交给云端 AI 代理，工程团队最恐惧的一定是越权合并、规则篡改与提示词注入（Prompt Injection）。拆解完 pr-steward-security 与 approvals 文档后，我把 Claude Ship 的防御体系画成了下面这张五层补偿安全堆栈（Compensating Security Layers）——注意，没有任何一层是绝对无懈可击的，但每一层都在精准填补上一层的残余风险：

拆解其中的几个硬核安全机制：

  • Token 外置与服务层指令截断：在 Anthropic 云端运行的 PR Steward 会话拿不到 GitHub App 的原始安装密钥，它的 gh 与 git 请求必须经由沙盒外部的 Anthropic 代理服务注入 Token。该代理层在协议侧硬性拒绝四类高危操作：批准 PR（Approve）、修改分支保护或 Rulesets/写入 Check Run、删除分支、推送 Git Tag。
  • 默认分支信任锚点（Trust Anchor）：无论是 Code Review 的 REVIEW.md、PR Steward 的 .claude/skills/steward/SKILL.md，还是 Claude Approvals 的 .claude/approvals.yml，云端代理永远只从受保护的默认分支（如 main）读取，绝不采信当前 PR 分支自带的规则文件。这意味着外部贡献者或失控代理绝对无法通过“在同一个 PR 里顺便改掉审批策略”来给自己放行。
  • 双通道评论防注入与人类兜底：PR Steward 默认只把 PR 作者、拥有仓库 Write 权限的协作者以及受信任机器人的评论当作驱动指令。但文档也十分坦诚地指出了残余风险：任何文本解析型代理都可能被评论区精心构造的文本欺骗，而且如果企业开启了 GitHub auto-merge，而策略又允许 seats: 1（作者本人可填充席位）加上 claude: approves，理论上就存在“作者发起后，PR Steward 修完，Claude 点批，GitHub 自动合并”的零第二人介入路径。
  • 因此最后一层依然属于 GitHub Branch Protection：必须将 Claude Approvals 设为 Required Check，把 Claude GitHub App 彻底移出 Bypass List（绕过名单），开启 Dismiss stale pull request approvals when new commits are pushed（新提交作废旧批准），并利用 Merge Queue 在合入前对最新 main 重跑全量 CI。值得一提的是，一旦本地 Watch 或 PR Steward 替你把 main 合并进了 PR 分支产生 Merge Commit，原作者的默认席位可能会因为最新提交并非本人签出而失效，此时需要作者手动评论 @claude approve 显式签字背书。

五、防死循环与灰度落地：Anthropic 的收敛飞轮工程学

如果让一个 AI 评审代理和一个 AI 修补代理在一个 PR 上自由对接，会发生什么？Anthropic 在博客里自爆了一起真实的内部事故：在早期未设防时，一个 CLI PR 上的代理作者与代理评审员在夜间互相挑刺、互相提交修复，足足拉锯了超过 50 个回合（50+ Rounds），直到人类作者早上起床手动叫停。

更致命的是，Anthropic 对高频复审发现的 Bug 做了 git blame 溯源，结果令人惊讶：高达 59% 后续回合新报出来的缺陷，其实早在第一轮评审时代码就已经存在了——评审代理并不是在抓新改出来的问题，而是在每一轮全量重读时“又多挑出几个陈年旧错”。

为了彻底治好这种“代理震荡病”，同时安全地把团队从人工审批过渡到策略驱动审批，Anthropic 沉淀出了一套六步自进化收敛飞轮：

1. 强行收敛的四大硬机制

  • 三轮硬熔断（3-Round Cap）：不论是本地 /ship 盯守还是云端机制，针对同一个问题或未决评审，代理最多尝试推进 3 轮修复。一旦 3 轮仍未收敛，必须立刻停手、汇总已尝试过的方案并强制升级（Escalate）给人类开发者——因为连续失败 3 次大概率意味着整体实现路径错了，继续局部修补只会浪费 Token。
  • 增量 Diff 复审与同类归并：前几轮过后，复审仅聚焦新增 Diff；发现一类问题时要求作者一次性扫清全仓同类模式，且绝不重复播报已经发过的问题。这套收敛改造在 Anthropic 内部立竿见影：一轮通过率从 65% 跃升至 78%，需要 5 轮以上拉锯的 PR 比例从 8.9% 骤降至 1.5%，平均评审轮次从 2.08 次降至 1.32 次。

2. 从 Observe 灰度到硬门禁的人机校准矩阵

Anthropic 强烈反对第一天就直接打开 claude: approves 并设为必过检查。正确的上线节奏是先加上 mode: observe 跑 1～2 周——此时 Claude Approvals 会在 PR Check 标题上打印 (observe mode) 与拟议裁决结果，但不阻断合并——然后对照下表做回溯校准：

策略模拟裁决（Observe） 人类真实评审表现 工程调优动作
原本会直接批准 人类也直接批准，毫无补充意见 规则安全有效，予以保留
原本会直接批准 人类提出了实质性修改意见（最危险！） 立即收紧路径规则强制要求人类，或把漏网条件沉淀进 REVIEW.md
要求双人审查 人类每次都扫一眼秒过 积累足够样本后，可考虑收窄该规则的 paths 范围
要求双人审查 人类确实提出过深度架构质疑 规则命中高价值风险区，予以保留

只有当第二行“代理误放行、人类却抓出了真问题”的盲区被逐一修补后，才把规则拆分成“核心敏感路径无条件强制非作者人类（!pr/authors）”和“常规路径交由机器放行”，随后删除 mode: observe 并在开放 PR 上评论 @claude approvals rerun 刷新状态。

3. “两次重复原则”与仓库规则分层

当团队跑通这套飞轮后，日常的隐性工程经验会被持续写回默认分支的四份文件，形成可版本化审计的“组织记忆”：

  • CLAUDE.md：编码规范、技术栈约定与禁忌（所有会话与本地 /code-review 均读取）。
  • REVIEW.md：纯评审标准、严重度定义与降噪指令（仅云端 Code Review / PR Steward 读取）。Anthropic 内部的铁律是：同一个评审意见至少在 2 个不同 PR 上重复出现，才有资格被人类审批合入 REVIEW.md；同时要定期清理过时规则，防止上下文膨胀。
  • .claude/skills/verify/SKILL.md：定义如何拉起本地栈、跑端到端验证并截图取证。
  • .claude/skills/steward/SKILL.md：教导 PR Steward 如何处理本仓库特殊问题（例如“Lockfile 必须由 npm install 生成而非手改”、“e2e-nightly 属于已知不稳定用例，先重试一次再查代码”），并通过 user-invocable: false 与 disable-model-invocation: true 防止它在普通对话里被误触发。

六、商业计费、合规盲区与我观察到的真实边界

站在工程负责人的视角评估这套方案，不能只看提效故事，更要算清账本与合规边界。我逐条核对了 Claude Ship 的官方定价与准入限制文档，发现几项极其关键的约束条件：

  1. 独立的 Token 账单机制与促销窗口：Claude Ship 仅面向 Claude Team 与 Enterprise 计划开放，且只能接入 GitHub（支持 github.com 及 GitHub Enterprise Cloud / Server，暂不支持 GitLab 等其他托管平台）。三个云端代理的消耗不包含在套餐基础订阅额度内，而是全部按实际 Token 用量从组织的 Usage Credits（额外用量额度）中实时扣除——哪怕在 Organization settings > Usage 中关闭了额外用量额度，只要代理处于开启状态，它依然会继续运行并产生账单，停费的唯一方式是按 Approvals -> PR Steward -> Code Review 的逆序彻底关闭开关。目前 Anthropic 为符合条件的 Enterprise 组织提供了至少 10,000 美元 的 Claude Ship 试用额度（需在 2027 年 1 月 15 日前领取，领取后 30 天内有效）。
  2. 高度敏感合规组织的硬性禁入：如果所在企业开启了 Zero Data Retention（ZDR，零数据保留）、HIPAA 合规配置或 Customer-Managed Encryption Keys（CMEK，客户自管密钥），目前完全无法使用 Claude Ship；启用了 FERPA 或 Access Transparency 的组织也无法启动 Claude Approvals。对于金融、医疗和强合规政企而言，这直接决定了短期内只能先在非敏感边缘仓库试水本地 /ship，而无法全量上云。
  3. 跨职能协同的新可能与新风险：Anthropic 在文章里举了一个很有意思的内部真实案例：一名产品经理看到客户抱怨 Analytics API 文档让人误以为 Admin Key 可以拉取 Pro/Team 用量，于是直接在对话中通过 Claude Tag 发起了一个修复 PR，随后撒手去做下一件事；当晚 Code Review 未发现阻断项，一名文档评审人签字确认，Claude Approvals 放行，补丁当晚就合并上线了。这固然大幅降低了非工程角色参与修复的门槛，但也意味着：哪怕写代码的成本降到了接近零，决定“应不应该做这个改动（Direction & Taste）”以及“为线上结果兜底（Accountability）”的人类责任，反而变得更加沉重。

归根结底，Claude Ship 并不是让人类彻底撒手不管，而是用一套机器初筛 + 有限自愈 + 声明式风险分流的工程系统，把人类评审员从海量琐碎的拼写、测试报错和机械修补中解放出来，重新聚焦回架构演进、产品边界与真正致命的高危变更上。
