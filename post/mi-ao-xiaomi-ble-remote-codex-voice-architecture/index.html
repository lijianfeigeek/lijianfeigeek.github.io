一根 99 元遥控器直通 Codex 输入框：米遥（MI-AO）的 ATVV 蓝牙音频流、十二键中性隔离与本地语音架构实测

2026-11-26 21 min read # 系统架构 # Codex # Whisper # macOS # Swift # BLE

在高频使用 Codex 推进多任务开发时，我经常遇到一种割裂的交互体验：靠在椅背上审视完一段长 Diff 或架构方案，脑子里已经想好了清晰的修改指令，却还得坐直身子切回窗口、用触摸板找准输入框、敲下一大段提示词；如果改用 macOS 自带听写或第三方全局语音输入法，不仅笔记本麦克风极易把桌面风扇和环境杂音一并收进去，一旦窗口焦点不慎落在终端或代码编辑器里，还会瞬间把半成品语音误敲成一串灾难性的回车命令。

最近我拉取并在本机完整编译验证了开源项目 fanxeon/mi-ao（中文名米遥）。它的切入点极其巧妙：直接把一根百元级的小米蓝牙遥控器 2 Pro 变成握在手里的物理语音魔杖——按住遥控器语音键对着自带近讲麦克风说话，松手即由本机 whisper.cpp 完成离线转写，并在确认唯一可用的 Codex 输入框后精准投递；方向环、确认、返回与音量加减则化身为鼠标指针与会话切换器。这篇文章我将结合源码审计与 Apple Silicon 实机测试，把它的 ATVV 蓝牙音频解码、零全局键盘钩子的十二键中性隔离、双模模型完整性契约以及防误发辅助功能护栏逐层讲透。

一、从 BLE 近讲麦克风到唯一输入框：四域解耦的端到端语音管线

市面上绝大多数“AI 语音编程入口”本质上只是给电脑内置麦克风套了一层全局快捷键壳子。米遥最硬核的差异在于：它完全不碰 MacBook 自身的音频输入设备，而是直接在 CoreBluetooth 用户态接管遥控器内置麦克风发出的 Google Android TV Voice（ATVV）BLE 低功耗音频流。

顺着这条四域流水线往下拆，能看到作者在真机联调中踩出的多处底层协议细节与并发边界设计：

1. 标准 ATVV 协议栈与小米固件 2671 的字节对调容错

小米蓝牙遥控器 2 Pro（固件版本 2671）在底层暴露了标准的 Google ATVV GATT 服务（Service UUID AB5E0001-5A21-4F05-BC7D-AF01F617B664），包含三条各司其职的特征通道：

  • TX（AB5E0002-...）：主机向遥控器下发 GET_CAPS（0A 01 00 00 03 03）、MIC_OPEN（v1.0 为 0C 00）与录音期 KEEP_ALIVE（0E <stream-id>）；
  • RX Audio（AB5E0003-...）：遥控器高频推送压缩后的 120 字节 IMA/DVI ADPCM 裸音频帧；
  • Control（AB5E0004-...）：遥控器上报能力响应（0x0B）、按键触发 START_SEARCH（0x08）、开麦 AUDIO_START（0x04）、解码器同步帧 AUDIO_SYNC（0x0A）以及松手 AUDIO_STOP（0x00）。

在真机抓包阶段，作者抓到了一个极易导致第三方客户端直接罢工的固件怪癖：固件 2671 大多数时候返回标准的 v1.0 能力包 0B 01 00 02 03 00 78 00 00（第 4 字节 0x02 代表 ADPCM 16 kHz，第 5 字节 0x03 代表交互模型，帧长 0x0078 = 120 字节），但在首次连接协商时偶发返回 0B 01 00 00 03 00 78 00 00——两个字段的顺序被固件颠倒了！

打开 Sources/MiAo/ATVVProtocol.swift（第 145～162 行），米遥没有粗暴地放宽校验，而是写了一段极其克制的无歧义字节对调兼容逻辑：

// Sources/MiAo/ATVVProtocol.swift
case 0x0100:
    guard bytes.count >= 7 else { return nil }
    let standardCodecs = bytes[3]
    let standardInteractionModel = bytes[4]
    // 小米遥控器固件 2671 偶发将这两个字节颠倒返回；
    // 仅当标准 codec 位完全无有效编码、且相邻字节恰好含 8k/16k ADPCM 标志位时才互换。
    let hasKnownStandardCodec = standardCodecs & 0x03 != 0
    let hasKnownSwappedCodec = standardInteractionModel & 0x03 != 0
    let codecs = !hasKnownStandardCodec && hasKnownSwappedCodec
        ? standardInteractionModel : standardCodecs
    let interactionModel = !hasKnownStandardCodec && hasKnownSwappedCodec
        ? standardCodecs : standardInteractionModel
    return ATVVCapabilities(
        version: .v10,
        codecs: codecs,
        interactionModel: interactionModel,
        frameSize: Int(UInt16(bytes[5]) << 8 | UInt16(bytes[6]))
    )

与此同时，区别于把序列号、预测值（predictor）和步长索引（stepIndex）硬塞进每帧前 6 字节的 ATVV v0.4（常见 134 字节帧），v1.0 的音频帧是不带包头的纯负载。ADPCMDecoder.swift 用不到 55 行零外部依赖的纯值类型代码实现了 89 阶步长表与高位优先（High-Nibble First）4-bit 差分还原，每逢控制通道推来 AUDIO_SYNC（0x0A）便即时校准 predictor 与 stepIndex 并校验序列号连续性；收尾阶段同时兼容物理松手 AUDIO_STOP、二次短按 START_SEARCH 与静音超时三路收口，哪怕遇到手指轻触产生的过短无效采样（如真机实测 240 samples），也会立即取消并把菜单栏状态平滑归位到 ready，绝不让界面卡死在“正在听”的幽灵状态。

2. 容量为 2 的串行背压队列与 148MB 模型双模 SHA-256 校验

如果把 WAV 落盘、whisper-cli 子进程拉起和辅助功能树遍历全部阻塞在 CoreBluetooth 所在的主队列上，用户在转写期间按方向键移动鼠标或者紧接着说第二句话就会全部卡死；反过来，如果做成无上限异步队列，一旦本地模型异常慢转写，积压的十来条过期指令会在几分钟后像连珠炮一样灌进 Codex。

我在 SpeechJobQueue.swift 与 ModelIntegrity.swift 中看到了两条非常老练的工程权衡：

  1. 主线程瞬时脱钩 + 最多 2 任务的硬背压（maximumPendingJobs = 2）：录音结束瞬间，PCM 数组被打包进 SpeechJobRequest 投递给串行后台队列 com.fanx.miao.speech-processing，BLE 会话当即回到 ready 态继续响应实体按键与下一段录音。队列内部通过 NSLock 严格限制最多只允许“1 条正在转写 + 1 条排队等待”，第 3 条并发语音会直接返回 false 明确拒收并在菜单栏提示，彻底杜绝后台静默堆积。所有落盘的 .wav 与 .txt 文件均强制收紧为目录 0700、文件 0600 权限，仅当前登录用户可读。
  2. UI 元数据缓存 vs 转写边界强制重算的双模完整性契约：米遥通过 Resources/WhisperModel.sha256 将多语言 ggml-base 模型（约 148 MB）死死锚定在单一哈希值 60ed5bc3dd14eea856493d334349b405782ddcaf0028d4b5df4088345fba2efe 上。为了避免每次打开设置诊断页都重读 148 MB 磁盘阻塞界面，ModelIntegrityVerifier 在设置页启用基于 (path, byteCount, modificationDate, systemFileNumber) 四元组的内存缓存；但在 WhisperTranscriber.init 真正准备调起 whisper-cli 之前，始终以 useMetadataCache: false 按 1 MB 分块重新流式计算 SHA-256（实测包含“同字节大小篡改拒绝”单测覆盖），同时为中文环境默认注入领域引导词 "米遥。Codex。项目。代码。测试。发送。" 显著降低专业词汇误识率。

二、零全局键盘钩子：十二键设备级 No Event 隔离与双契约热重载

把电视遥控器连上 macOS 当输入外设，最棘手的难题不是“怎么读到按键”，而是“怎么在不监控用户 Mac 实体键盘的前提下，摁住遥控器原生的系统副作用”。

只要把小米遥控器配对到 Mac，macOS 默认就会把它识别成一把普通蓝牙 HID 键盘加多媒体控制器：按遥控器上下键会直接滚动前台网页或乱切代码光标，按音量加减会直接调大 Mac 系统外放音量。很多改键软件的常规套路是注册全局 Quartz Event Tap（CGEvent.tapCreate）拦截全系统键盘事件再做过滤——但这意味着你在 MacBook 主键盘上敲下的每一行代码和每一次密码输入都会流经改键进程，不仅隐私攻击面过大，一旦进程崩溃还会引发全局键盘假死或修饰键粘连。

米遥彻底抛弃了全局键盘钩子，设计了一套极其干净的五层物理隔离与热重载架构：

1. 十二键 0x700000000 中性化与 Menu 键原生右键豁免

翻开 scripts/remote-mapping.sh 与内置真机档案 Resources/HardwareProfiles/xiaomi-remote-2-pro-2671.plist，米遥利用了 IOKit HID 层一个非常精妙的上下游分层特性：

  • 对系统上层事件流做“定点消音”：启动门禁通过 /usr/bin/hidutil property --matching 精确匹配 VendorID: 10007 (0x2717)、ProductID: 12984 (0x32B8) 的蓝牙 HID 服务，仅将这支遥控器上的 12 个接管键（方向四键 0x52/0x51/0x50/0x4F、确认 0x28、返回 0xF1、HOME 0x4A、TV 0x35、电源 0x66、语音 0x3E、音量 0x80/0x81）在系统驱动出口映射为 HIDKeyboardModifierMappingDst = 0x700000000（即 HID No Event 空事件），使 macOS 前台应用完全收不到任何原生方向键或调音副作用；唯独第 13 个“菜单键”被刻意排除在映射表之外，原封不动保留 macOS 对它的原生鼠标右键行为！
  • 在下层 IOHIDManager 照常读取原始物理 Usage：尽管系统上层把这 12 个键吞成了 No Event，HIDButtonController.swift 通过 IOHIDManagerSetDeviceMatching 直接绑定该硬件句柄时，依然能毫秒级收到最原始的 UsagePage 0x07 按压与释放数值；而用户的 Mac 内置键盘和外接机械键盘由于 VendorID/ProductID 根本不匹配，100% 物理旁路，连米遥进程的边都不会沾。
  • 严格的所有权状态机与防误删保护：remote-mapping.sh 绝不盲目清空系统 UserKeyMapping。写入前它先检查当前遥控器是否已有用户自建的其他改键规则（有则立即中止拒绝覆盖）；写入后立即执行回读比对（read_mapping + mapping_is_expected），并在 ~/Library/Application Support/mi-ao/system-mapping/ 原子写入 owner=mi-ao 状态凭据（内置 v1、v2、v3、v4 历史映射格式自动识别迁移），退出或收到异常信号时精准还原为空映射。

2. 成对事件收敛、双契约解耦与 60Hz 动作执行细节

在拿到原始 HID 信号之后，HIDButtonEventReducer.swift、ButtonPreset.swift 与 ButtonActionExecutor.swift 解决了三个直接决定手感的交互细节：

特别值得一提的是模式不变量设计：默认 pointer 方案下按 TV 键只切换方向环本身的“移动鼠标指针 / 上下左右方向键”两种模态，而中间确认（Return）、返回（Escape）、音量加减（经由 kAXMenuBarAttribute 无损点击 Codex 菜单栏的 Previous Task / Next Task 切换上下会话）以及电源键（启动或聚焦 Codex）在两种模式下保持完全一致，肌肉记忆负担几乎为零。

三、Codex 投递护栏：单进程 AX 树唤醒、唯一输入框判定与剪贴板并发锁

语音转写出了准确文字，怎么把它安全送进 Codex 桌面端（com.openai.codex）？如果简单粗暴地切窗口、写剪贴板、模拟 Cmd+V 加 Return 回车，十次里至少有两次会把话发错地方——比如 Codex 正在弹窗确认、打开了多个分栏搜索框，或者用户在转写那两秒钟里恰好自己按了一次 Cmd+C 复制代码。

细读 scripts/codex-accessibility.sh 与 Sources/MiAo/CodexSubmitter.swift，我梳理出了米遥层层设防的四道安全闸门：

  1. 非侵入式单进程 --force-renderer-accessibility 唤醒：Codex 桌面端底层基于 Chromium 构建，默认出于性能考量不会把网页渲染区的输入框完整暴露给 macOS 辅助功能树（Accessibility Tree）。米遥既没有去篡改 Codex 的持久化配置文件，也没有开启高危的 --remote-debugging-port（CDP 调试端口），而是仅在 Codex 未运行时通过 open -b com.openai.codex --args --force-renderer-accessibility 注入单次进程级参数，并在外部进程边界调用 MiAoProcessEnvironment.sanitizedForExternalProcess 自动剥离所有 MI_AO_* 内部环境变量。如果检测到 Codex 已经在运行但未带该参数，米遥会立刻停在门禁前提示用户，绝不擅自杀掉正在干活的 Codex 进程。
  2. BFS 广度优先扫描与“唯一可用输入框”硬门槛：提交前，CodexSubmitter 对当前焦点窗口执行带硬上界保护的广度优先搜索（最大深度 50 层、最多扫描 10,000 个节点，防止复杂 DOM 引发死循环），筛选处于 enabled 状态的 AXTextArea 或 AXTextField：
    • 只有当 candidates.count == 1（恰好存在唯一一个可用输入框），且对其写入 kAXFocusedAttribute = true 后回读 kAXFocusedUIElementAttribute 严格匹配（CFEqual）时，才放行后续的粘贴与回车；
    • 一旦 Codex 未运行、缺少辅助功能授权、找不到输入框或同时存在多个候选输入框（歧义态），米遥一律降级为仅将转写文本写入剪贴板并报错提示，绝不盲敲半个回车键。
  3. 基于 changeCount 的剪贴板并发防覆写锁（PasteboardSnapshot）：由于 macOS 模拟 Cmd+V 是异步生效的，米遥在注入转写文本前会先用 PasteboardSnapshot.capture() 完整备份用户剪贴板里的多类型原始二进制条目，随后在 0ms 贴入文本并记下此时的 injectedChangeCount = pasteboard.changeCount，200ms 发送 Return 回车，550ms 后尝试恢复用户原本的剪贴板。最细腻的一笔在第 309 行：
// Sources/MiAo/CodexSubmitter.swift
enum PasteboardRestorePolicy {
    static func shouldRestore(expectedChangeCount: Int, currentChangeCount: Int) -> Bool {
        expectedChangeCount == currentChangeCount
    }
}

如果在这 550ms 的异步窗口期内，用户自己在别的软件里复制了一段新内容，系统 pasteboard.changeCount 就会递增——此时 shouldRestore 立即返回 false 放弃回写旧快照，从而保证绝不会用半秒前的旧剪贴板把用户刚刚复制的新代码悄悄吞掉！

四、BLE 睡眠自愈与交付工程：三次看门狗、双模式恢复与原子安装回滚

低功耗蓝牙语音遥控器在硬件设计上极其省电：闲置几分钟就会主动断开 BLE 连接并停止广播，或者在重连瞬间偶尔吞掉一次 GET_CAPS 通知。如果客户端处理不好，要么会让状态栏永远卡在“连接中”，要么会在后台疯狂空转扫描把 Mac 蓝牙协议栈拖慢。

我将 BLEVoiceBridge.swift 与 DeviceConnectionPolicy.swift 中的连接仲裁与恢复机制提炼成了下面这张有限状态机图：

这套状态机解决了长驻菜单栏工具最痛的三个稳定性隐患：

  1. 三级寻址快路径与确定性多设备仲裁：每次启动或重连时，米遥并非直接开启全频道盲扫，而是优先调用 retrievePeripherals(withIdentifiers:) 直连用户固定的设备 UUID，其次调用 retrieveConnectedPeripherals(withServices: [ATVV]) 捞取已被 macOS 系统层保持连接但停止广播的遥控器，最后才进入广播扫描。若周围存在多支兼容设备，扫描器开启 0.8 秒窗口，按 固定 UUID > 名称匹配 > 广播含 ATVV > RSSI 信号强度 > UUID 字典序 做 100% 确定性排序仲裁。
  2. 1.5s × 3 能力协商看门狗与空闲期零轮询：连接成功后，只有当 RX Audio 与 Control 两个特征全部确认 isNotifying 订阅完成，才发出 GET_CAPS 并启动 1.5 秒定时器；单次丢包自动重发，连续 3 次未响应则果断调用 cancelPeripheralConnection 断开重来，且协商完成前到达的任何语音事件一律丢弃，绝不使用未初始化的解码器。一旦进入 READY 态，空闲期保持零轮询，10 秒一次的 KEEP_ALIVE 心跳仅在按住说话的 STREAMING 录音窗口内运行。
  3. “随时就绪”与“智能休眠”双策略实时热切换：在 0.2.2（Preferences v3）中，默认“随时就绪”模式按 1 → 2 → 4 → 8 → 16 → 32 → 60 秒指数退避，随后维持 60 秒一次的极低频后台重连；可选的“智能休眠”模式则在 1s、2s 两次快速重连失败后彻底挂起后台蓝牙握手，但此时 IOHIDManager 实体按键链路依然独立待命——只要你拿起遥控器随便按一下方向键、重新打开系统蓝牙或点一下菜单栏，休眠态就会被瞬时跨通道唤醒！

除此之外，在软件交付与隐私合规上，米遥展现出了极强的工程克制力：

  • 内置自包含 Runtime 与原子回滚安装：build-app.sh 把启停脚本、硬件档案与 SHA-256 契约一并打进 米遥.app/Contents/Resources/Runtime 参与 ad-hoc 签名（安装后即使删掉或移动源码仓库也能独立运行）；install-app.sh 先在同卷隐藏目录 .米遥.app.install.$$ 分期校验深度签名并提取 CDHash，替换过程中任一步失败都会由 trap rollback_install EXIT 自动恢复旧版 App 与 install-context.plist，且当检测到二进制 CDHash 变更时主动提醒用户刷新 macOS TCC 辅助功能授权。
  • 面向社区逆向的默认脱敏采集器（CaptureRecorder.swift）：如果开发者想为手头其他品牌的 Android TV 语音遥控器贡献适配，./scripts/capture.sh 在探索未知设备时坚守“只读枚举与订阅 Notify、绝不向未知特征盲写任何字节”的硬件安全红线，且生成的 report.json 默认将外设 UUID 混入单次随机 sessionID 做 SHA-256 前缀哈希假名化、抹除广播名称与厂商字段。

五、本机三分钟构建与上手实操指南

由于项目在未接入 Apple Developer ID 公证前坚持 Source-First Beta 透明交付原则（拒绝分发来历不明的未公证 DMG），在搭载 macOS 14+ 与 Xcode Command Line Tools 的 Mac 上，只需三条命令即可完成本地编译、模型校验与安装向导拉起：

# 1. 克隆源码并执行全套单元测试门禁（可选，验证本机 Swift 6 工具链）
git clone https://github.com/fanxeon/mi-ao.git
cd mi-ao
swift test

# 2. 一键安装 whisper-cpp、校验下载 148MB base 模型、构建签名并安装至 ~/Applications/米遥.app
./scripts/setup.sh

# 3. 配对遥控器（同时长按小米遥控器 2 Pro 的“菜单键 + HOME 键”在系统蓝牙中连接）后：
#    可直接通过米遥设置向导图形界面点击启动，或使用等效命令行门禁启动：
./scripts/start.sh

# 若只想体验纯语音输入、完全不接管遥控器实体按键映射，可运行无映射模式：
./scripts/run.sh --name "小米蓝牙语音遥控器" --no-buttons

# 安全退出并自动清空 12 键 No Event 映射恢复原生状态：
./scripts/stop.sh

[!TIP] MacBook 刘海屏菜单栏遮挡排查提示
米遥运行态固定使用 17pt 单色太阳图标常驻菜单栏。如果你的 MacBook 带有屏幕刘海且右上角常驻图标过多，macOS 可能会将新创建的状态项挤进刘海不可见区——此时并非进程崩溃，直接再次双击 ~/Applications/米遥.app，RuntimeApplicationDelegate 会自动复用现有单实例进程并唤出“米遥设置与诊断”主窗口。

把一个看似简单的“蓝牙遥控器转语音输入”点子，一路做到协议容错、零全局键盘监听、有界背压队列、剪贴板 changeCount 并发保护与安装失败原子回滚，米遥在不到一万行 Swift 6 代码里给出了一份教科书级的 macOS 原生硬件桥接示范。如果你手头恰好躺着一根吃灰的小米蓝牙遥控器 2 Pro，非常推荐亲手编译体验一次这种“按住即说、松手开工”的物理掌控感。
