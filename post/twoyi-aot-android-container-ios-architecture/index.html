把完整 Android 13 塞进免越狱 iPhone：解剖两仪 Twoyi 的 2852 单元静态 AOT 引擎、gfxstream/Metal 管线与双端容器演进

2026-11-20 23 min read # AOT # 架构剖析 # 虚拟化 # AI Agent # Android # iOS # Metal

过去几年，在非越狱 iPhone 上跑完整的 Android 系统几乎被视为一道工程死结：苹果严格的 W^X 内存签名机制禁止普通 App 在运行时生成可执行指令，导致 QEMU/UTM 等传统整机模拟器一旦脱离电脑端调试器或 StikDebug 开启 JIT，就只能退回到缓慢的解释执行路径。最近我深入研究了由知名系统底层开发者 weishu（KernelSU 与 VirtualXposed 作者）全新升级的 两仪 Twoyi（涵盖 twoyi.app 双端容器与 twoyi.ai 两仪分身），发现它给出了一条与整机硬件模拟截然不同的解法：iOS 版无需越狱、无需开启 JIT，约 3 秒即可启动一套完整的 Android 13，并且支持 GPU 加速与 ProMotion 高刷新率。

为了看清这背后的真实工程边界，我不仅系统梳理了 twoyi/twoyi 开源仓库的 Rust 与 Java 容器源码，还直接拉取了最新发布的 iOS 安装包（twoyi_1.1.0_932.ipa，约 582 MiB）与 Android 安装包（twoyi_0.7.5-11131322.apk，约 211 MiB）进行静态拆包与 Mach-O/ELF 二进制审计。结果令我颇感震撼：仅仅 iOS 端主程序 Twoyi 单个 Mach-O 可执行文件就高达 469 MB，其中 __TEXT 代码段占据了 403.17 MB——里面静态编译进了 2,852 个构建期预翻译的 Android 13 AOT 单元、1.04 GiB 只读 EROFS 镜像与基于 24 枚苹果补丁改造的 gfxstream + MoltenVK 渲染管线。下面我将以第一视角的静态审计实证，彻底拆解两仪从“安卓容器”跃迁为“跨端无 JIT 运行时 + AI 分身底座”的全套技术栈。

[!NOTE] 静态审计基线与实测范围说明
本文所有文件大小、段偏移、编译参数、补丁序列与架构细节，均源自我在 2026 年 11 月 20 日对公开分发产物与源码仓库的直接静态检验：包括 twoyi.app 与 twoyi.ai 官网声明、开源仓库 twoyi/twoyi 与 twoyi/platform_art（提交 33d557a）、iOS 版 twoyi_1.1.0_932.ipa 内部元数据（runtime-build.json、baseline.lock.json、gpu-build.json、rom/rootfs.manifest.json、gpu-notices/neo-source-boundary.md、display.metal 及 otool 对主程序 Twoyi 的段表分析）以及 Android 版 twoyi_0.7.5-11131322.apk 内部原生库与提示词模板。

一、从“轻量级安卓容器”到“双端运行时 + AI 分身”的五年演进

要读懂今天的 Twoyi，必须先看清它的两代技术演化脉络。2021 年底 weishu 首次开源 twoyi/twoyi 时，它解决的核心痛点是在免 ROOT 的 Android 手机上运行第二个可深度定制的 Android 8.1 系统。

当我通读 twoyi/twoyi 仓库中仅 580 行的 Rust 原生层（app/rs/src/lib.rs 与 input.rs）和 RomManager.java 时，能明显看出初代设计极度克制：

  1. 宿主与客体共享 Linux 内核：在 Android 宿主上，Twoyi 不需要任何虚拟化 CPU 模拟，而是由 Java 层的 Render2Activity 解压 rootfs.7z，再通过 Rust JNI 线程调用 Command::new("./init") 拉起客体系统的 init 进程，同时将 TYLOADER（libloader.so）注入环境变量实现二进制路径与系统调用截获。
  2. 输入与渲染双通道：Rust 层的 input.rs 直接在客体根目录下构建字符流模拟 uinput 设备（/data/data/io.twoyi/rootfs/dev/input/touch 与 key0），将宿主 MotionEvent 转换为标准 EV_ABS 多点触控帧（ABS_MT_SLOT、ABS_MT_TRACKING_ID）；画面则通过 libOpenglRender.so 接管 ANativeWindow 完成 OpenGL ES 硬件加速渲染。
  3. ADB 回环安装与抽象 Socket 控制面：Installer.java 内嵌 libadb.so 连向 localhost:22122 执行静默安装与多包安装（install-multiple）；TwoyiSocketServer.java 则通过 Linux 抽象命名空间 TWOYI_SOCK（SOCKET_SEQPACKET）实现 SWITCH_HOST、BOOT_COMPLETED 与 SETTINGS 的跨系统切屏控制。

而到了 2026 年 11 月的官网版本，Twoyi 已经裂变出两条极其清晰的进化线：

  • Android 端（v0.7.5）：底层引擎升级为统一 vulkan-cereal / gfxstream 渲染桥接与 zstd 压缩镜像（assets/rootfs.tar.zst 体积 212 MB，兼容 Android 8.1、13 与 17 多版本客体，约 1 秒启动、最高 120 FPS），并原生内建了面向自动化任务执行的 AI 智能体 两仪分身（Twoyi Twin）。
  • iOS 端（v1.1.0_932）：为了跨过 iOS 既没有 Linux 内核、又禁止运行时 JIT 的双重封锁，weishu 重新构建了代号为 Neo 的独立用户态运行时（Apache-2.0 核心），把完整的 AOSP android-13.0.0_r84 塞进了一个不到 600 MB 的标准 IPA 安装包里。

二、为什么 iOS 跑安卓不需要越狱和 JIT？拆解 469 MB 主程序的“静态 AOT 戏法”

把 twoyi_1.1.0_932.ipa 解压后，最反直觉的现象摆在眼前：整包解压后资源总计约 1.59 GB，其中 Android 13 只读镜像 rom/system.erofs 占了 1.12 GB，而 App 主程序可执行文件 Payload/Twoyi.app/Twoyi 单个二进制文件居然高达 469,115,392 字节（约 447 MB）！

用 macOS 自带的 otool -l 查看它的 Mach-O 64 位段分布后，谜底瞬间揭晓：

LC_SEGMENT_64 __TEXT       vmaddr 0x100000000   filesize 403,177,472 (384.5 MB)
LC_SEGMENT_64 __DATA_CONST vmaddr 0x118080000   filesize  61,767,680 ( 58.9 MB)

一个 iOS 原生壳程序绝不可能自己写 400 MB 的 Objective-C/Swift 代码。结合包内附带的 runtime-build.json、baseline.lock.json 与 gpu-notices/neo-source-boundary.md，我还原出了这套代号 neo 的四层无 JIT 虚拟化架构。

1. 不模拟硬件，直接用 Darwin 承接 Linux AArch64 ABI

QEMU 与 UTM 之所以沉重，是因为它们必须模拟一整套虚拟电脑主板、设备树、内存控制器乃至完整的 Linux 内核。而 Twoyi iOS 版选择了完全不同的路线：彻底跳过硬件模拟，直接在 Darwin/XNU 用户态之上重建 Android 所需的 Linux 内核接口与用户态系统服务边界。

从 rom/rootfs.manifest.json（共 2,593 条根目录清单）与 neo-source-boundary.md 的技术边界记录中，我核实了以下几个关键设计：

  • 用户态虚拟 Binder（dev/vbinder）：Android 极其依赖内核态 Binder 驱动做跨进程通信，而 iOS XNU 显然没有 Binder。Twoyi 在宿主机沙盒内实现了用户态 vbinder 协议与进程/文件描述符表（Process/FdTable/UnixSocket），直接打通 servicemanager、zygote64、surfaceflinger 与系统服务之间的 IPC。
  • 共享内存属性树（/dev/__properties__）：Android 13 的 Bionic prop_area / prop_bt / property_info Trie 树结构由运行时直接按公开布局构造并只读映射给客体，连带 ro.twoyi.display.* 与 ro.sf.lcd_density 一并注入，无需启动真实内核属性服务。
  • Darwin 原生 Futex 优先级继承适配：针对 Android 多线程锁竞争，Twoyi 独立实现了 Linux FUTEX_WAIT / WAKE_OP / LOCK_PI / robust_list 语义，并在 src/futex_pi.cpp 中通过 Darwin pthread 优先级继承适配器实现宿主机侧线程调度让渡。

2. 核心杀手锏：2,852 单元构建期静态 AOT + musttail 尾调用链

既然宿主芯片（iPhone/iPad 的 A 系列与 M 系列）和 Android 13 客体指令集同为 ARM64（AArch64），那到底是什么拦住了直接执行？答案有二：第一，iOS 代码签名禁止执行未签名 ELF 内存页与动态 JIT 页；第二，Android 系统二进制编译为 Linux ELF + 4 KB 内存页，而 iOS 运行于 Mach-O + 16 KB 内存页（guest_page_size: 4096 vs host.page_size: 16384）。

runtime-build.json 完整记录了 Twoyi 绕开这两道封锁的构建参数：

{
  "aot": true,
  "aot_selection": {
    "asm": true,
    "inline_leaf": 128,
    "transfers": true,
    "translator_version": 22,
    "units": 2852,
    "units_optimization": "-O3"
  },
  "block_dispatch": "musttail",
  "block_links": true,
  "block_maximum": 16,
  "cache_bytes_per_kernel": 2147483648,
  "cache_slots": 4096,
  "default_engine": "blocks",
  "engines": ["step", "blocks"],
  "fp_flags": ["-frounding-math", "-ffp-contract=off", "-ffp-exception-behavior=maytrap"],
  "l1_slots": 256,
  "shared_bytes_per_memory": 268435456,
  "shared_slots": 1048576
}

这段配置信息量极大，几乎就是一份高阶二进制翻译器的设计蓝图：

  1. 将 Android 核心资产静态转译进 Apple 签名 __TEXT：在构建阶段（translator_version: 22），Twoyi 的 AOT 选择器读取锁定的 Android 13 r84 system ELF 符号以及 ART boot-image OAT、services.odex（通过 aot-whitelist.json 白名单过滤），预先把系统框架与核心原生库翻译成 2,852 个静态 C++/汇编翻译单元，开启 -O3 优化与内联叶函数（inline_leaf: 128）直接编入 Twoyi 可执行文件的 __TEXT 段。
  2. 用 [[clang::musttail]] 消除块间跳转开销：翻译后的基本块之间如果走常规函数调用或 while-switch 循环分发，寄存器溢出和分支预测惩罚会非常惨重。Twoyi 显式启用 "block_dispatch": "musttail" 与 "block_links": true，借助 Clang 尾调用优化让每个翻译块结束时直接通过原生 B 指令跳向下一个物理地址，既不消耗宿主机调用栈，又完美通过苹果的代码签名审核。
  3. 严格的 IEEE-754 浮点精度锁：注意到 fp_flags 中专门关闭了浮点融合乘加（-ffp-contract=off）并开启了 -frounding-math 与 -ffp-exception-behavior=maytrap，确保 AArch64 客体浮点指令在静态转译后不因宿主编译器激进合并 FMA 指令而出现精度漂移。
  4. 未入白名单的第三方 APK 怎么办？双轨降级至预解码块引擎：用户装进两仪的第三方 64 位 Android App（及其自带的 .so 动态库）不可能在构建期就存在白名单里。此时 neo 运行时无需 JIT 也能平稳接管——未命中 AOT 身份标识的代码自动落入 "default_engine": "blocks" 预解码块解释器（配备每线程 256 槽 L1 缓存、4,096 槽位及 256 MiB 共享解码表，并辅以基于 QSBR 延迟回收的软件 Data TLB，极端边界指令回退至 step 单步解释）。

3. 为什么冷启动只需 3 秒？system.erofs 零解压镜像与 4K-on-16K 映射

在初代 Android 容器里，首次启动往往要花掉近一分钟去解压成千上万个小文件到沙盒目录。而在 iOS 版 rom/image.lock.json 中，我看到 Twoyi 引入了一个极其漂亮的存储工程优化：system.erofs 只读文件系统镜像。

构建脚本使用未修改的 mkfs.erofs 1.8.6（-b 4096 --dsunit=4 -E ^inline_data --tar=f）将整个 android-13.0.0_r84 系统树打包成一块确定性可复现的 1,119,846,400 字节镜像，直接通过用户态 EROFS 读取器加上 default_boot_overlay: true 挂载覆盖 /system、/system_ext、/product、/vendor、/odm、/apex 与 /linkerconfig。开机时省去了海量小文件随机 I/O 与解包耗时，配合启动即驻留 __TEXT 的 2,852 个 AOT 系统模块，才能在手机端实现“点开约 3 秒直达 TwoyiLauncher”的体验。

[!IMPORTANT] 4 KB 客体页面如何安全运行在 16 KB 苹果芯片上？
现代 Apple Silicon（iPhone/iPad）在 iOS 15+ 之上采用 16,384 字节（16 KB）硬件内存页，而标准 Android ARM64 ELF 与 EROFS 块对齐在 4,096 字节（4 KB，在 baseline.lock.json 中明确记录了 guest_page_size: 4096 与 host.page_size: 16384）。由于 Twoyi 并非直接将 ELF mmap 进硬件 MMU 执行，而是由自研 48-bit 虚拟 VMA 管理器与软件 Data TLB 统一托管内存读写与权限检查，它在用户态完美消化了 4K 与 16K 页粒度的错位冲突。

三、零 CPU 回读图形管线：ANGLE → gfxstream-apple → MoltenVK → Metal

在虚拟化环境里，比“指令能跑”更难的是“图形不卡”。如果在 iOS 上用 CPU 软渲染（如 SwiftShader）跑 Android 13 的 SurfaceFlinger 与 Material You 动效，别说 ProMotion 高刷，连桌面滑动都会掉帧发烫。

打开 Payload/Twoyi.app/gpu-build.json 与 display.metal，并对照 otool -L 列出的动态库链接列表，我发现 Twoyi 在图形栈上几乎把移动虚拟化的前沿工程能力拉到了极致。

整条图形链路从 Android 客户机一直贯通到 iPhone 的 Metal 显示层，没有任何一个环节退回 CPU 像素逐行搬运：

  1. 客户机端（ANGLE + 定制 Vulkan / HWC2）：在 rom/rootfs.manifest.json 的 /system/vendor/lib64/ 下，Twoyi 预置了 Google ANGLE 转换层（其中 libGLESv2_angle.so 达 8.05 MB）以及自研驱动 vulkan.twoyi.so（1.21 MB）、gralloc.twoyi.so 与 hwcomposer.twoyi.so。所有 Android App 的 OpenGL ES 调用首先经 ANGLE 转为 Vulkan 指令，或直接由 Vulkan 客户端发出；SurfaceFlinger 的多图层合成则通过 gpu-display-layers-v1 协议经 hwcomposer.twoyi.so 走主机侧合成路径。
  2. 跨端共享内存桥（twoyi_protocol.h v1.6）：在 gpu-notices/integration-scope.md 中可以看到，Twoyi 的第 24 号补丁将客体与宿主通信升级为 Protocol 1.6 直接共享内存模型（dev/twoyi-display 与 TWGB 图形缓冲契约），并专门通过第 9、10、13、14、18 号补丁实现了 SYNC_FD 围栏信号量导出 与 Display Consumer Lease（显示消费租约） 机制，保证多设备家族与跨帧写入的严格同步。
  3. 宿主端 gfxstream-apple + MoltenVK：Twoyi 将 Google Android 模拟器的核心图形流引擎 device/generic/vulkan-cereal（即 gfxstream）连同 24 枚苹果平台专属补丁 静态编入主程序，由它解包 Vulkan 与 renderControl 序列化流，再交给固定提交 db660224 的 MoltenVK + SPIRV-Cross 翻译为原生 Apple Metal 指令提交给 GPU。
  4. 原生 display.metal 多层直出合成：在 Payload/Twoyi.app/display.metal 中，我直接读到了仅有 26 行却极为干练的 Metal 着色器源码——其中 neo_layer_vertex 与 neo_layer_fragment 分别处理全屏与分图层合成，支持不透明图层（layer.blend == 0）、预乘 Alpha 与非预乘直通 Alpha（layer.blend == 2 时执行 color.rgb *= color.a），最终结合 IOSurface、QuartzCore（CAMetalLayer）与 MetalKit 在支持 ProMotion 的 iPhone 和 iPad 上跑出丝滑高帧率。

不仅是图形渲染，otool -L 与 Info.plist 还证实了完整的宿主硬件 HAL 透传闭环：

四、横向对比：在 iOS 上跑 Android 的四种路线有何本质差异？

结合 twoyi.app 整理的 2026 年 11 月行业对比与我本次拆包验证的底层实现，我绘制了一张以“执行速度”和“脱机独立性”为双轴的四象限权衡矩阵。

从架构权衡来看，每条路线解决的问题边界非常清晰：

  • UTM（开启 JIT） 走的是最通用、最正统的“全硬件虚拟化 + 动态 JIT 编译”路线，甚至能运行桌面级 Linux/Windows；但受限于苹果安全策略，每次系统重启或进程被杀后，用户都必须连接电脑调试器或借助 StikDebug 重新激活 JIT，便携性大打折扣。
  • QEMU / UTM SE 放弃了 JIT 以换取完全脱机运行，但受制于 TCTI 线程化解释器与整机硬件模拟双重税负，启动与 UI 交互延迟明显。
  • Husk 的强项在于其面向特定游戏优化的翻译层（可跳过启动整个 Android 系统直接跑单个游戏），但一旦需要完整 Android 桌面系统，其模拟模式依然需要退回 QEMU 中的 LineageOS。
  • Twoyi for iOS 则精准卡位在“只针对 ARM64 架构的 Android 系统做极致特化”——放弃模拟硬件、放弃跑 x86/Windows 等通用包袱，把 Android 13 当作一组可以静态预编译进 __TEXT 的标准程序集和一份可只读挂载的 EROFS 镜像，从而在 免越狱、免外部 JIT 激活 的前提下，独自占领了右上角“脱机自包含 + 原生级响应”的黄金象限。

[!TIP] 顺带发现的一枚 ART OSR 寄存器修复彩蛋
在审计 github.com/twoyi/platform_art 时，我注意到作者在 2026 年 10 月 27 日专门提交了一个非常硬核的补丁 33d557a（Save floating point registers in art_quick_osr_stub）。由于客体里未经过静态 AOT 的第三方 App 仍需通过 ART 的 JIT/OSR 编译运行，而旧版 art_quick_osr_stub 漏掉了保存被调用者保存浮点寄存器 d8-d15，导致 Launcher3 的 IconNormalizer.getScale() 在 OSR 返回后浮点面积值被清零，进而把部分应用图标（如 MiniIme）缓存成了全透明。weishu 反向移植该修复后，才彻底消除了容器内部分图标“隐身”的诡异 Bug。

五、Twoyi for Android 与“两仪分身”：当沙盒容器长出双环 AI Agent

聊完惊艳的 iOS 版，我也同样关注 Twoyi 在 Android 宿主端的最新进化——Twoyi for Android（v0.7.5） 以及深度整合在其中的 AI 智能体 两仪分身（twoyi.ai）。

拆开 twoyi_0.7.5-11131322.apk，我发现它与 2022 年的开源版已经不可同日而语：

  • 容器底座全面升级：libtwoyi.so（9.4 MB）同样引入了 vulkan-cereal / gfxstream（直接调用宿主硬件 GPU 实现最高 120 FPS）、同时支持 64 位与 32 位兼容加载器（libloader.so 与 libloader32.so），并且已规划兼容独立沙盒内的 KernelSU 与 Xposed 模块，支持 Android 8.1、13 与 17 多版本镜像切换。
  • 把“AI 手机自动化”塞进安全沙盒：过去市面上的手机 GUI Agent 最大的痛点是抢占主屏幕和无隔离风险——AI 点按屏幕时你自己没法用手机，且一旦模型出现幻觉误触支付或删除键后果不堪设想。Twoyi 直接把 AI Agent 放进了两仪独立分身手机里，形成了天然的“人机分屏 + 权限隔离”结构。

更有意思的是，我在 twoyi_0.7.5-11131322.apk 的 prompts/ 目录下，直接看到了两仪分身完整的多智能体 Prompt 工程骨架（包含 manager/、executor/ 与 fast_agent/ 三套 Jinja2 模板）：

  1. 双环分层控制（Manager + Executor）：
    • prompts/manager/system.jinja2 扮演高阶规划者：维护只增不减的步骤上下文记忆（<add_memory>）、动态子目标队列（<plan>）、卡死错误日志恢复（<potentially_stuck>），并随时监听用户的半途插话指令（<external_user_message>）动态修正计划；
    • prompts/executor/system.jinja2 则被刻意约束为“字面机械执行器（LITERAL EXECUTION RULE / dumb robot）”：严禁越权自主思考或擅自优化路径，只读取 <plan> 第一条子目标并精确翻译为标准 JSON 原子操作（open_app、click、swipe、type、type_secret）。这种“慢思考规划 + 傻瓜式精确落地”的拆解，极大降低了多步 GUI 操作的幻觉漂移。
  2. 快速单环与视觉回退（fast_agent）：针对短路径任务，prompts/fast_agent/system.jinja2（基于 Mobilerun 风格多工具编排）支持无障碍节点树优先、遇到游戏/直播等无节点界面时自动附带截图走多模态视觉识别。
  3. 高危操作门禁与“我来”接管：遇到删除、付款、发送、发布动作时，分身自动暂停等待人工点击确认；遇到登录账号、短信验证码、支付密码，绝不让大模型瞎猜，而是交回手机端由人类输入，或使用凭据管理器的 type_secret(secret_id, index) 安全注入；离开 Twoyi 时任务会缩成 画中画（PiP） 小窗悬浮监控。
  4. Android 14+ ROOT/Shizuku 隐身后台屏：如果用户的宿主手机已获取 ROOT 或运行着 Shizuku，两仪分身甚至可以切出沙盒，在一块宿主用户看不见的虚拟后台屏幕上直接操纵真机已有 App 与账号，前台正常刷视频聊天完全互不打扰。
  5. 纯本地 BYOK 隐私边界：Twoyi 官方不倒卖模型额度，API Key 加密保存在本机，直接直连用户指定的 DeepSeek、通义千问、Kimi、智谱 GLM、OpenAI、Anthropic、Gemini 或本地兼容接口。

六、工程局限性与实操评估建议

站在工程审计的客观立场，没有任何架构是银弹。基于我对安装包与官方说明的交叉核对，使用或研究 Twoyi 时需要明确以下边界：

评估维度 实测工程现状 使用与研究建议
32 位兼容边界 iOS 版纯 64 位架构（aarch64），不支持 32 位老旧 APK；Android 版虽保留 libloader32.so 但主推 64 位应用 测试老旧 32 位游戏建议优先使用 Android 8.1 客体容器；iOS 版专注现代 64 位 Android 应用
体积与磁盘占用 iOS 版 IPA 达 582 MiB（内含 469 MB 静态 AOT 主程序 + 1.12 GB system.erofs）；Android 版运行需预留约 4 GB 存储 iOS 侧载建议预留至少 3~4 GB 剩余闪存空间；TestFlight 满员时可通过 SideStore / AltStore / TrollStore 签名 IPA
加固与反调试应用 不模拟硬件内核，部分强金融加固、硬件级 Keystore 校验或主动反调试检测应用可能触发异常退出 iOS 版若遇闪退，可在“Android 已停止”页面直接导出共享日志排查；勿用于对抗风控敏感的主力账号
开源与合规边界 twoyi/twoyi（Android 8.1 初代容器）与 neo 核心思路遵循开源声明；iOS 版 neo 运行时及 android-13.0.0_r84 ROM 尚未整包公开源码 在 neo-source-boundary.md 中作者也明确标记了部分三方图形/ROM 组件的再分发法务审查边界，适合个人极客体验与学术/工程研究

回过头看，Twoyi 最打动我的工程质感，在于它没有被“做虚拟机就得模拟 CPU + QEMU”的思维定势困住。当行业里绝大多数人还在为 iOS 怎么绕开调试器开启 JIT 焦头烂额时，weishu 直接选择在构建阶段把 Android 13 整个系统的关键执行路径提前焊死进 Apple 签名的 __TEXT 段，再用 EROFS 和 gfxstream + MoltenVK + Metal 补齐存储与图形短板——这是一次极其硬核、把平台物理限制当作设计约束来反向优化的教科书级系统工程示范。
