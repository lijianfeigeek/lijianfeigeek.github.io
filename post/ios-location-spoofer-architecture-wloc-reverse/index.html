不用越狱如何改写系统级 GPS？剖析 iOS-Location-Spoofer-Web 的 WLOC 逆向与纯 JS 编解码架构

2026-10-28 26 min read # 网络协议 # Shadowrocket # 逆向工程 # iOS # Cloudflare

在 iOS 生态中进行基于地理位置（LBS）的开发与测试，向来是一件让移动端工程师和逆向研究员颇为头疼的事。无论是验证复杂的多边形地理围栏（Geofencing）、调试出海应用在不同国家/地区的本地化逻辑，还是对依赖 CoreLocation 框架的 App 进行边界条件测试，苹果严密的系统沙箱都构筑了极高的防御壁垒：Xcode 的 LocationSimulation（.gpx 模拟）需要通过数据线连接 Mac，在 iOS 17+ 引入 Developer Mode 与基于 QUIC 的 RemoteXPC/CoreDevice 协议后，这套 USB 联调通道变得更加繁琐脆弱；越狱插件（如 Relocate 或 LocationFaker）虽然强大，但在配备 A12+ 仿生芯片且运行现代 iOS 版本的日常主力机上早已脱离实际；而常规的 VPN 或节点代理仅能修改 IP 出口归属地，面对直接调用系统 GPS 硬件与 Wi-Fi 基站定位的 App 毫无效果。

最近，我深入研究了一个在技术思路上极具启发性的开源项目 —— iOS-Location-Spoofer-Web。它摒弃了依赖电脑数据线联调或越狱注入动态库的传统思路，直接将手术刀切入了苹果私有的定位辅助协议（Apple Location Services，简称 WLOC）；通过在 Shadowrocket（小火箭）的 MITM 中间人代理层挂载纯 JavaScript 实现的流式 Protobuf 与 ARPC 封包编解码引擎，并结合一套基于 Cloudflare Pages Serverless 架构的 Liquid Glass（液态玻璃）前端控制面板，实现了一键在手机端修改系统全局 GPS 定位。在本文中，我将以第一视角深入拆解其底层定位劫持原理、纯 JS 64 位 Varint 运算、WLOC 最小改写策略以及 Serverless 边缘协同实践。

一、 iOS 系统定位是如何工作的？WLOC 的阿喀琉斯之踵

要想在不越狱、不插线的前提下让整台 iPhone “相信”自己正身处世界上的任意一个角落，首先必须搞清楚 iOS 底层的定位决策机制。

在很多人的直觉中，手机定位完全依赖于机身内置的 GPS/北斗/GLONASS 卫星接收芯片。但在真实的城市峡谷、高楼室内或地下车库中，卫星信号衰减极度严重，不仅搜索冷启动时间长达数十秒甚至数分钟，功耗也极为惊人。为了实现“打开地图秒定位”，苹果在系统底层设计了一套高度精密的辅助定位体系（Assisted GPS / Wi-Fi Positioning System），其核心中枢就是运行在 root 权限下的守护进程 —— locationd。

1. Wi-Fi 与基站联合定位的通信链路

当某个应用通过 CLLocationManager 请求精度较高的位置时，locationd 会执行以下流水线：

  1. 本地环境快照采样：调用无线网卡与蜂窝基带，快速嗅探收集当前设备周边广播的所有 Wi-Fi 路由器的 MAC 地址（BSSID）、信号强度（RSSI），以及当前连接和监测到的基站标识（包括 MCC 移动国家代码、MNC 移动网络代码、LAC 位置区码和 Cell ID）；
  2. 发起 WLOC 协议查询：将收集到的 Wi-Fi 和基站列表打包为二进制数据，通过 HTTPS POST 请求发送给苹果的云端定位服务器。在海外或通用网络下，请求的目标域名通常是 gs-loc.apple.com 或 gsp-ssl.ls.apple.com；而在中国大陆地区的行货设备上，为遵循合规要求，请求会被分流至高德提供的端点（如 bluedot.is.autonavi.com 或 gs-loc-cn.apple.com），接口路径统一为 /clls/wloc；
  3. 空间参考系下发与三角加权：苹果的 WLOC 服务器检索全球数十亿个热点与基站的物理坐标数据库后，将这些 Wi-Fi 和基站对应的真实经度、纬度、海拔及置信半径（Horizontal Accuracy）打包在响应报文中返回给手机；
  4. 终端自主加权解算：locationd 结合自身扫描到的各信号源 RSSI 衰减模型，运行加权质心（Weighted Centroid）或多边测量滤波算法，在数毫秒内解算出当前设备的精准位置，并广播给请求定位的所有 App。

2. 定位劫持的破局点

这套设计蕴藏着一个绝妙的技术切入点：locationd 并不在本地存储全球基站数据库，它极度依赖云端返回的参考系数据。

如果我们在网络传输链路中进行中间人解密（MITM），拦截云端向 locationd 返回的 /clls/wloc 响应报文，将其中包含的每一个周边 Wi-Fi 热点和蜂窝基站的坐标，全部改写为我们期望的目标位置（例如将所有附近的路由器坐标强制修改为巴黎埃菲尔铁塔）：

  • locationd 在收到这份被篡改的响应后，基于经典物理测量逻辑，会判定当前设备周边的所有基站和 Wi-Fi 实际上全部聚集在巴黎；
  • 无论本地的算法怎么进行加权或多边解算，最终输出的设备坐标都将无一例外地收敛到目标经纬度上；
  • 更关键的是，这个计算结果由系统原生 locationd 确认并签发，所有调用苹果官方 CoreLocation API 的第三方 App（微信、高德、钉钉、美团、Tinder 等）都会透明接收到这个被改写的系统级 GPS 坐标！

二、 协议逆向：解剖 Apple WLOC 封包的二进制骨架

虽然理论逻辑清晰，但在实际落地中，苹果的 /clls/wloc 响应报文绝不是一个普普通通的 JSON 文本，而是一套经历了多次演化、嵌套深厚且高度紧凑的私有二进制结构。

在深入研读 iOS-Location-Spoofer-Web 的核心驱动脚本 location-spoofer.js 时，我梳理出了其完整的二进制封包骨架：

1. 四类外层封包容器的识别

苹果定位服务响应在外层会采用不同的封箱协议包裹内部的 Protobuf 数据流：

  1. 结构化 ARPC（Apple RPC）封包：苹果早期及部分特定系统组件采用的 RPC 格式，包含大端序（Big-Endian）的 16 位协议版本、以 Pascal 字符串形式存储的 Locale 区域、AppIdentifier 与 OS 版本号，以及 32 位的 Function ID 和 32 位有效载荷长度；
  2. Synthetic 封包：以特定的 8 字节序列 0x00, 0x01, 0x00, 0x00, 0x00, 0x01, 0x00, 0x00 开头，紧随其后的是 2 字节（UInt16）的大端序负载长度；
  3. Marker 特征封包：报文中包含 0x00, 0x00, 0x00, 0x01, 0x00, 0x00 特征签名与 2 字节载荷长度；
  4. Bare Protobuf 裸流：不包含任何私有头，直接以 Protobuf 的 Tag 字节打头。

2. Protobuf 内层结构与经纬度定点化编码

一旦将外层容器剥离，展现在面前的便是一串合法的 Google Protocol Buffers 二进制流。在 WLOC 根消息中：

  • Tag 2（Wire Type 2，Length-delimited）：代表周围扫描到的 Wi-Fi 列表。在每一个 Wi-Fi 消息内部，字段编号 2（Field 2）是一个内嵌的 Location 子消息；
  • Tag 22 与 Tag 24（Wire Type 2）：分别对应蜂窝网络中的 LTE/5G 与 GSM/CDMA 基站列表。在基站消息内部，字段编号 5（Field 5）是内嵌的 Location 子消息。

而在最终的 Location 子消息内，经纬度的存储方式极其精妙 —— 它没有使用体积较大的 64 位双精度浮点数（Fixed64），而是采用了乘上 10810^8108 的有符号 64 位定点整数（Signed Varint）：

EncodedValue=round⁡(Degrees×100 000 000)\text{EncodedValue} = \operatorname{round}(\text{Degrees} \times 100\,000\,000) EncodedValue=round(Degrees×100000000)

例如，北京天安门的纬度 39.90872° 经过放大后变为整数 3990872000，再转换为 Protobuf 的 Varint 变长字节流进行存储。这既能以极其微小的体积保留高达 8 位小数（分米级）的空间精度，又显著降低了序列化开销。

三、 突破边界：location-spoofer.js 的四大工程创新

在很多早期尝试通过代理改写 WLOC 的脚本中，经常会出现“在某些 iOS 版本上代理频繁崩溃”、“改写后地图出现跳跃闪烁”或“系统直接报错无定位”的问题。iOS-Location-Spoofer-Web 针对这些棘手痛点，在客户端改写模块中做出了极具深度的工程重构。

1. 纯 JS 64 位 Varint 引擎：斩断 BigInt 依赖枷锁

在标准的 JavaScript 环境中，处理像 399087200039908720003990872000 这样的大整数及其移位操作时，最自然的方案是使用 ES2020 引入的 BigInt。

然而，在 iOS 平台的各代系统演进中，Shadowrocket 内部挂载的 JavaScriptCore 引擎在不同 iOS 大版本（尤其是 iOS 12 ~ iOS 14 老设备或特殊系统分支）下对 BigInt 的语法解析和内置方法支持极不均匀，极易因为语法不兼容导致脚本在加载阶段静默报错中断。

作者在 location-spoofer.js 中构建了一套纯 JavaScript 的 64 位无符号与有符号 Varint 编解码器（Varint64）。它将一个 64 位长整数巧妙地拆解为两个 32 位的无符号字：low（低 32 位）和 high（高 32 位），完全依靠位运算（>>> 0、>>> 7、<< 25）和纯双精度算术（UINT32_MOD = 4294967296）完成补码转换与流式展开：

// 零 BigInt 依赖的纯 JS 64 位有符号 Varint 拆解
fromSigned: function (val) {
  var num = Math.trunc(Number(val));
  if (!Number.isFinite(num) || Math.abs(num) > Varint64.MAX_SAFE) {
    throw new Error("Invalid signed int64 value: " + val);
  }
  if (num >= 0) {
    return Varint64.fromUnsigned(num);
  }
  // 负数求二进制补码运算 (Two's Complement)
  var pos = Varint64.fromUnsigned(-num);
  var low = (~pos.low + 1) >>> 0;
  var carry = low === 0 ? 1 : 0;
  var high = (~pos.high + carry) >>> 0;
  return { low: low, high: high };
}

这段实现使得脚本无论是在古老的 iPhone 6s（iOS 12）上，还是在最新的 iPhone 16 Pro（iOS 18+）上，都能以 100% 原生的确定性毫秒级运行。

2. WLOC 最小改写策略（Minimal Rewrite）：消除指纹防封

早期许多脚本采用“全量重建模式（Synthetic Rebuilding）”—— 在捕获到 WLOC 请求后，丢弃服务器下发的所有未知字段，强行手动拼接一个只有经纬度的极简响应包回传给系统。

这种粗暴的做法在 iOS 16 及以后的系统中引发了灾难性的后果：苹果在 WLOC 根消息中悄然加入了校验字段、服务端时间戳令牌（Field 3、Field 4、Field 33 等）以及特定的基站配对特征。一旦将这些未知字段丢弃，locationd 会立刻检测到协议指纹破损，判定云端下发的数据遭遇重放攻击或数据损坏，从而直接触发回滚，转而强行读取纯硬件弱 GPS，导致改写彻底失效。

本项目坚决贯彻了“WLOC 最小改写（Minimal Rewrite）”策略：

  • 全流程采用流式遍历，把原响应中的字段按 Tag 拆分成独立的切片；
  • 只有在命中了 Wi-Fi（Field 2）或基站（Field 22/24）内部的 Location 子消息，且该消息内真实存在经纬度 Varint 时，才将 Field 1（纬度）、Field 2（经度）和 Field 3（水平精度）换成目标字节；
  • 原始响应中的所有未知根级字段、设备上下文标识与安全特征令牌，一律 100% 原样保留并直通透传！
function patchLocationRecord(locationBytes, config) {
  if (!locationBytes || locationBytes.length === 0) return locationBytes;
  var fields = ProtobufEngine.readFields(locationBytes);
  var hasLat = false, hasLon = false;

  for (var i = 0; i < fields.length; i += 1) {
    if (fields[i].fieldNumber === 1 && fields[i].wireType === 0) hasLat = true;
    if (fields[i].fieldNumber === 2 && fields[i].wireType === 0) hasLon = true;
  }
  // 若无经纬度结构，原样放行，杜绝破坏非空间响应
  if (!hasLat || !hasLon) return locationBytes;

  var parts = [];
  for (i = 0; i < fields.length; i += 1) {
    var f = fields[i];
    if (f.fieldNumber === 1 && f.wireType === 0) {
      parts.push(ProtobufEngine.makeVarintField(1, coordToInt(config.latitude)));
    } else if (f.fieldNumber === 2 && f.wireType === 0) {
      parts.push(ProtobufEngine.makeVarintField(2, coordToInt(config.longitude)));
    } else if (f.fieldNumber === 3 && f.wireType === 0) {
      parts.push(ProtobufEngine.makeVarintField(3, config.horizontalAccuracy));
    } else {
      // 关键：海拔、置信度以及其他未知空间属性完整透传
      parts.push(f.raw);
    }
  }
  return ByteUtils.concat(parts);
}

3. 滑窗特征扫描兜底（Sliding Window Fallback）

苹果在不同的 iOS 测试版（Beta）或不同地区分发机制中，有时会动态调整前缀长度或插入数个字节的追踪标记。一旦外层的严格容器解析（ARPC / Synthetic / Marker）全部未命中，传统脚本就会束手无策。

本项目内置了 scanPatchRawBuffer 滑窗探测机制：

  • 在报文的前 0 ~ 256 字节区间内以步长滑动，主动探测候选字节是否符合 Protobuf Tag 的结构特征（looksLikeWlocPayload）；
  • 一旦在某个偏移量处成功反序列化并完成 Wi-Fi/基站实体的命中，立刻封装成标准的 Synthetic 响应输出。这层自适应兜底使得整个劫持系统具备了跨越版本未知的强健韧性。

4. 故障安全放行（Fail-Open）机制

在网络安全工程中，代理脚本最忌讳在异常时“卡死断网”。脚本明确遵循 Fail-Open（故障开放） 原则：

  • 无论网络超时、Protobuf 解析格式畸变还是服务端报错，只要捕获到无法处理的异常，代码一律以 $done({}) 快速退场，将原始报文无损放行给系统；
  • 这一机制确保了即使遭遇极端特殊响应，用户的 iPhone 也绝不会遭遇无故断网或系统定位服务僵死的惨剧。

四、 协同闭环：从 Serverless 架构到全栈地图交互

仅有一个代理改写脚本是不够的。如果每次改个坐标都要打开电脑去改脚本里的经纬度参数，体验依然十分割裂。iOS-Location-Spoofer-Web 的另一大亮点，在于其构建了一套近乎零成本的单用户 Serverless 远程控制体系。

1. 极简 Serverless 边缘中枢

项目的后端完全基于 Cloudflare Pages + Functions + Workers KV 构建：

  • 存储层（KV Namespace）：创建单个名为 SPOOFER_DATA 的键值对存储，存放当前的定位坐标（loc）与用户收藏夹数据（favorites）；
  • 动态模块生成（ios-location-spoofer.sgmodule.js）：这是整个项目最亮眼的设计之一。用户在手机浏览器中打开部署好的 Pages 面板后，该函数会自动根据当前访问的 Host 域名和用户的 Token 参数，动态渲染并输出一份 Shadowrocket 专属的 .sgmodule 模块配置文件。用户只需在面板的设置中点击一键复制，粘贴进小火箭即可全自动完成规则绑定与订阅，彻底摆脱了手动编辑配置文件的痛苦；
  • 配置同步 API（loc.json.js & set.js）：提供低延迟的读写接口。Shadowrocket 拦截到 /clls/wloc 响应时，通过内置的 $httpClient.get 异步轮询 loc.json，实现毫秒级的跨端坐标动态下发。

2. 消除 500 米偏差：火星坐标系（GCJ-02）与 WGS-84 无缝转换

在国内进行地图应用开发，绕不开国家测绘局制定的火星坐标系（GCJ-02 加密偏移）。很多开发者在自制定位工具时常常发现：自己在高德地图上选了一个点，改写生效后地图上的小蓝点却莫名其妙偏离了 300 到 500 米。

这是因为：

  • 国内高德底图的瓦片数据采用的是经过非线性偏移的 GCJ-02 坐标；
  • 而苹果的底层 locationd 以及国际 GPS 卫星信号统一使用标准的 WGS-84 椭球体坐标！

前端面板（index.html）在底层完整集成了双向纠偏算法库（GCJ）：

// 当用户在地图上移动准星时：
function onMapMove() {
  var c = map.getCenter();
  // 若使用 CartoDB 或 Esri 卫星图，直接读取 WGS-84；若使用高德底图，执行 g2w 逆向解偏
  var w = (currentLayer === 'osm' || currentLayer === 'esri') ? [c.lat, c.lng] : GCJ.g2w(c.lat, c.lng);
  WGS = { lat: w[0], lng: w[1] };
  updateBubble();
  scheduleElevation();
}

通过在前端视口渲染与物理保存之间设立一层透明的 GCJ.g2w（火星转大地）与 GCJ.w2g（大地转火星）隔离层，并设定 0.000015°（约 1.7 米）的浮点容差对齐，确保了无论在国际卫星底图还是国内高德街道图上，准星所指的位置与手机系统最终生效的位置达到像素级的绝对重合。

3. Open-Meteo 海拔自动测绘

很多反作弊策略或高阶 LBS 应用（例如涉及无人机禁飞区、高差围栏等）会监测设备的 Altitude（海拔高度）。如果改写了经纬度却把海拔长期固定在 0 米，极易引起应用层的风控怀疑。

面板巧妙地引入了 Open-Meteo 的公开地形测绘接口（api.open-meteo.com/v1/elevation）：

  • 只要用户在地图上滑动准星停顿超过 800ms（防抖触发）；
  • 前端自动向测绘 API 查询当前经纬度所在的地表真实海拔；
  • 自动将海拔值回填进高级参数面板中随坐标一同提交，使伪造出的三维地理信息无懈可击。

五、 实操部署与踩坑全记录

为了验证该方案在真实环境下的可用度，我按照其官方架构将其完整部署并进行了深度实测。

1. 部署架构清单

整个搭建过程可以在 5 分钟内零成本完成：

  1. GitHub Fork 仓库：将代码 Fork 至个人 GitHub；
  2. Cloudflare Pages 绑定：创建 Pages 项目，框架预设选择 None，构建命令填 exit 0，构建输出目录填 public；
  3. 注入环境变量：
    • TOKEN：私有访问密码（用于面板鉴权防盗刷）；
    • AMAP_KEY（可选）：高德 Web 服务 Key，用于在国内快速搜索地名；
  4. 绑定 KV：在 Pages 设置中将变量名 SPOOFER_DATA 绑定到之前新建的同名 Workers KV。

2. 手机端联调四步法

在手机端的配置也极其优雅：

  1. 安装 PWA 面板：在 iPhone 的 Safari 中打开专属域名，输入 Token 进入，点击 Safari 底部的「分享」→「添加到主屏幕」。得益于对 apple-mobile-web-app-capable 和 black-translucent 状态栏的针对性适配，面板会全屏沉浸运行，外观与原生 App 毫无二致；
  2. 小火箭安装模块：点击面板右上角「设置」复制模块链接，在 Shadowrocket「配置」→「模块」中点击添加并开启；
  3. 信任根证书（关键步骤）：
    • 在 Shadowrocket「HTTPS 解密」中开启中间人攻击（MitM）并生成 CA 证书；
    • 在 iPhone「设置」→「通用」→「VPN 与设备管理」中安装描述文件；
    • 千万别漏了这一步：前往「设置」→「通用」→「关于本机」→「证书信任设置」，将刚安装的 Shadowrocket 根证书勾选为完全信任；
  4. 验证生效与缓存刷新：
    • 在 Web 面板上选定目标地点（例如杭州西湖），点击「锁定」；
    • 前往 iPhone 「设置」→「隐私与安全」→「定位服务」，关闭总开关后等待约 10 秒钟，再重新开启（这一步至关重要，目的是强行清空 locationd 内部驻留的内存缓存）；
    • 打开高德地图、微信或 Apple 原生地图，此时当前位置瞬间瞬移到了西湖断桥之上！

[!TIP]
日常快速切换小窍门：在日常使用中换点时，无需重启 Shadowrocket，只需在面板上点击新位置并锁定，然后通过快捷指令或控制中心关闭/重开一下 Wi-Fi 与定位，系统位置便会自动完成重新解算。

1. 优势与局限性边界

将该方案与市面上的主流手段对比，其优势极其显著：

  • 免线缆、免越狱、单人自建：摆脱了 Mac 和数据线的物理束缚，随时随地在手机端滑动选点；
  • 系统级底层广播：由于篡改发生于 locationd 守护进程层，因此能够跨越几乎所有常规调用 CoreLocation 的 App。

但它也有其固有的技术阿喀琉斯之踵：

  1. 强卫星信号露天场景：如果在完全开阔的操场或高速公路上，iPhone 能够稳定接收到 6 颗以上纯硬件 GNSS 卫星的直接射频信号时，locationd 会提高卫星解算的权重，此时系统定位可能会在真实卫星位置与 WLOC 篡改位置之间产生轻微跳动；
  2. iOS 27+ 的安全暗礁（TLS Pinning）：正如项目作者在兼容性矩阵中所披露的，从 iOS 27 beta 6 开始，苹果在定位系统的核心组件中逐步启用了更为严苛的强证书固定（Certificate Pinning）机制，系统定位守护进程会忽略用户手动安装的第三方根证书。这意味着纯用户态的 MITM 方案正在逼近苹果防御壁垒的极限。

2. 软件工程的道德准则

最后，不得不提的是该开源项目的开源许可协议。作者在代码各处显著标注了 CC BY-NC-SA 4.0 协议，并发表了严厉的防倒卖声明。

在国内二手交易平台与某些封闭灰产圈子中，经常有人将此类优秀的开源网络中间人脚本重新打包，冠以“独家防封打卡神器”的名头向普通用户收取数十乃至数百元的“代搭建费”。技术本身是中立且优雅的，它诞生于开发者对网络协议的好奇心与对自动化测试的追求；任何利用开源成果进行信息差牟利和欺诈的行为，不仅是对开源精神的肆意践踏，更给使用者带来了巨大的安全隐患。

结语

从深入解析 Apple WLOC 的私有二进制封包，到用纯 JavaScript 巧妙实现 64 位 Varint 与流式 Protobuf 引擎；从火星坐标系与海拔测绘的前端无缝纠偏，到利用 Cloudflare Pages 构筑起毫秒级同步的 Serverless 边缘中枢 —— iOS-Location-Spoofer-Web 为我们展示了一场精彩绝伦的移动端协议逆向与前端工程物理学相融合的实战典范。

对于每一位热衷于网络协议逆向、iOS 内部机制探索或现代 Web/Serverless 架构的开发者而言，这都是一份不可多得的、兼具理论深度与极高可玩性的高保真代码样本。
